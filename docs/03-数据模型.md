## 1. 物理数据库全景概览 (22+ 实体表)

  - `idx_inspection_orders_sales_order_no` / `idx_inspection_orders_customer_name`: `(sales_order_no)` / `(customer_name)`（008 出货检验台账按出库单号、客户检索加速）

### 2.3 不合格品待审核池 (`pending_mrb_items`)
> **口径来源**：迁移 `004`（建表）+ `015_mrb_pool_and_flow_wiring.ts`（补齐 6 列 / 状态归一 / 唯一索引）
> + `018_pending_pool_hardening.ts`（`source_order_id` 由 `VARCHAR(64)` 收紧为 `UUID` 并补级联外键）。
> 池是「判定不合格、尚未发起评审」的待办队列，**物理列共 22 列**，业务口径见 `21-MRB不合格品处置数据字段与接口打通设计.md` §4.1。
> **供应商维度（2026-09-23 修订，`docs/39` §2 D2）**：池表**没有** `supplier_code` 列，而 PBAC 的「供应商白名单」维度必须参与行级过滤，
> 故统一**经源检验单换算**：`(SELECT src.supplier_code FROM inspection_orders AS src WHERE src.id = pending_mrb_items.source_order_id)`；
> 源单缺失（子查询为 NULL）即该规则不匹配 —— 保持 fail-closed，不放大可见范围。

| 字段名 | 物理类型 | 约束 | 业务说明 |
|:---|:---|:---|:---|
| `id` | `UUID` | PK, DEFAULT `gen_random_uuid()` | 池条目主键（也是前端「发起评审」入参 `pendingDefectId`） |
| `source_order_id` | `UUID` | NOT NULL, UNIQUE (`uq_pending_mrb_source_order`), FK → `inspection_orders(id)` ON DELETE CASCADE（018 收紧） | 源检验单 ID，**入池幂等键**（同单重复判定走 upsert）。018 之前为 `VARCHAR(64)` 且无外键，源单删除会留下孤儿池条目（列表可见、发起评审 404），故收紧为 `UUID` + 级联删除从结构上根治 |
| `source_order_no` | `VARCHAR(64)` | NOT NULL | 源检验单号（列表「来源检验单」列） |
| `source_stage` | `VARCHAR(32)` | NOT NULL | 检验环节多段编码（`IQC` / `IPQC_CT` / `IPQC_FN` / `OQC_SF` …），筛选按前缀匹配 |
| `material_code` | `VARCHAR(64)` | NOT NULL | 物料编码 |
| `material_name` | `VARCHAR(255)` | NOT NULL | 物料名称 |
| `batch_no` | `VARCHAR(64)` | NOT NULL | 批次号 |
| `defect_qty` | `NUMERIC` | NOT NULL | 不合格数量 |
| `total_qty` | `NUMERIC` | NOT NULL, DEFAULT `defect_qty`（015 新增） | 受检数量（**不良率分母 = 检验单抽样数量**，非报检总数） |
| `defect_rate` | `NUMERIC` | NOT NULL | 不良率(%) = `defect_qty / total_qty × 100`，入池时服务端计算并落库 |
| `fail_reason` | `TEXT` | NOT NULL | 不合格现象/超差实测描述（接口字段 `defectDescription`） |
| `failed_items` | `JSONB` | NOT NULL, DEFAULT `'[]'` | 不合格指标项明细快照（`itemCode` / 实测值 / 判定） |

| `supplier_name` | `VARCHAR(255)` | NULL（015 新增） | 供应商名称（来料 / 委外类不合格）。来源检验单为空的名称由 022 迁移按 `source_order_id` 同步补齐，与台账口径同源 |
| `customer_name` | `VARCHAR(255)` | NULL（015 新增） | 客户名称（出货 / 委外类不合格） |
| `inspector_id` | `VARCHAR(64)` | NULL（015 新增） | 源检验单检验人 ID |

| `status` | `VARCHAR(32)` | NOT NULL, DEFAULT `'PENDING_INITIATE'`, CHECK 三态 | `PENDING_INITIATE`（待发起评审）/ `INITIATED`（已发起评审）/ `DISMISSED`（撤销）；015 已把历史 `PENDING_REVIEW` 归一 |

### 2.4 MRB 评审工单 (`mrb_reviews`) 与会签 JSONB
> **口径来源**：迁移 `004`（建表）+ `015`（补齐 6 列：`pending_defect_id` / `review_flow_id` / `urgency_level` / `review_notes` / `disposed_at` / `disposed_by`）。
> **物理列共 24 列**；会签不单独建表，统一存 `approvers JSONB`（`MRBApproverAction` 数组）。
>
> **供应商维度（2026-09-23 修订，`docs/39` §2 D4）**：MRB 表同样无 `supplier_code` 列，供应商维度按
> `(SELECT src.supplier_code FROM inspection_orders AS src WHERE src.order_no = mrb_reviews.source_order_no)` 换算（`source_order_no` 存的是检验单号）。

| 字段名 | 物理类型 | 约束 | 业务说明 |
|:---|:---|:---|:---|
| `id` | `UUID` | PK | 工单主键 |
| `mrb_no` | `VARCHAR(64)` | UNIQUE NOT NULL | MRB 单号（`MRB-YYYYMMDD-XXX`） |
| `source_type` | `VARCHAR(64)` | NOT NULL, CHECK | 不合格来源：`INCOMING_FAIL` / `PROCESS_FAIL` / `SHIPMENT_FAIL` / `SUBCONTRACT_FAIL`（驱动评审流程路由） |
| `source_order_no` | `VARCHAR(64)` | NOT NULL | 来源检验单号（检验人 `inspectorName` 读侧按此列联表派生） |
| `batch_no` / `material_code` / `material_name` | `VARCHAR` | NOT NULL | 批次与物料快照 |
| `workshop_code` | `VARCHAR(64)` | NULL | 车间编码（过程检验场景） |
| `defect_description` | `TEXT` | NOT NULL | 不合格现象描述 |
| `defect_qty` | `NUMERIC` | NOT NULL | 不合格数量 |
| `status` | `VARCHAR(32)` | NOT NULL, DEFAULT `'PENDING_REVIEW'`, CHECK 四态 | `PENDING_REVIEW` / `UNDER_REVIEW` / `DISPOSED` / `REJECTED` |
| `disposition` | `VARCHAR(32)` | NULL, CHECK 四类 | `SCRAP`（报废）/ `REWORK`（返工）/ `RETURN_TO_VENDOR`（退货）/ `CONCESSION`（特采放行） |
| `disposition_notes` | `TEXT` | NULL | 处置决议理由与防范措施（接口字段 `dispositionReason` / `dispositionNotes`） |
| `approvers` | `JSONB` | NOT NULL, DEFAULT `'[]'` | 多方会签历史：`userId` / `userName` / `roleCode`（QA_MGR / TECH_DIR / PROD_SUP / MGMT_DIR）/ `action` / `comment` / `signatureUrl` / `signedAt` |
| `concession_attachment_url` | `TEXT` | NULL | 特采（让步接收）必须携带的客户书面签署件；缺失时服务端返回 `400 CONCESSION_NOT_SIGNED_OFF`，**不做任何默认兜底** |
| `confidentiality_level` | `SMALLINT` | NOT NULL, DEFAULT `1`, CHECK 1~4 | 保密级别 |
| `pending_defect_id` | `UUID` | NULL, FK → `pending_mrb_items(id)` ON DELETE SET NULL（015 新增） | 池 → MRB 正向溯源 |
| `review_flow_id` | `UUID` | NULL, FK → `review_flows(id)` ON DELETE SET NULL（015 新增） | 发起时选用的评审流程定义 |
| `urgency_level` | `VARCHAR(16)` | NOT NULL, DEFAULT `'NORMAL'`, CHECK 三值（015 新增） | 紧急程度：`NORMAL` / `URGENT` / `CRITICAL` |
| `review_notes` | `TEXT` | NULL（015 新增） | 发起说明/建议处置方向（与不合格描述分离） |
| `disposed_at` | `TIMESTAMPTZ` | NULL（015 新增） | 处置闭环时间（KPI「本月评审率」的处置侧锚点） |
| `disposed_by` | `VARCHAR(64)` | NULL（015 新增） | 最终裁决人姓名 |

### 2.9 编号流水号池 (`inspection_order_no_sequences` / `inspection_plan_code_sequences`)

单据类编码（检验单号 `order_no`、质检方案编码 `plan_code`）**不使用数据库自增序列**，
而是按 **(前缀, 日期)** 在池表中原子 upsert 取号：一行 = 某前缀在某一天的已用最大流水号，
该行即并发取号的排他锁点。取号发生在业务事务内，因此事务回滚时流水号一并回滚（不漏号、不跳号）。

| 表 | 创建迁移 | 服务的编码 | 编码形态 | 流水段 |
|:---|:---|:---|:---|:---|
| `inspection_order_no_sequences` | `012` | 检验单号 `inspection_orders.order_no` | `{类型前缀}-{YYYYMMDD}-{NNNN}` | 4 位 |
| `inspection_plan_code_sequences` | `017` | 方案编码 `inspection_plans.plan_code` | `QP-{YYYYMMDD}-{NNN}` | 3 位 |

两表列结构同构，**只承担取号、不存业务数据**：

| 列 | 类型 | 约束 | 说明 |
|:---|:---|:---|:---|
| `prefix` | `VARCHAR(32)` | NOT NULL，联合主键之一 | 编码前缀（如 `INS` / `OQC-SH` / `QP`） |
| `day_key` | `CHAR(8)` | NOT NULL，联合主键之一 | 建单 / 创建日期键 `YYYYMMDD`（本地时区自然日，见 `day-key.ts`） |
| `last_seq` | `INTEGER` | NOT NULL，DEFAULT 0 | 当日该前缀已分配到的最大流水号 |
| `updated_at` | `TIMESTAMPTZ` | NOT NULL，DEFAULT `NOW()` | 最近一次取号时间 |

迁移 `017` 在建表的同时，把库中**已存在的合规方案编码**（`^QP-\d{8}-\d{3}$`）按 (前缀, 日期)
取最大值回填进池，避免新建方案编码与历史编码撞号；`QP-IQC-304SS` 这类人工语义编码不参与回填
（其文本形态与流水号编码不可能相等）。

> 唯一口径落点 —— 领域侧规则函数：`toLocalDayKey()`（`packages/domain/src/services/day-key.ts`）、
> `formatInspectionOrderNo()`（`inspection-order-number.ts`）、`formatInspectionPlanCode()`（`inspection-plan-number.ts`）；
> 仓储侧取号：`allocateOrderNoSequence()`（`inspection-order-repository.ts`）、
> `allocatePlanCodeSequence()`（`inspection-plan-repository.ts`）。

| `new_category_code` | `VARCHAR(64)` | NOT NULL | 归位后的分类（`CAT-FIN-MACH`） |
| `note` | `TEXT` | NULL | 归位依据说明 |
| `migrated_at` | `TIMESTAMPTZ` | NOT NULL，DEFAULT `NOW()` | 归位时间 |

> 口径：本表只增不改；`pnpm db:seed` 从零播种的库「生来就是新分类」，本表为空（已纳入种子 `TRUNCATE` 清单）。
> 完整设计与 PBAC 同步口径见 `docs/33-委外检验录入表单演示值清理与编码族收敛设计.md` §4。

### 2.13 委外单号 / 委外批次号改号留痕 (`outsource_reference_renumberings`)

迁移 `028_unify_outsource_references` 把 7 条委外行的 `inspection_orders.outsource_no` 由 `WW-` 号段
统一为 ERP 口径 `WWJG-`（`DlyndxSC`, VchType=181），并把同 7 行与委外加工单号**恒同值**的 `batch_no`
解耦为批次号形态 `B{YYYYMMDD}-{NNN}`。每行改号逐条留痕，既作「改号 ↔ 对账」依据，也作 `down()` 回滚依据。

| 列 | 类型 | 约束 | 说明 |
|:---|:---|:---|:---|
| `id` | `UUID` | PRIMARY KEY，DEFAULT `gen_random_uuid()` | 留痕主键 |
| `order_id` | `UUID` | 与 `kind` 组成 UNIQUE | 被改号的检验单（`inspection_orders.id`） |
| `order_no` | `VARCHAR(64)` | NULL | 被改号单的检验单号（便于人工对账） |
| `kind` | `VARCHAR(16)` | NOT NULL | `OUTSOURCE_NO`（委外加工单号）/ `BATCH_NO`（委外批次号） |
| `old_value` | `VARCHAR(64)` | NOT NULL | 改号前的值（如 `WW-20260705-007`） |
| `new_value` | `VARCHAR(64)` | NOT NULL | 改号后的值（如 `WWJG-20260705-007` / `B20260705-007`） |
| `note` | `TEXT` | NULL | 改号依据说明 |
| `migrated_at` | `TIMESTAMPTZ` | NOT NULL，DEFAULT `NOW()` | 改号时间 |

**同步的活引用**（同一事务内改写，范围由留痕表的 `old_value` 驱动）：
`inspection_orders.outsource_no` / `inspection_orders.batch_no`、`pending_mrb_items.batch_no`、
`mrb_reviews.batch_no`、`batch_trace_nodes.batch_no`（追溯主键）、以及 **未投递** Outbox 事件的
`payload.batchNo` / `payload.outsourceNo`。

> 留痕红线（与 025 / 026 / 027 同款）：`audit_logs.diff_patch` 与 `authorization_logs` **只增不改**；
> 已投递（`PUBLISHED` / `DEAD_LETTER`）的 Outbox 事件**保留原值**，仅追加 `batchNoRenumberedFrom` /
> `outsourceNoRenumberedFrom` 来源标记；两条 2023 历史行 `outsource_no` 为 `NULL`（ERP 侧无对账单），不参与改号。
> `mrb_reviews.source_order_no` 存的是**检验单号**，本轮不变，故无需迁移。
> 完整设计与实测证据见 `docs/34-遗留项收口设计（委外单号与批次口径 + 证书去编造 + 委外录入写路径）.md` §2 / §8.1。
