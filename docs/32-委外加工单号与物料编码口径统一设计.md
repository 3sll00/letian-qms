## 1. 背景与问题

承接 `docs/31`（检验单号统一）：用户在【委外检验】台账上继续指出同一页签内
**「委外加工单号」与「物料编码」两列同样存在「同一列两代形态并存」**。本机库实测（`letian_qms_db`）
定位到两个互不相同的根因。

### 1.1 委外加工单号：不是数据脏，是**读路径兜底伪造**

`inspection_orders.outsource_no` 实测分布（`order_type IN ('OQC_SF','OQC_MACH','OQC_HEAT')`，共 9 行）：

| 行 | `outsource_no` | `batch_no` | 界面实际看到的「委外加工单号」 |
|:---|:---|:---|:---|
| `OQC-SF-20260705-0007/0008`、`OQC-SF-20260706-0001` | `WW-2026070x-00x` | 同值 | `WW-20260705-007` 等 |
| `OQC-MC-2026070x-000x`、`OQC-HT-2026070x-000x` | `WW-2026070x-0xx` | 同值 | `WW-20260705-005` 等 |
| `OQC-SF-20231012-0001` | **NULL** | `B20231010-03` | **`B20231010-03`** |
| `OQC-SF-20231013-0001` | **NULL** | `B20231013-05` | **`B20231013-05`** |

根因是 `inspection-order-repository.ts#mapRow` 的两条兜底（迁移 009 时代写入、迁移 011 文档里明确「不触碰」）：

```ts
// 009 委外检验 (OQC 七分类) 台账字段；委外单号缺失时以批次号兜底，
// 回厂日期缺失时回落到建单日期，保证前端「委外加工单号 / 回厂日期」两列永不为空。
...((row as any).outsourceNo ? { outsourceNo: (row as any).outsourceNo } : row.batchNo ? { outsourceNo: row.batchNo } : {}),
...((row as any).returnDate ? { returnDate: String(row.returnDate).slice(0, 10) } : { returnDate: row.createdAt.toISOString().slice(0, 10) }),
```

**该兜底已被后续口径明确禁止**，属「代码未跟上文档」的漂移：

| 权威出处 | 原话 |
|:---|:---|
| `docs/09` §2.4 §3 表格（界面口径，最新） | 委外加工单号「无（缺失显示 `-`；**不再回落 `batch_no`**——批次号 ≠ 委外加工单号，混用会让台账口径失真）」；回厂日期「无（缺失显示 `-`；**不再回落 `created_at`**——制单时间不是回厂时间）」 |
| `docs/09` §2.4 正文 | 「**委外加工单号无真实值时显示 `-`**，不再以批次号顶替」 |
| `scripts/testing/README.md` §断言口径 | 「**入库单号 / 委外加工单号 / 回厂日期不得是推导值**：历史实现用 `'RK-' + 检验单号` 合成入库单号、用 `batch_no` 顶替委外加工单号、用 `created_at` 顶替回厂日期——这些都会让「链路是否真打通」无法判断」 |
| `docs/15` §6.3（旧） | 「`outsourceNo`：优先取 `outsource_no`，为空时回落 `batch_no`；`returnDate`：…回落 `created_at`」← **本条已过时，本设计 §2 予以更正** |

前端 `OutsourceList.tsx` 早已按新口径写成 `o.outsourceNo ?? '-'`，但接口从不返回 `null`（永远被兜底填满），
所以 `-` 的语义在真实链路上**从未生效**——用户在页面上看到的就是 `B20231010-03` 这类批次号。

### 1.2 物料编码：主数据里并存两套编码族

`materials` 实测 17 行，编码分两族：

| 编码族 | 行数 | 来源 | 分类 |
|:---|:---|:---|:---|
| `MAT-*`（如 `MAT-BLT-109-M10`、`MAT-35CRMO-08`） | 10 | ERP 主数据口径（`docs/26`/`27`/`30` 以 `Ptype.UserCode` → `materials.material_code` 对齐） | `CAT-RAW-WIRE` / `CAT-RAW-ALLOY` / `CAT-FIN-*` / `CAT-SEMI-*` |
| `CP-*`（`CP-001` ~ `CP-007`） | 7 | **原型（WPS 设计稿）遗留**：`docs/16` §6.3「原型里的成品编码 `CP-001` / `CP-002` / `CP-003` 在 `seedMaterials` 中补齐」，`CP-004`~`CP-007` 由 009 委外种子补齐 | 全部 `CAT-FIN-BOLT` / `CAT-FIN-NUT` |

【委外检验】三个页签同时命中两族（表面处理 Tab 全 `MAT-*`；机加工 Tab `CP-004`/`CP-005`；
热处理 Tab `CP-006`/`CP-007`），用户在「物料编码」列看到的就是两代形态。

DB 侧引用面实测（`material_code LIKE 'CP-%'`）：

| 表 | 命中行数 |
|:---|:---|
| `materials` | 7 |
| `inspection_orders` | 8（`CP-001`×2、`CP-002`~`CP-007` 各 1） |
| `batch_trace_nodes` / `inspection_plans` / `mrb_reviews` / `pending_mrb_items` / `material_permissions` / `authorization_logs` | 0 |
| `outbox_events.payload`（文本含 `CP-0`） | 0 |

`material_code` 无任何外键约束（实测 `pg_constraint` 0 条），因此改号不会撞外键。

## 2. 委外加工单号：定稿口径（读路径，无数据迁移）

### 2.1 编号形态

**唯一权威形态 `WW-{YYYYMMDD}-{NNN}`**（ERP 委外加工单号），出处：
`docs/03` §2.1 `outsource_no` 示例 `WW-20260706-010`、`docs/09` §2.4 示例、
`docs/15` §2 示例、`packages/contracts/src/schemas/inspection.ts` 的 `openapi({ example: 'WW-20260706-001' })`、
迁移 `009` 头注释。

> ERP 侧单据前缀为 `WWJG-*`（`docs/07` §4.2：`DlyNdxSC` VchType=181），QMS 台账口径统一用 `WW-` 形态；
> 两者是否为同一号段属 **ERP 集成待确认项**，见 §5 Q1。

### 2.2 读路径禁止推导（本次修复）

`mapRow` 删除两条兜底，使 `outsourceNo` / `returnDate` 只反映物理列：

| 界面列 | 修复后口径 |
|:---|:---|
| 委外加工单号 | 只取 `outsource_no`；为 `NULL` 时不返回该键（前端渲染 `-`） |
| 回厂日期 | 只取 `return_date`；为 `NULL` 时不返回该键（前端渲染 `-`） |

### 2.3 历史委外行（2023 两条）为什么是 `-` 而不是补号

`OQC-SF-20231012-0001` / `OQC-SF-20231013-0001` 的 `batch_no` 为 `B20231010-03` / `B20231013-05`
（2023 代批次号形态），库中 `outsource_no` 为 `NULL`，ERP 侧也没有可对账的委外加工单可查。

* **定稿**：维持 `NULL` → 界面显示 `-`。理由：`outsource_no` 是**外部单据号**，真值只能来自 ERP 委外加工单；
  用「按日期+流水补一个号」填满，等于**制造一条并不存在的对账关系**，与 `docs/09` §2.4 已定稿口径、
  `scripts/testing/README.md` 的「不得是推导值」红线直接冲突。
* **备选（未采用，可随时切换）**：若业务确认这两行在 ERP 里确有委外加工单，应按**真实单号**回填；
  若仅需演示数据形态统一，则按 `docs/31` 的补号先例新增一条 backfill 迁移，取
  `WW-20231012-001` / `WW-20231013-001`（日期段取原单自身日期，当日无既有号故从 `001` 起），
  并用留痕表记录来源供 `down()` 回滚。

### 2.4 回归断言同步

`apps/api/test/integration/outsource-inspection-link.test.ts` 原先把兜底写成断言
（`dbRow.outsourceNo ?? dbRow.batchNo`），本次同步改为 `?? undefined`，即**断言「不得回落」**。

## 3. 物料编码：统一到 `MAT-*` 主数据口径（迁移 026）

### 3.1 命名规则（自既有 10 条 `MAT-*` 归纳）

```
MAT-{品类缩写}-{特征}-{规格}[-{区分属性}]
```

| 片段 | 取值示例 | 说明 |
|:---|:---|:---|
| 品类缩写 | `BLT` 螺栓 / `NUT` 螺母 / `WSH` 垫圈 / `SCR` 螺柱 / `THRD` 搓丝 / `SLV` 轴套 / `CON` 连接件 | 与既有 `MAT-BLT-*` / `MAT-NUT-*` / `MAT-WSH-*` 一致 |
| 特征 | `88` / `109` / `10`（强度等级）、`304SS` / `35CRMO` / `45`（材质）、`FLG`（法兰面）、`SPR`（弹簧） | 强度等级省略小数点（`8.8` → `88`） |
| 规格 | `M10` / `M8` / `20-30` | 杆类用 `M{公称直径}`；双尺寸件用 `-{尺寸}-{尺寸}` |
| 区分属性 | `-40`（长度）、`-HT`（热处理回厂态） | **仅当「品类+特征+规格」在 `materials` 内已存在另一行时追加**，否则省略 |

### 3.2 映射表（本机库实测 7 条）

| 旧编码（原型遗留） | 物料名称 | 规格型号 | 新编码 | 消歧说明 |
|:---|:---|:---|:---|:---|
| `CP-001` | 六角螺栓M10 | M10×30 / 8.8级 / 蓝白锌 | `MAT-BLT-88-M10` | 无冲突 |
| `CP-002` | 六角螺栓M12 | M12×40 / 8.8级 / 发黑 | `MAT-BLT-88-M12-40` | 与既有 `MAT-BLT-88-M12`（M12*60）同等级同直径 → 追加长度 |
| `CP-003` | 法兰螺栓 | M8×25 / 法兰面 / 镀锌 | `MAT-BLT-FLG-M8` | 无冲突（特征位用法兰面） |
| `CP-004` | 精密轴套 | Φ20×30mm / 45# 钢 / 精磨外圆 | `MAT-SLV-45-20-30` | 双尺寸件，规格段自带两个尺寸 |
| `CP-005` | 连接件 | M12 连接件 / 机加工成品 | `MAT-CON-M12` | 无冲突 |
| `CP-006` | 高强度螺栓 | M10×45 / 10.9级 / 热处理回厂 | `MAT-BLT-109-M10-HT` | 与成品态 `MAT-BLT-109-M10`（蓝白锌）同等级同直径同长度 → 追加工艺阶段 |
| `CP-007` | 弹簧垫圈 | Φ10 / 65Mn / 热处理回厂 | `MAT-WSH-SPR-M10` | 无冲突（特征位用弹簧垫圈） |

> `CP-004`（精密轴套）/ `CP-005`（连接件）的 `category_code` 现为 `CAT-FIN-BOLT`（螺栓分类），
> 属既有分类错位；因分类码参与 PBAC 三维隔离（`docs/18`），**本次不动分类**，仅登记为遗留项（§5 Q4）。

### 3.3 引用改写清单

同一事务内改写下列**活引用**：

| 表 | 列 | 本机命中 |
|:---|:---|:---|
| `materials` | `material_code` | 7 |
| `inspection_orders` | `material_code` | 8 |
| `batch_trace_nodes` | `material_code` | 0 |
| `inspection_plans` | `material_code` | 0 |
| `mrb_reviews` | `material_code` | 0 |
| `pending_mrb_items` | `material_code` | 0 |
| `material_permissions` | `material_codes`（JSONB 数组元素） | 0 |
| `outbox_events` | `payload.materialCode` | 0 |

留痕红线（与 `docs/31` §2.3 同款）：

* `material_name` / `specification` / `unit` 为**物料主数据快照**，不随编码改名；
* `authorization_logs.material_code` 属**权限校验留痕**，保持原值，迁移仅打印命中数（本机 0）；
* 已投递 Outbox 事件保留原值，仅追加 `materialCodeRenumberedFrom`。

### 3.4 迁移步骤（`026_unify_material_codes.ts`）

1. 建留痕表 `material_code_renumberings(old_code PK, new_code UNIQUE, material_id, material_name, migrated_at)`；
2. 按 §3.2 的**固定字典**（编码口径是决策，不由数据推导）写入映射，跳过已留痕项以保证幂等；
3. 依次改写 §3.3 的活引用（仅命中映射表的行）；
4. 打印各表命中行数。

### 3.5 回滚（`down()`）

按映射表反向执行：`materials.material_code` 与全部引用还原为旧编码 → 删除映射记录 → 删除留痕表。
