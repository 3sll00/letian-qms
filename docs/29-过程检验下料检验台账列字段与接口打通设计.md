# 过程检验「下料检验」台账列字段与接口打通设计

## 1. 背景与需求

【过程检验】-【下料检验】台账的表格列与业务确认的设计图不一致（多了「工序/关卡」「规格型号」
「检验员」三列，且「数量」「断料长度」「设备」「完成时间」四列的取值口径与图上不同），
需要按图收敛为 **11 列**：

```
检验单号 | MES工单号 | 物料编码 | 物料名称 | 数量 | 断料长度 | 操作员 | 设备 | 完成时间 | 状态 | 操作
```

同时核查这 11 列**每一列是否真的接到数据库字段与后端接口**。核查结论：列级字段本身在库中
都已存在（迁移 `001` 的 `total_qty`、迁移 `007` 的 `work_order_no` / `blanking_length` /
`operator_*` / `equipment_*` / `process_step` / `completed_at`），契约（`InspectionOrderSchema`）
与读侧映射（`mapRow`）也齐备，但**写入路径整条断链**，导致库里这些列实测全是 `NULL`、
台账上「断料长度 / 操作员 / 设备 / 完成时间 / 数量」只能是 `--`。本方案把清单列的
**迁移脚本 + 契约 + 后端接口 + 写路径 + 前端视图** 一并打通。

## 2. 列 ⇄ 字段 ⇄ 物理列对照（口径决策）

| # | 台账列（图） | 前端字段 | 物理列 | 契约 | 展示口径 |
|:--|:---|:---|:---|:---|:---|
| 1 | 检验单号 | `orderNo` | `inspection_orders.order_no` | `orderNo` | 原样展示（蓝色单号链接，点击进详情） |
| 2 | MES工单号 | `workOrderNo` | `work_order_no` | `workOrderNo` | `work_order_no`；为空时按 `batch_no` 兜底（读侧 `mapRow` 口径，见 `docs/28` §2.3） |
| 3 | 物料编码 | `materialCode` | `material_code` | `materialCode` | 原样展示 |
| 4 | 物料名称 | `materialName` | `material_name` | `materialName` | 原样展示（ERP `Ptype.FullName` 快照） |
| 5 | 数量 | `totalQty` | `total_qty` | `totalQty` | **报检批量**（生产/送检总量）。缺失显示 `--`，**不再用 `sampleQty` 顶替** |
| 6 | 断料长度 | `blankingLength` | `blanking_length` | `blankingLength` | `150.2 mm` 形态；缺失显示 `--` |
| 7 | 操作员 | `operatorName` | `operator_name` | `operatorName` | 下料机台作业员姓名快照 |
| 8 | 设备 | `equipmentCode` | `equipment_code` | `equipmentCode` | **设备编号**（如 `EQ-001`），不再用设备名称当主值 |
| 9 | 完成时间 | `completedAt` | `completed_at` | `completedAt` | `YYYY-MM-DD HH:mm`；口径 = 该工序报工/报检登记时间（MES 同步链路 `mes-sync-service` 一直以 `check_date` 写该列） |
| 10 | 状态 | `status` | `status` | `status` | `formatIpqcStatus()` 四态：待检验 / 检验中 / 已合格 / 不合格 |
| 11 | 操作 | — | — | — | 状态为「待检验」→【检验】（录入判定）；其余状态 →【详情】（只读回看，证书打印在详情弹窗内） |

> 「数量」与「断料长度」两类数值各自只认自己那一列：`total_qty` 为空即 `--`，
> 绝不用 `sample_qty` / `batch_no` 等其它列推导出一个「看起来有值」的数（与 `docs/26`
> 「不得出现由其它字段推导出来的伪造值」同一条口径）。

## 3. 核查结论：真正的断链在写入路径

| 环节 | 现状（改造前） | 判定 |
|:---|:---|:---|
| 物理列 | `total_qty`(001) / `work_order_no`、`blanking_length`、`operator_name`、`operator_id`、`equipment_code`、`equipment_name`、`thread_spec`、`inspection_team`、`process_step`、`completed_at`(007) 均已存在 | 已具备，无需新增列 |
| 契约 | `InspectionOrderSchema` / `CreateInspectionOrderRequestSchema` 均已声明上述字段 | 已具备 |
| 读侧 | `mapRow()` 逐列解析并做数值/日期归一 | 已具备 |
| 筛选接口 | 控制器声明了 `operatorName` / `equipmentCode` / `threadSpec` / `inspectionTeam` / `processStep` 查询参数，但 `OrderListQuery` **未声明**、`listOrders()` **无任何条件** —— 控制器用对象展开传参不触发 excess property 检查，**输入即静默丢弃** | **断链 ①（与 `docs/28` §2.2 同型）** |
| 写侧（仓储） | `save()` 的 insert/upsert 只写 `work_order_no`，其余 9 个 IPQC 列**一列都没写**；且 insert 处 `totalQty` 被**硬编码为 `null`** | **断链 ②（读得出、写不进）** |
| 写侧（领域/用例） | 领域聚合根 `InspectionOrder` **不含**这 9 个字段，`toDTO()` 既不吐这些字段也不吐 `totalQty`，还把 `completedAt` 错写成 `updatedAt`；`CreateInspectionOrderCommand` / 控制器未透传 | **断链 ③** |
| 写侧（种子） | `seeds/runner.ts` 建单**从未写入** `totalQty` 与 9 个 IPQC 列，字段只存在于 `seeds/data.ts` 的类型声明里 | **断链 ④** |
| 迁移 | `007` 的回填 `UPDATE ... WHERE order_type = 'IPQC_CT'` 只作用于**执行当时已存在的行**；本机库在 `007` 之后重新播种，新行全部为 `NULL`，回填对它们等于空转 | **断链 ⑤** |
| 前端 | 下料检验列与设计图不一致（14 列），「数量」用 `totalQty \|\| sampleQty` 推导、设备用 `equipmentName \|\| equipmentCode` | **断链 ⑥** |

**实测取证（改造前）**：`GET /api/v1/inspections?inspectionType=IPQC_CT` 返回的 2 行中
`totalQty` / `blankingLength` / `operatorName` / `equipmentCode` / `equipmentName` /
`processStep` / `completedAt` **全部缺失**，台账对应列只可能渲染 `--`。

## 4. 数据库迁移脚本（024）

新增 `packages/infrastructure/src/migrations/024_backfill_ipqc_ledger_fields.ts`（已注册 `runner.ts`）：

1. 对 `order_type = 'IPQC_CT' / 'IPQC_RL' / 'IPQC_FN'` 的行，按 `007` 同一套工序映射
   **只补 NULL 列**（`COALESCE` 语义，绝不覆盖 MES 同步写入的真实值）：
   - `IPQC_CT`：`process_step='自动断料'`、`equipment_code='EQ-CT-01'`、
     `equipment_name='1#全自动高速冷镦机'`、`operator_name='陈操作'`、`operator_id='OP-0102'`、
     `blanking_length` 按物料取 `25.150 / 140.220 / 85.120 / 16.050 / 65.140 / 150.000`；
   - `IPQC_RL`：`手工滚牙` / `EQ-RL-02` / `2#精密数控滚丝机` / `刘滚丝` / `OP-0205` / `thread_spec`；
   - `IPQC_FN`：`process_step='检测入库'` / `inspection_team='终检一组'`（`is_mandatory_gate` 由种子/建单按业务判定写入，迁移不代判）。
2. `completed_at` 为空的 IPQC 行按 `updated_at` 回填（口径见 §2 第 9 列）。
3. **不回填 `total_qty`**：库内没有可信来源（`sample_qty` 是抽检数、不是报检批量），
   按 §2 第 5 列口径宁可显示 `--`，也不推导假值 —— 该列由 §5 的写路径负责，历史行重新播种/重新建单即补齐。
4. `down()` 空实现并注明理由（回填不可逆，与 `011` / `022` / `023` 一致）。

## 5. 契约与后端接口改造

### 5.1 契约（`packages/contracts/src/schemas/inspection.ts`）

字段均已存在，本轮**只补口径注释**：`totalQty` 明示「过程检验台账『数量』列 = 报检批量」、
`completedAt` 明示「工序报工/报检登记时间」、`operatorName`/`operatorId` 明示「机台作业员
（**不是**当前登录操作人）」，避免两个同名字段再次混淆。

### 5.2 仓储（`inspection-order-repository.ts`）

- `save()`：
  - insert：`totalQty` 由硬编码 `null` 改为 `order.totalQty ?? null`，并补写
    `blankingLength` / `operatorName` / `operatorId` / `equipmentCode` / `equipmentName` /
    `threadSpec` / `inspectionTeam` / `processStep` / `completedAt`（ISO 字符串转 `Date`）；
  - `onConflict doUpdateSet`：同一批字段「显式传入才写」，避免旧调用方把已有值覆盖成 NULL。
- `OrderListQuery` 新增 `operatorName` / `equipmentCode` / `threadSpec` / `inspectionTeam` /
  `processStep`，并在 `listOrders()` 落地 5 条 `ILIKE`（值统一走 `escapeLike()`），
  修复控制器已声明却空转的 5 个筛选参数（断链 ①）。

### 5.3 领域与用例

- 领域聚合根 `InspectionOrder` 补齐 9 个过程工序字段（构造入参 + getter + `toDTO()` 输出）
  与独立属性 `totalQty`（`toDTO()` 仅在非 `undefined` 时回吐，落地物理列 `total_qty`），
  并把 `toDTO()` 中错位的 `updatedAt: completedAt` 修正为 `completedAt`。
- `CreateInspectionOrderUseCase`：新增 `ipqcProcess` 入参（嵌套结构，避免与「当前操作人」
  `operatorName` / `operatorId` 同名撞车），建单时写入聚合根；`totalQty: cmd.totalQty` 单独落库。
  控制器侧 `batchQty` 改为 `body.totalQty ?? body.sampleQty`（`batchQty` 只参与 AQL 抽样默认值，
  不再与「数量」列混同）。
- 重建型用例（`save-inspection-draft` / `record-measurements-and-judge`）以 `{...orderDto, ...}` 还原聚合根，
  其 `batchQty: orderDto.sampleQty` 只是 AQL 抽样默认值的占位。因此「数量」**不挂在 `batchQty` 上**，
  而是聚合根新增独立属性 `totalQty`（缺省即 `undefined`、缺省即不落库）：既能建单写入，
  又不会让「暂存草稿」把 `total_qty` 覆写成抽检数（若挂在 `batchQty` 上，草稿保存必然写出 `sampleQty` 假值）。
  9 个过程工序字段同样由构造函数声明 + `...orderDto` 展开自动带入，「暂存草稿 / 录入实测值」的回吐不再丢字段。
- `create-reinspection`：复检单与原单是同一批次，「数量」沿承原单 `totalQty`
  （与 `docs/24` 的「沿承原单单据标识快照」同口径），否则复检行「数量」列必然是 `--`。
- 控制器 `POST /api/v1/inspections`：把请求体的 9 个字段收拢进 `ipqcProcess` 下推，
  并补 `totalQty` 透传（此前契约声明了但被静默丢弃，与 `docs/26` 属同型缺陷）。

## 6. 前端视图改造（`IpqcViews.tsx`）

- 仅调整 `sub === 'blanking'`（下料检验）台账：表头与行按 §2 的 11 列渲染；
  滚丝检验 / 成品检两个子页沿用原有列集（螺纹规格 / 终检班组等专有列不受影响）。
- 列取值口径：
  - 数量：`totalQty`（缺失 `--`）；
  - 断料长度：`formatBlankingLengthMm(blankingLength)` → `150.2 mm`（整数不带小数，否则保留 1 位）；
  - 设备：`equipmentCode`（缺失 `--`）；
  - 完成时间：`formatLedgerDateTime(completedAt)` → `YYYY-MM-DD HH:mm`（沿用本页既有「截取 ISO 串」口径，解析不出即 `--`）；
  - 操作：`待检验` →【检验】按钮（打开录入弹窗）；`检验中 / 已合格 / 不合格 / MRB评审`
    →【详情】按钮（打开只读详情，内含「打印质检证书」）。
- `colSpan`（加载 / 空态）按列数动态取值，避免下料检验页空态跨列错位。

## 7. 验收口径

1. `GET /inspections?type=IPQC_CT` 返回的每行均含 `totalQty` / `workOrderNo` /
   `blankingLength` / `operatorName` / `equipmentCode` / `completedAt` 六个非空字段
   （`total_qty` 由重新播种/建单写入后成立）。
2. 台账逐行与接口逐字段一致：数量=`totalQty`、断料长度=`blankingLength`、操作员=`operatorName`、
   设备=`equipmentCode`、完成时间=`completedAt`、MES工单号=`workOrderNo ?? batchNo`。
3. 11 列表头顺序与设计图一致；「操作」列按状态显示【检验】/【详情】。
4. 筛选接口不再空转：`?type=IPQC_CT&operatorName=陈操作`、`&equipmentCode=EQ-CT-01`、
   `&processStep=自动断料` 命中数 > 0；不存在的值返回 `total = 0`（不退化为全量）。
5. 库中 `blanking_length` / `operator_name` / `equipment_code` / `completed_at` 非空行数
   等于 IPQC 行数（迁移 024 + 重新播种后）。
