# 质检方案设计页数据字段与接口打通设计

> 适用页面：`apps/web/src/pages/plans/index.tsx`（质检方案设计 / 质检方案与指标库）
> 迁移脚本：`packages/infrastructure/src/migrations/016_inspection_plan_field_alignment.ts`
> 相关文档：`03-数据模型.md`、`04-API与导入规范.md`、`09-界面与开源组件.md`、`17-检验录入界面说明与质检方案匹配口径.md`

## 1. 背景与问题定位

「质检方案设计」页第一轮已完成视觉对齐（见 `09-界面与开源组件.md` §2.6），但表格 10 列与 4 张 KPI 卡中，
有 5 处展示值并非来自数据库字段或后端接口，而是前端临时拼接/推导出来的，属于「界面口径与库表口径不一致」：

| # | 页面列 / KPI | 改造前取值路径 | 结论 |
|:--|:--|:--|:--|
| 1 | 方案编号 | `GET /plans` → `items[].planCode` ← `inspection_plans.plan_code` | 已打通 |
| 2 | 方案名称 | `items[].planName` ← `plan_name` | 已打通 |
| 3 | 适用产品 | 前端额外拉取 `GET /master-data/inventory` 得 `materialName`，缺失回退 `material_code` | **缺口 1：物料名称未下沉** |
| 4 | 质检类型 | `items[].inspectionType` ← `inspection_stage` | **缺口 2：库内 CHECK 仅允许 6 类，契约 13 类** |
| 5 | 检验类别 | 生效版本 `items[].metricCategory` 去重 ← `items` JSONB | 已打通 |
| 6 | 检验项目数 | 生效版本 `items.length` ← `items` JSONB | 已打通 |
| 7 | 状态 | 前端按 `versions[].status` 自行推导 `ENABLED/PENDING_APPROVAL/DISABLED` | **缺口 3：方案级状态未下沉** |
| 8 | 创建人 | 前端额外拉取 `GET /master-data/employees` 按 `created_by` 映射姓名 | **缺口 4：创建人姓名未下沉** |
| 9 | 更新时间 | `items[].updatedAt` ← `updated_at` | 已打通 |
| 10 | 操作（编辑 / 复制 / 审批） | `GET /plans/:id`、`POST /plans`、`POST /plans/versions/:versionId/status` | 已打通（审批见 §10 TBD-10，已闭环；编码取号见 §10 TBD-11，已闭环） |
| K1 | 质检方案总数 | 前端 `GET /plans?pageSize=100` 后本地计数 | **缺口 5：KPI 未下沉**（方案数 > 100 时必然算错） |
| K2 | 已启用 | 同上，前端过滤推导 | 缺口 5 |
| K3 | 待审批 | 同上，前端过滤推导 | 缺口 5 |
| K4 | 覆盖产品数 | 同上，前端 `Set(materialCode)` 去重 | 缺口 5 |

另外核实到的 3 处「字段空转」（契约声明了、库里有列或可派生，但接口从不返回）：

1. `InspectionPlanSchema.categoryName` 从未返回，`inspection_plans.category_code` 已存在却查不出分类名；
2. `InspectionPlanSchema.categoryId` / `isCategoryDefault` 对应的 `inspection_plans.category_id` /
   `is_category_default` 列由 `004` 迁移建立后从未被任何代码写入（实测 8 行全为 `NULL` / `false`）；
3. `004` 同时建的 `category_name` / `valid_from` / `valid_to` 三列同样无人写入，其中生效周期已由
   `014` 明确改由 `sampling_config.effectiveStartDate / effectiveEndDate` 承载（见 `03-数据模型.md`）。

此外还有 2 处**接口口径与契约不一致**的业务缺陷（会让页面筛选与列表直接报错或漏数据）：

- `KyselyInspectionPlanRepository` 内硬编码 `INSPECTION_TYPES` 只有 6 个值，按「委外热处理」等委外七分类
  筛选时 `toInspectionType()` 直接抛 `PLAN_INSPECTION_TYPE_INVALID`，与契约 13 值枚举不一致；
- 列表 `categoryCode` 过滤只经主数据 `materials` 反查，`014` 引入的「分类通用方案」
  （`material_code = '' + category_code = X`）永远命中不到，页面「产品分类」下拉对其无效。

本方案的目标：**页面每一列、每张 KPI 卡的取值都必须能追溯到数据库列或后端接口字段**，
前端不再承担名称映射、状态推导与全量聚合。

## 2. 数据库设计（迁移 `016`）

### 2.1 质检类型取值域对齐契约（缺陷修复）

`inspection_plans.inspection_stage` 的 CHECK 约束实际只允许 6 类
（`IQC / IPQC_CT / IPQC_RL / IPQC_FN / OQC_SF / OQC_SH`），而契约 `InspectionTypeEnum` 为 13 类
（含 `OQC_HEAT / OQC_BLACK / OQC_ZINC / OQC_NICKEL / OQC_PHOSPH / OQC_DACRO / OQC_MACH` 委外七分类）。
同库 `inspection_orders.order_type` 已由 `009` 对齐为 13 类，方案表被漏掉，
后果是**委外七分类的质检方案无法落库**（建方案直接触发 CHECK 违规）。

迁移按幂等方式重建约束（DROP + ADD，与 `009` 同一写法），取值直接抄录契约 13 值。

### 2.2 清理 `004` 遗留的空转列（口径统一）

`016` 删除以下 5 列，理由均为「同一语义已有唯一真相源，冗余列只会制造两个数据源」：

| 被删列 | 唯一真相源 | 说明 |
|:--|:--|:--|
| `category_id` | `category_code` + `inventory_categories.id` | 全库主数据引用统一用编码（`materials.category_code` 等），不另存 UUID |
| `category_name` | `category_code` + `inventory_categories.category_name` | 名称属主数据，落快照会产生改名后不一致 |
| `is_category_default` | `014` 的 `material_code = '' + category_code = X` 约定 | 两套「分类通用方案」判定标准互相冲突 |
| `valid_from` / `valid_to` | `sampling_config.effectiveStartDate / effectiveEndDate` | `014` 已定口径：版本级属性统一放 `sampling_config` |

实测该 5 列在现有库中全为空值（`is_category_default` 为建表默认 `false`），删除不丢数据。

### 2.3 名称类字段不落冗余列

`material_name` / `created_by_name` / `category_name` **不新增快照列**，而是在读侧 JOIN 派生，理由：

- 检验工单（`inspection_orders`）落 `material_name`/`inspector_name` 快照，是因为工单是不可变质量记录，
  必须固化「当时检的是什么」；质检方案是可维护配置，物料改名后应即时反映最新主数据；
- 方案列表按 `plan_code` 聚合、当页 ≤ 100 行，`materials.material_code`、
  `inventory_categories.category_code`、`employees.id` 均为唯一索引/PK，JOIN 成本可控；
- 少一次前端主数据全量拉取（`/master-data/employees`、`/master-data/inventory`），
  也避免「名称映射表漏项 → 列表显示 `-`」这类静默降级。

## 3. 契约层（`@letian/contracts`）

`packages/contracts/src/schemas/inspection.ts`：

### 3.1 新增方案级状态枚举

- `PlanStatusEnum = z.enum(['ENABLED', 'PENDING_APPROVAL', 'DISABLED'])`（OpenAPI 组件名 `PlanStatus`），
  与页面「已启用 / 待审批 / 已停用」三色徽标一一对应，是全系统唯一的方案状态口径：
  - `ENABLED`：存在 `version_status = 'ACTIVE'` 的版本；
  - `PENDING_APPROVAL`：无 ACTIVE，但存在 `DRAFT` 版本；
  - `DISABLED`：以上皆无（仅剩 `INACTIVE`）。

### 3.2 `InspectionPlanSchema` 新增字段

| 字段 | 类型 | 来源 | 页面用法 |
|:--|:--|:--|:--|
| `status` | `PlanStatusEnum.optional()` | 由该方案全部版本行派生 | 状态列徽标 |
| `materialName` | `z.string().optional()` | `materials.material_name`（按 `material_code`） | 适用产品 |
| `categoryName` | 已有字段，改为读侧填值 | `inventory_categories.category_name`（按 `category_code`） | 适用产品（分类通用方案兜底） |
| `categoryId` | 已有字段，改为读侧填值 | `inventory_categories.id`（按 `category_code`） | 分类继承模式消费方 |
| `isCategoryDefault` | 已有字段，改为读侧填值 | `material_code = '' AND category_code IS NOT NULL` | 标识分类通用方案 |

### 3.3 `InspectionPlanVersionSchema` 新增字段

- `createdByName: z.string().optional()`：`created_by` 对应 `employees.name`，与同版本的 `createdBy` 一一对应，
  避免方案级再开一个「创建人」字段导致两个数据源。

### 3.4 新增 KPI 契约

- `PlanStatsSchema = { total, enabled, pending, productCount }`（OpenAPI 组件名 `PlanStats`）：
  - `total`：方案数（`count(distinct plan_code)`）；
  - `enabled`：存在 ACTIVE 版本的方案数；
  - `pending`：无 ACTIVE 但有 DRAFT 版本的方案数；
  - `productCount`：`material_code <> ''` 的去重物料数（分类通用方案不计入覆盖产品）。

## 5. 基础设施层（`KyselyInspectionPlanRepository`）

1. `INSPECTION_TYPES` 改为直接引用契约 `InspectionTypeEnum.options`，
   消除「契约 13 值 / 仓储 6 值」的口径漂移（委外七分类筛选不再抛错）。
2. `loadPlanByCode()` 增加三个 LEFT JOIN 派生展示字段：
   - `materials ON materials.material_code = inspection_plans.material_code` → `materialName`；
   - `inventory_categories ON inventory_categories.category_code = inspection_plans.category_code`
     → `categoryName` / `categoryId`；
   - `employees ON employees.id::text = inspection_plans.created_by` → 版本级 `createdByName`。
3. `buildPlanDto()` 补 `status` / `materialName` / `categoryName` / `categoryId` / `isCategoryDefault`；
   `mapVersion()` 补 `createdByName`。
4. `listPlans()` 的 `categoryCode` 过滤改为
   `inspection_plans.category_code = $code OR EXISTS(materials 反查)`，使分类通用方案参与命中
   （`idx_plans_category_stage_status` 已覆盖第一分支）。
5. 新增 `getPlanStats({ permissions })`：单条 CTE 聚合 SQL 一次算出 4 个 KPI，
   仅施加 PBAC 权限过滤，不受页面筛选条件影响（与 `MRB` 页「KPI 不得用当页数据推算」口径一致）。

## 6. 接口层（`apps/api/src/controllers/plans.controller.ts`）

- `GET /api/v1/plans`：返回体字段随契约扩展，无需改路由；`items[]` 内每个方案即携带
  `status / materialName / categoryName / categoryId / isCategoryDefault` 与版本级 `createdByName`。
- 新增 `GET /api/v1/plans/stats`：返回 `{ total, enabled, pending, productCount }`，
  施加与列表一致的 PBAC 过滤，供 4 张 KPI 卡直接渲染。路由注册在 `/:id` 之前。
- `POST /api/v1/plans` 的 **body 校验改用新增的 `CreateInspectionPlanRequestSchema`**（`@letian/contracts`）：读模型 `InspectionPlanSchema` 要求 `versions[].planId / createdBy` 必填，而这两个字段在创建时由服务端派生（版本行 UUID 落库时才生成、创建人取 JWT 操作人），页面无从伪造 —— 在此之前方案设计页的「新建」恒定返回 400（`versions.0.planId: Required; versions.0.createdBy: Required`）。读模型本身未改，方案列表 / 详情响应仍按 `InspectionPlanSchema` 校验。
- 新增 `POST /api/v1/plans/versions/:versionId/status`：**方案版本启停（审批）**。body 只传
  `{ action: 'ACTIVATE' \| 'DEACTIVATE' }`，目标版本由 URL 的**版本行 UUID** 唯一确定，不做任何
  「按方案编码回退」（避免审批落到非预期版本上）；`assertPlanApprover` 按角色门禁
  （`QA_MANAGER` / `ADMIN` / `SYSTEM`，其余 403）。状态机由 `@letian/domain` 的 `InspectionPlan` 保证：
  ① 单激活态（启用新版本时同方案旧 `ACTIVE` 自动转 `INACTIVE`）；② 空指标项版本不可启用；
  ③ `DEACTIVATE` 只接受当前为 `ACTIVE` 的版本。
- `POST /api/v1/plans` 空指标项的**错误收敛**：契约允许省略 `versions`，但领域规则 `PLAN_EMPTY_ITEMS`
  要求版本至少 1 个指标项。`CreatePlanUseCase` 现把该领域异常收敛为 `ValidationFailedError`
  （400 / `validation-failed` + `invalidParams`），不再冒成 500 `internal-server-error`。

## 7. 前端（`apps/web/src/pages/plans/index.tsx`）

1. 删除 `/master-data/employees`、`/master-data/inventory` 两次额外拉取（**仅保留**
   `/master-data/categories` 用于「产品分类」下拉选项，该下拉是筛选器的取值域，不属于表格字段）；
2. `PlanRow.applicableProduct`：物料专属方案取 `materialName`（缺失回退 `materialCode`），
   分类通用方案（`materialCode` 为空）取 `categoryName`，都没有才是 `-`；
3. `PlanRow.creator`：取生效版本的 `createdByName`（无生效版本时取最新版本，与「检验项目数」同版本口径）；
4. `PlanRow.status`：直接使用接口 `status`，删除前端 `planStatusOf()` 推导函数
   （契约缺失时按 `DISABLED` 兜底并保持徽标可渲染）；
5. KPI 改为 `GET /plans/stats` 单请求，不再拉取 `pageSize=100` 全量列表本地聚合。
6. 「产品编码」框内的 `MAT-304SS-05` 由「预填草稿值」改为**灰色占位提示**（`placeholder="MAT-304SS-05"`）：
   设计稿该文本与「请输入方案名称」同为占位灰（RGB 117），原先按真实值预填会让用户点【查询】时
   以库中不存在的示例编码过滤（真实后端复现为 0 条），改为占位后既与设计稿一致，也不再把示例值当过滤条件提交。
7. 「新建质检方案」弹窗（`CreatePlanModal.tsx`）补**版本生效周期**入口：`effectiveStartDate`（默认当天）/ `effectiveEndDate`（留空 = 长期有效）两个日期框，提交前校验起始日不得晚于截止日；请求体显式写 `status: 'DRAFT'`（服务端强制草稿），按钮与成功提示同步改为「保存为新方案草稿 / 待审批后启用」，不再暗示"提交即启用"；
8. `PlanRow.periodHint`：由 `planMatch.ts` 的 `planPeriodHint(生效版本)` 计算，状态列在「已启用 / 待审批 / 已停用」徽标下补一行小字「未生效 / 已过期」（空串不渲染），`title` 给出完整周期；方案详情弹窗补「生效周期」一行。过滤口径与后端 `findActivePlan` 的 SQL 逐字一致（起始日可空 / 截止日可空）。
9. **操作列真实启停**：`toggleVersion(row, action)` 调 `POST /plans/versions/{versionId}/status`，
   成功后以 `setRefreshToken((t) => t + 1)` 刷新列表与 KPI（**不本地改状态**，避免与后端单激活态口径漂移）；
   `DEACTIVATE` 前 `window.confirm` 二次确认。「待审批」行显示【审批】、「已启用」行显示【停用】、
   【复制】始终可用；原先「版本启停接口尚未接入」的假提示已删除。
