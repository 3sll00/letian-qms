## 1. 现状核查

### 1.1 一句话结论

**「合格后传递」今天在 QMS 侧不存在。** 四个环节的建单路径（`POST /api/v1/inspections`）**零上游校验** —— 只取批次排他锁 + PBAC 物料权限；唯一被执行的放行判定只有一个卡点（成品检 / 出货），且以 **MES 侧只读查询**形式存在。而服务端那套「批次级放行规则」实现**从未被任何控制器调用**，是死代码（§1.4）。

### 1.2 环节之间现在靠什么关联（逐条回答「按工单 / 按批次 / 按 BOM 工艺路线 / 按 batch_trace_nodes」）

现状是**六个候选键并存，但没有一个是全链路的**：

| 候选串联键 | 物理载体 | 实际覆盖 | 能否作传递判据 |
|:---|:---|:---|:---|
| **批次号** | `inspection_orders.batch_no` | 同一批次上的多条检验单（返工复检明确复用原单 `batchNo`，见 `create-reinspection.ts`） | ✅ 覆盖「同批次多环节」 |
| **炉批号** | `inspection_orders.furnace_heat_batch_no`（迁移 `004` 建列；`034` 加归一化生成列 + 索引） | **唯一已打通的跨批次关联**：IQC ↔ `OQC_HEAT` ↔ 出货检验（`docs/47`） | ✅ 覆盖「同炉批号」 |
| **MES 生产工单号** | `inspection_orders.work_order_no` | 仅 IPQC 三工序写入，IQC / OQC 不写；读侧为空时用 `batch_no` 兜底（`docs/24` §6 D4） | ⚠️ 仅覆盖 IPQC 内部 |
| **来源单据族** | `inbound_no` / `outsource_no` / `sales_order_no` / `sales_order_po_no` | 描述「本环节的凭证来源」，不表达环节先后 | ⚠️ 仅做一致性提示 |
| **血缘边** | `batch_trace_relations`（`parent_batch` → `child_batch`） | 运行期**唯一写入方是返工→复检**，且源端写伪批次 `${orderNo}:FAIL`、目标端写**复检单号**（`create-reinspection.ts:158`）；真正工序流转边依赖 MES/ERP，**当前无写入方**（`docs/41` §6 R3） | ❌ 现状不可用（P2 目标） |
| **追溯节点** | `batch_trace_nodes` | `batch_no` 有 **UNIQUE 约束 + ON CONFLICT DO UPDATE**（迁移 `002:173`、`docs/41` §4.1）—— **一个批次一个节点、后写覆盖先写**，只表达「本批次最近一个环节」 | ❌ 结构上无法承载多环节链 |

**决定方案形状的关键现状事实**：本项目**跨工序批次号是变化的**。种子/演示链路为
`COIL-20230925-01 → WIRE-20230927-04 → BLANK-20231002-01 → THRD-20231005-02 → HEAT-20231008-01 → PLT-20231010-03 → LOT-2026-FN-01 → SHP-20231012-01`（`packages/infrastructure/src/seeds/data.ts:2510-2591`），环节先后**只由 `batch_trace_relations` 表达**；`docs/47` 的炉批号演示链同样是**每张单一套批次号**（`TEST2609-IQC-001` / `TEST2609-HT-001A~C` / `TEST2609-SH-001`），只靠炉批号串起来。

> 结论：**「按批次串」只在「同批次多环节」成立；真正的「跨工序」串联今天没有可用数据源**，且 **BOM / 工艺路线表在本项目并不存在**（只有 `ORDER_TYPE_STAGE` 的检验类型序位与 MES 工序模板配置，均非链条数据源）。
> 因此本方案把「上游」定义为一个**可解析的锚点集合**（§2.2），而不是假定已存在一条完整的链。

### 1.3 检验类型之间的先后顺序：有定义，但只用于展示、未用于门禁

| 定义位置 | 内容 | 用途 |
|:---|:---|:---|
| `packages/application/src/use-cases/traceability/inspection-stage.ts:26-40` `ORDER_TYPE_STAGE` | `IQC(1) → IPQC_CT(2) → IPQC_RL(3) → IPQC_FN(4) → OQC_*(5) → OQC_SH(6)` + 环节中文名 | **唯一顺序定义**：订单维度台账排序（`get-order-chain.ts`）、追溯节点命名（`register-inspection-trace-node.ts`） |
| `packages/contracts/src/schemas/inspection-groups.ts:12` `INSPECTION_GROUPS` | 检验类型**分组**（IQC / IPQC / OQC / 委外七分类 → MRB 不合格来源类别） | MRB 自动建单来源分类 | 
| `packages/contracts/src/schemas/inspection.ts` 枚举 | `InspectionTypeEnum`(13) / `InspectionStatusEnum`(8) / `OverallDecisionEnum`(3) | 类型与状态枚举，**不含先后** |

**PRD 层面只定义了「一个卡点」而不是「一条链」**：`01-PRD.md` §3.3 成品检强制物理阻断关卡（`MANDATORY_GATE`）+ §3.5 出货检验放行阻断，对应实现 `GET /api/v1/release-gates/{batchNo}`（MES 只读校验）。

**建议定义位置**：把顺序从应用层**下沉到领域层**作为唯一真相（§2.1），`ORDER_TYPE_STAGE` 只保留中文名并**派生** `seq`，避免出现第二份顺序表。

### 1.4 放行判定现存两份实现（其中一份是死代码）

| 位置 | 判定内容 | 是否被执行 |
|:---|:---|:---|
| `apps/api/src/controllers/release-gates.controller.ts:75` | 按 `batch_no` 取该批次 OQC（`OQC_SF`/`OQC_SH`，取不到再回退任意单）→ 查 `mrb_reviews.findByBatchNo` → 409 阻断（`GATE_NOT_INSPECTED` / `GATE_INSPECTING` / `GATE_FAILED` / `GATE_UNDER_MRB`） | ✅ MES 侧调用（纯读、幂等、不写审计） |
| `packages/application/src/use-cases/release-gates/check-release-gate.ts:27` `CheckReleaseGateUseCase` | 取该批次**全部**单 → 要求 `status = COMPLETED` → `FAILED` 必须有 `DISPOSED + CONCESSION` 的 MRB → 写审计 + Outbox | ❌ 仅 `container.ts:160` 注册，**全仓无调用方** |

> 风险：同一件事两处口径（一处要求 `COMPLETED`、一处只要求非 `FAILED`；一处「该批次 OQC 优先」、一处「全部单」，任一不合格即阻断），MES 与 QMS 可能得出相反结论。**P0 必须收敛为一份**（§8 硬约束 4）。

### 1.5 MRB 结论不回写链路（今天的三个缺口）

`decide-mrb-disposition.ts` 当前只做三件事：改 `mrb_reviews`（`status=DISPOSED` + `disposition`）、`REWORK` 时建复检单并把原单置 `RE_INSPECTING`、发 Outbox + 审计。

1. **让步接收（CONCESSION）不解锁 QMS 侧任何东西**：`inspection_orders.overallDecision` 仍是 `FAILED`，`batch_trace_nodes` 节点仍是 `FAILED` —— 看板上特采批次永远显示不合格（`TraceNodeStatusEnum.CONCESSION` 目前**只有种子数据**，运行时无写入方）。
2. **返工后合格解锁是「副作用」而非规则**：复检单与原单**同 `batch_no`**，复检终判 `PASSED` 时按 `batch_no` upsert 覆盖节点，链上看不出「返工 → 复检 → 合格」过程，只看到结论被覆盖。
3. **退货 / 报废没有任何链终止动作**：下游已建未终判的单据不会被冻结。

### 1.6 现状能力矩阵

| 场景 | 今天的行为 | 依据 |
|:---|:---|:---|
| 上游不合格 → 下游建单 | **完全放行**（无校验） | `create-inspection-order.ts`：仅 `acquireXactLock(LOCK_ORDER_{batchNo})` + PBAC |
| 上游检验中 → 下游建单 | **完全放行** | 同上 |
| 上游未建单 → 下游建单 | **完全放行** | 同上 |
| 出货发货放行 | 已阻断（未检 / 检验中 / 不合格 / MRB 中 / 无让步接收） | `release-gates.controller.ts:75-190`（MES 侧读） |
| MRB 让步接收解锁 | **仅在 MES 关卡生效**；QMS 看板与建单仍按不合格处理 | `release-gates.controller.ts:163` |
| MRB 返工后解锁 | 靠「同批次节点覆盖」隐式生效，无显式规则 | `register-inspection-trace-node.ts:68` |

## 2. 口径定义（唯一真相写在哪一层）

### 2.1 分层职责：规则在领域、执法在应用、其余各层只做呈现

| 层 | 角色 | 是否唯一真相 | 说明 |
|:---|:---|:---:|:---|
| **领域层纯函数** | **规则**：`canTransferToNextStage(...)` | ✅ **是** | 纯函数、无 IO。入参 = 本单 + 上游候选集 + MRB 结论；出参 = 结构化 `TransferDecision`。建单 / 关卡 / 看板 / 前端预览**只能消费它**，不得各写一份 `if` |
| **应用层用例** | **执法点**（唯一执行点） | ✅（执行） | 事务内组装数据 → 调纯函数 → 阻断即抛 `422 TRANSFER_BLOCKED` + 落审计 / Outbox |
| 数据库（CHECK / trigger） | 结构与性能保障 | ❌ **不做业务判定** | 不写传递 trigger（理由见 §4.1）；只提供锚点列、归一化生成列与索引 |
| 仓储层 | 取数（上游候选 / MRB / 节点） | ❌ | 归一化与排序口径必须在 SQL 内固定，调用方不得二次排序（`docs/47` D6 教训：`Array.find` 取到了最旧一条） |
| 契约层 | 形状 | ❌ | 只定义 `TransferDecision` 与状态码枚举，不含规则 |
| API 层 | 拦截的**出口** | ❌ | 只做「调用用例 + 把判定翻译成 HTTP」（problem+json，与现有 409 关卡口径并存，见 §4.6） |
| 前端 | 展示 + 体验（禁用） | ❌ | 硬拦截一律以服务端 422 为准；前端禁用只是提前告知，**不做判据** |

> 一句话：**规则在领域（纯函数）、执法在应用（事务内）、数据库只给结构与索引、API 与前端只做呈现。**

### 2.2 上下游关系的定义：四个锚点 + 一张顺序表

不假定已存在完整的链，而是用**「锚点集合 + 顺序表」**定义上下游：

| 锚点 | 定义 | 强度 | 落地状态 |
|:---|:---|:---|:---|
| **A1 同批次** | `batch_no` 等值 | 强（同一物理批次） | ✅ P0 可用 |
| **A2 同炉批号** | `furnace_heat_batch_no` 归一化后等值，默认叠加 `material_code` 相同 | 强（同一冶炼炉 / 同热处理炉） | ✅ P0 可用（复用 `docs/47` 迁移 `034` 的归一化生成列） |
| **A3 同工单** | `work_order_no` 等值（非空） | 中（同一 MES 工单，覆盖 IPQC 三工序） | ✅ P0 可用 |
| **A4 血缘边** | `batch_trace_relations` 的 1 跳上游 | 强（真实工序流转） | ⏳ **P2**（待 MES/ERP 写入方，`docs/41` R3） |

**锚点解析优先级：A1 → A2 → A3 →（P2）A4，命中即停、不混合**（与 `docs/47` §3.2「L1 命中即返回，不混合」同型）。全部未命中 → `UPSTREAM_MISSING`（按 TBD-01 处理）。

**顺序表（传递阶梯）**：由 `ORDER_TYPE_STAGE.seq` 派生，每个环节的门禁上游集合如下：

| 本环节 | 门禁上游 | 备注 |
|:---|:---|:---|
| `IQC` | 无 | 上游是采购入库 / 供应商 MTC，QMS 侧不门禁（TBD-08） |
| `IPQC_CT` | `IQC` | |
| `IPQC_RL` | `IPQC_CT` | |
| `IPQC_FN` | `IPQC_RL` | 同时是 PRD §3.3 定义的成品检强制关卡 |
| `OQC_SF` / `OQC_HEAT` / `OQC_BLACK` / `OQC_ZINC` / `OQC_NICKEL` / `OQC_PHOSPH` / `OQC_DACRO` / `OQC_MACH` | `IPQC_FN` | 委外七分类彼此**并列**（同一批次可先后委外多道工艺），互不为上下游 |
| `OQC_SH` | `OQC_*` 或 `IPQC_FN`（按 `seq` 最大者） | 出货放行；无委外环节时以 `IPQC_FN` 为准 |

### 2.3 传递判定矩阵（上游状态 → 是否放行）

| 上游单状态 | 传递许可 | 理由码 | 说明 |
|:---|:---:|:---|:---|
| 无任何上游单 | 放行（打标） | `UPSTREAM_MISSING` | **默认放行 + 显式标记**；是否升级为阻断见 TBD-01 |
| `PENDING` / `DRAFT` / `INSPECTING` | 阻断 | `UPSTREAM_INSPECTING` | 「上游还在检验中」 |
| `IN_MRB_REVIEW`（MRB 未结案） | 阻断 | `UPSTREAM_UNDER_MRB` | 待 MRB 结论 |
| 终判合格（`overallDecision = PASSED`） | 放行 | `UPSTREAM_PASSED` | 是否要求 `status = COMPLETED` 见 TBD-02 |
| `overallDecision = FAILED`，无 MRB 单 | 阻断 | `UPSTREAM_FAILED` | 不合格未处置 |
| `FAILED` + MRB `DISPOSED / CONCESSION`（且客户授权件在位） | **受限放行** | `UPSTREAM_CONCESSION` | 携带特采举证要求（§4.8） |
| `FAILED` + MRB `DISPOSED / REWORK`，复检单**已终判合格** | 放行 | `UPSTREAM_REWORK_PASSED` | 返工闭环 |
| `FAILED` + MRB `DISPOSED / REWORK`，复检单**未终判** | 阻断 | `UPSTREAM_REINSPECTING` | 复检中 |
| `FAILED` + MRB `DISPOSED / REWORK`，复检再判不合格 | 阻断 | `UPSTREAM_FAILED` | 回到 MRB 分支（是否复用原单见 TBD-05） |
| `FAILED` + MRB `DISPOSED / RETURN_TO_VENDOR` 或 `SCRAP` | 阻断 + **链路终止** | `CHAIN_TERMINATED` | `terminateChain = true`，下游禁止建单、已建单冻结（TBD-06） |

> **术语沿用，不新造**：`CONCESSION` / `REWORK` / `RETURN_TO_VENDOR` / `SCRAP` 全部取自 `MRBDispositionEnum`；`PASSED` / `FAILED` / `INSPECTING` 取自 `InspectionStatusEnum` / `OverallDecisionEnum`（与 `docs/24` §5.1「同名同义、不新造词」同一纪律）。

### 2.4 上游「取哪一张单」（回答跨批次 / 跨工单 / 同环节多张单）

三条确定性规则，缺一不可（本次必须写进领域纯函数，禁止 `Array.find` / 数据库默认顺序）：

1. **候选集 = 上游环节类型 ∩ 锚点等值**（§2.2 优先级，命中即停）。
2. **组内取「最近一次终判」**：`updatedAt DESC → createdAt DESC → orderNo DESC`（与 `heat-batch-trace-service.ts` 的 `pickLatest` 完全同式，复用同一口径）。
3. **返工轮次优先**：同一上游环节若存在复检单（单号形如 `{原单号}-R{n}`，`create-reinspection.ts`），**轮次最高者胜**（复检结论覆盖原结论，与 `docs/47` AC-05「取最近一次终判」同一思想）。

**跨物料**：默认只在 `material_code` 相同时视为同一链路；跨物料命中只提示、不阻断（TBD-03，与 `docs/47` TBD-02 同型）。

## 3. 传递规则要覆盖的场景（10 条逐条作答）

| # | 场景 | 判定 | 理由码 | 判据与动作 | 批次 |
|:---:|:---|:---:|:---|:---|:---:|
| 1 | 来料检验不合格 → 过程检验能否开始 | **阻断** | `UPSTREAM_FAILED` | 取 A1/A2/A3 锚点下该环节最近终判单；`overallDecision = FAILED` 且无生效放行结论 → 拒绝建 IPQC 单 | P0 |
| 2 | 过程检验不合格 → 委外能否发出去 | **阻断** | `UPSTREAM_FAILED` | 拒绝建委外检验单（`OQC_*`）+ 发 Outbox `TRANSFER_BLOCKED` / `BATCH_LOCKED`；**物理拦截需 ERP 消费事件**（TBD-07） | P0 |
| 3 | 委外检验不合格 → 出货检验能否开始 | **阻断** | `UPSTREAM_FAILED` | 拒绝建 `OQC_SH` 单 | P0 |
| 4 | 出货检验不合格 → 能否出货 | **阻断** | `GATE_FAILED`（沿用）/ `UPSTREAM_FAILED` | `GET /release-gates/{batchNo}` 409；证书打印同步禁止（`report-templates` 侧只出合格结论） | P0（已存在，本轮改为同一规则产出） |
| 5 | 上游还在「检验中」→ 下游能否开始 | **阻断** | `UPSTREAM_INSPECTING` | 上游单存在但 `status ∈ {PENDING, DRAFT, INSPECTING}` | P0 |
| 6 | 上游还没建单 → 下游能否开始 | **默认放行 + 打标** | `UPSTREAM_MISSING` | 界面与看板显式提示「上游环节缺失」；是否升级为硬阻断由质量部拍板（TBD-01） | P0 |
| 7 | MRB 判「让步接收」→ 下游能否解锁 | **受限放行** | `UPSTREAM_CONCESSION` | 必须：MRB `status = DISPOSED` 且 `disposition = CONCESSION` **且有客户书面授权件**（缺件即阻断，与 `mrb-state-machine.ts:35` 一致）；下游单必须携带特采标记 | P0 |
| 8 | MRB 判「返工/返修」→ 返工后合格如何恢复 | **条件放行** | `UPSTREAM_REWORK_PASSED` | 解锁条件 = 复检单存在且**已终判合格**；复检未终判 → `UPSTREAM_REINSPECTING` 仍阻断 | P0 |
| 9 | MRB 判「退货/报废」→ 整链如何终止 | **终止** | `CHAIN_TERMINATED` | `terminateChain = true`：下游未建单禁止建单；已建未终判单据冻结并标记；发 Outbox `CHAIN_TERMINATED`（是否自动作废见 TBD-06） | P0 |
| 10 | 跨批次 / 跨工单 / 同环节多张单取哪张 | **三条确定性规则** | —— | §2.4：锚点优先级 → 最近终判 → 轮次最高。跨批次（A2/A3）命中即视为同一链路；同一锚点下多张单按 §2.4 收敛；**禁止取任意一张** | P0 |

> 补充口径（用户未列但必须一起定，否则规则会被绕过）：
> - **`OQC_*` 七分类彼此并列**：同一批次先后做「热处理 → 镀锌」是正常工艺，前者不合格**不阻断**后者（不同炉/不同工序）；只有 `OQC_SH` 才要求全部委外环节放行。
> - **免检 / 不解检（EXEMPT）**：指标级 `EXEMPT` 不影响整单结论；整批免检放行需显式记录豁免原因（TBD-11）。
> - **返工复检单本身不再门禁**：`RE_INSPECTING` 轮次由 `create-reinspection.ts` 直接生成，**不**走建单门禁（否则 MRB 判返工后永远建不出复检单，规则自锁）。

## 4. 改造清单（逐块）

### 4.1 数据库

**结论：P0 零迁移；不用 trigger / CHECK 做业务判定；P1 只加「留痕列」。**

| 项 | 动作 | 说明 |
|:---|:---|:---|
| 传递判定 | **不加 trigger / CHECK** | 理由：① 判定需要跨表聚合（检验单 + MRB + 节点 + 授权件），写进 SQL 等于把业务逻辑埋进数据库；② 判定必须**可撤销重算** —— MRB 结论、上游撤销都会改变结论，trigger 无法"回头解锁"；③ 调用方需要**结构化理由码**（给 MES、看板、前端），trigger 只能抛不透明异常；④ 本项目既有纪律是「写侧一律走用例，控制器不直接写 SQL」（`container.ts` 注释） |

### 4.8 MRB 与传递规则的接口（让步接收 vs 返工必须区别对待）

| MRB 处置 | 对传递规则的作用 | 回写动作（P0 必做） | 下游义务 |
|:---|:---|:---|:---|
| `CONCESSION`（让步接收） | **受限解锁** | 源单结论置 `CONCESSION`（`overallDecision`）；`batch_trace_nodes` 该批次节点状态由 `FAILED` 升为 `CONCESSION`（含 `mrbNo`）；缺客户书面授权件 → **不解锁** | 下游单必须携带特采标记，出货前可举证授权件 |
| `REWORK`（返工/返修） | **条件解锁** | 保持现建复检单行为；复检终判 `PASSED` → 节点覆盖为 `PASSED`（现有 upsert 天然完成），并把源单置 `COMPLETED`；复检未终判 → 仍阻断 | 无（但看板必须能看出轮次） |

## 5. 与 `docs/47`（出货检验炉批号关联）的关系

### 5.1 是同一套链路吗？—— 不是同一件事，但共用同一批锚点与排序口径

| 维度 | `docs/47` 炉批号关联 | 本次「合格后传递」 |
|:---|:---|:---|
| 要解决的问题 | **取值**：出货检验填炉批号后带出上游实测值 | **放行**：上游没合格，下游不许开始 |
| 输入 | 炉批号（`furnace_heat_batch_no`）+ 物料编码 | 本单所在链路的锚点（A1/A2/A3/A4） |
| 输出 | 指标值（`inheritedItems`）+ 源单留痕 | 结构化 `TransferDecision`（放行 / 阻断 + 理由码 + 上游单号） |
| 命中失败时 | **静默空态**、不报错、不弹窗（客户需求 R3） | **必须阻断**（或按 TBD-01 显式打标），绝不"没查到就默认合格" |
| 取哪一张 | 「最佳源单」：L1 `OQC_HEAT` → L2 `IQC`，命中即停，允许跨物料 `GLOBAL` | 「权威上游」：门禁上游环节集合 → §2.4 三条确定性规则；默认不允许跨物料放行 |
| 第一优先级 | 委外热处理 `OQC_HEAT`（客户指定） | IPQC（按传递阶梯），与检验类型优先级无关 |

**结论：两条链共享"锚点 + 归一化 + 排序"三件基础设施，但规则与失败语义完全不同 —— 不能合并成一套逻辑，也不能互相替代。**

### 5.2 怎么复用

1. **归一化复用**：炉批号锚点（A2）直接走迁移 `034` 的生成列 `furnace_heat_batch_no_norm` 与 domain 的 `normalizeHeatBatchNo`，**不新写第二份归一化**。
2. **排序复用**：`pickLatest`（`updatedAt DESC → createdAt DESC → orderNo DESC`）作为 §2.4 规则 2 的同一实现。
3. **状态集合复用（但必须分名）**：`docs/47` 的 `ELIGIBLE_SOURCE_STATUSES`（取值态：只认终判合格）≠ 本次的 `TERMINAL_STATUSES`（判定态）与 `RELEASABLE_STATUSES`（放行态）。三者必须在同一文件相邻声明并互相注释，改一处必须评审另两处。
4. **环节名 / 序位复用**：`inspection-stage.ts` 的环节名与 §2.2 顺序表同一来源（P0 把 `seq` 下沉到 domain，见 §4.3）。
5. **看板复用**：传递状态挂在既有节点/环节结构上（`TraceNode` / `TraceOrderChainStage`），**不新建看板**。

### 5.3 怎么避免两套规则打架（三条硬约束）

1. **锚点归一化只有一处**：门禁不得自写 SQL 归一（`docs/47` 迁移 `034` 已踩过两次转义坑，写在注释里）。
2. **排序只有一处**：禁止 `Array.find` / `orderBy createdAt asc` 直接取首条（`docs/47` D6 的教训：取到了最旧一条）。
3. **`batch_trace_nodes` 的 `CONCESSION` 必须有运行期写入方**：`docs/24` §5.1 已把 `CONCESSION` 定为节点合法状态并明确"由 MRB 评审结论回写"，但**运行期从未实现**（§1.5）。本次 P0 的 MRB 回写就是补这一条 —— 否则看板永远显示 `FAILED`，两套口径同时"正确"且互相矛盾。

### 12.5「平均阻断时长」口径明细规范（P2 固化口径）

在计算传递链 KPI（`GET /api/v1/traceability/transfer-kpis`）中的 `avgBlockDurationSeconds` 时，严格遵守以下业务与度量口径：

1. **统计起点（开始时刻）**：
   - **口径**：取**「下游首次尝试建单被门禁阻断的时间戳」**（即审计日志记录 `action = 'GATE_BLOCKED'` 或 Outbox 记录 `event_type = 'TRANSFER_BLOCKED'` 的最早 `created_at`）。
   - **原因**：若上游虽有不合格，但下游尚未排产建单，物料并未在下游工位发生停滞等待；只有下游发生真实建单动作且被拦截，才形成真实的生产受阻事件。
2. **统计终点（放行时刻）**：
   - **口径**：取**「该下游检验单最终成功创建的时间戳」**（`created_at`）。
   - **放行途径**包括：
     - ① 上游 MRB 做出特采让步接收（`UPSTREAM_CONCESSION`）；
     - ② 上游返工复检合格（`UPSTREAM_REWORK_PASSED`）；
     - ③ 质量主管签署特批豁免放行（`UPSTREAM_OVERRIDDEN`）。
3. **MRB 评审时间算不算？**：
   - **明确计入（算）**！从下游工位被阻断起，等待 MRB 召集、评审、决策并上传授权件的全部时长，属于物料周转停滞的关键组成部分，必须完整计入阻断时长，以真实暴露质量异常响应瓶颈。
4. **单批次多轮阻断计算原则**：
   - 若某一下游单据在放行前被拦截多次（例如 10:00 拦截一次、10:30 再次尝试被拦截、11:00 豁免放行），则以该链路**首次被阻断时刻**（10:00）作为唯一起点，计算单次完整阻断周期（1 小时），不重复统计分母。
5. **尚未放行的在途阻断**：
   - 尚未放行的单据记入「当前阻断数（`currentBlockedCount`）」，其在途阻断时长统计进「在途平均阻断时长」，与已闭环的「历史闭环平均阻断时长（`avgBlockDurationSeconds`）」区分下发。
