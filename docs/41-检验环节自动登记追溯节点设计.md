## 1. 问题现象与复现

用户路径：来料检验单判「不合格」→ 打开【质量追溯看板】，按物料编码 `MAT-304SS-05` 检索 → 命中批次 `B20231013-01`（不锈钢线材 Φ5.0mm），但**最近环节 / 状态 / 关联检验单三列全是「—」**、数据来源写着「仅检验台账」；点该行想开图，界面提示「尚未建立血缘节点」，查不到任何节点详情。

真实库 + 真实 HTTP 复现（2026-09-23）：

| 复现动作 | 实测结果 | 结论 |
|:---|:---|:---|
| `GET /traceability/batches?materialCode=MAT-304SS-05` | 行 `B20231013-01`：`sources = ['INSPECTION_ORDER']`，`stageName` / `nodeStatus` / `inspectionOrderNo` **全部缺省** | 批次行只能靠检验台账拼出来 |
| `GET /traceability/graph/B20231013-01` | **404**（图谱先 `findNode`，无节点即 404） | 点开批次开不出图 |
| 库内 `batch_trace_nodes` | **12 行，`created_at` 全部等于灌库时间 2026-09-23 09:48:50** | 节点表只有种子数据 |
| 全仓 `saveNode(` 调用点 | **唯一调用方是 `packages/infrastructure/src/seeds/runner.ts`** | 运行时**没有**写入口 |

> 与 MRB 那条问题（`docs/39`）同型：不是「权限把人挡掉了」，而是**上游从来没写过这份数据** ——
> 看板左侧批次行来自检验台账（所以看得到），右侧节点 / 图谱来自 `batch_trace_nodes`（所以什么都没有）。

## 2. 根因

| # | 断链点 | 根因 |
|:---:|:---|:---|
| **T1** | 追溯节点无运行时写入方 | 端口 `BatchTraceRepository.saveNode()` 早已实现（`batch_trace_nodes.batch_no` UNIQUE + `ON CONFLICT DO UPDATE` upsert），但**只有种子灌库调用它**；检验单的建单 / 实测 / 终判三条写路径都没有登记节点 |
| **T2** | 图谱以节点为根 | `PenetrateBatchDagUseCase` 先 `findNode(batchNo)`，无节点直接 404 ⇒「点开批次查不到节点详情」是 T1 的必然结果 |
| **T3** | 批次行字段依赖节点 | `SearchTraceBatchesUseCase` 的两路并集设计里，`stageName` / `nodeStatus` / `inspectionOrderNo` **只由节点数据源提供**（`hasNode` 为假时不回填）；检验台账那一路只能给批次号 / 物料 / 时间 ⇒ 三列恒「—」 |
| **T4** | 血缘边同样几乎无写入方 | 全仓 `saveEdge(` 只有 `create-reinspection.ts` 一处（返工 → 复检的拓扑边）；工序流转边依赖 MES/ERP 同步，**本轮不动**（见 §6 R3） |

## 4. 口径定义（定稿）

1. **一个批次一个节点**：`batch_trace_nodes.batch_no` 有 UNIQUE 约束（迁移 `002`），节点表达该批次**当前/最近一个环节**的事实；重复登记按 `ON CONFLICT (batch_no) DO UPDATE` 覆盖，不堆历史节点（过程留痕看审计日志与检验台账）。
2. **登记时机 = 终判**：终判是「本批次该环节检验结论」的唯一落点（与 `docs/39` D1 同源）。**建单不登记** —— 进行中环节的节点由 MES/ERP 同步承担（种子数据里的 `INSPECTING` 节点即该来源），QMS 只登记**有结论**的环节，避免把「刚建单」写成追溯事实。
3. **状态映射终判优先**：`CONCESSION`（特采）**不得**被压成合格；已结单却无终判按「检验中」呈现，**不冒充合格**（与订单维度视图同一函数，见 `inspection-stage.ts`）。
4. **不编造**：执行人优先取检验人，缺失才用终判操作人，仍无写「未登记」；来源单据号只认真实上游单据（IQC = 入库单、IPQC = 工单、委外 = 委外单、出货 = 销售出库单），查不到即**缺省**（界面显示 `—`），不用批次号顶替。
5. **同事务**：节点登记与状态写入、入池在同一事务提交；节点写失败即整个终判回滚 —— 不允许出现「判完了但追溯链断」的单据。
6. **不新增迁移**：节点表结构（含 `020` 加的血缘三列）已在位，本轮只补写入口。

## 6. 遗留与后续（本轮未做）

| # | 项 | 说明 |
|:---:|:---|:---|
| **R1** | 建单 / 进行中环节不登记 | 本轮只在**终判**登记（有结论才成节点）。若要求「检验中」也能在看板上看到环节，需要产品口径确认由 QMS 还是 MES 写（当前口径：MES 侧同步） |
| **R2** | 存量单据无节点 | 修复只对**新终判**生效；历史已终判的检验单仍无节点，需要一次性回填脚本（按 `inspection_orders.batch_no` 分组取最近一张终判单生成节点）。本轮不做，避免把历史数据一次性改写 |
| **R3** | 血缘边（工序流转）仍缺写入方 | `batch_trace_relations` 只有「返工 → 复检」一处写入（`create-reinspection.ts`）。真正的上下游（原材料 → 下料 → 滚丝 → 成品 …）属于 MES/ERP 工序流转数据，QMS 无源可造，**不得凭批次号规则猜测** |
| **R4** | 节点缺炉批号来源 | `TraceNode.furnaceHeatBatchNo` 已就位，但 `InspectionOrder` 契约未暴露 `inspection_orders.furnace_heat_batch_no`（列在库内存在），本轮不为此改契约 |
