# 检验单号历史遗留统一（方案 B）迁移设计

> **版本**：v1.0.0（2026-09-22）
> **关联文档**：`09-界面与开源组件.md` §2.3、`15-委外检验OQC数据字段与接口打通设计.md`、`16-出货检验OQC数据字段与接口打通设计.md` §2.3/§4.4、`25`/`26`/`27`/`30`、`03-数据模型.md`
> **迁移脚本**：`packages/infrastructure/src/migrations/025_unify_inspection_order_numbers.ts`
> **权威级别**：★ 检验单号历史遗留统一的口径基准（旧号 → 新号的唯一对照依据）

---

## 1. 背景与问题

* 【委外检验】表面处理页签的「检验单号」列同时出现两种形态：`INS-20231012-005`（旧）与 `OQC-SF-20260706-0001`（新），用户侧观感为「同一页签格式不统一」。
* 根因：迁移 `012_inspection_order_no_sequences.ts` 只做两件事——建流水号池 `inspection_order_no_sequences`、把**合规**历史号（正则 `^[A-Z0-9-]+-\d{8}-\d{4}$`）回填进池；对不合规的三段式历史号 `INS-{YYYYMMDD}-{NNN}` **刻意未处理**，因为当时改号会断开 MRB / 追溯的文本引用。
* 语义错位：`INS-` 是 `IQC / IPQC_CT / IPQC_RL / IPQC_FN` 的中性前缀，却被 2 条委外（`OQC_SF`）历史行占用。

---

## 2. 定稿口径（方案 B）

1. **单号统一**：全部不合规历史号 `INS-{YYYYMMDD}-{NNN}` 重编为 `{PREFIX}-{YYYYMMDD}-{NNNN}`。日期段保留原单自身日期（不改成迁移日期），前缀按领域唯一口径 `resolveInspectionOrderNoPrefix(order_type)` 推导。
2. **活引用改新号**（同一次迁移、同一事务内）：`inspection_orders.order_no`、`mrb_reviews.source_order_no`、`pending_mrb_items.source_order_no`、`batch_trace_nodes.order_no` / `inspection_order_no`、`external_document_mappings.local_aggregate_id`、**未投递**（`PENDING` / `FAILED`）Outbox 事件的 `aggregate_id` 与 `payload.sourceOrderNo`。复检单号 `{原单号}-R{n}` 同步改写基号。
3. **历史留痕不改写**：
   * `audit_logs` **零改动**。该表由 `prevent_audit_log_tampering` 触发器强制 append-only（任何 `UPDATE` / `DELETE` 直接抛 `55000`），且迁移**不制造伪审计事件**——批量插入 13 条并非真实业务动作的审计记录会污染看板「最近动态」（其口径是 `order by occurred_at desc limit 6`）与审计统计。
   * **已投递**（`PROCESSED` 等终态）的 Outbox 事件保留原值，仅在 `payload` 追加 `renumberedFrom` 字段，避免本地与外部系统记录不可对账。
   * 自由文本日志 `authorization_logs.detail`、`integration_sync_logs.error_message` 属留痕性质，不做改写；迁移会扫描并在执行日志中打印命中数（本机为 0）。
4. **映射表长期留痕**：新增 `inspection_order_no_renumberings`（`old_no` / `new_no` / `order_id` / `order_type` / `migrated_at`），既是「旧号 ↔ 新号」对账依据，也是 `down()` 确定性回滚的依据。
5. **单号池同步**：为每个新键补写 `inspection_order_no_sequences(prefix, day_key, last_seq)`，保证后续新建单不与历史号撞号。

> 口径优先级：**单号本体与活引用一律取新号**；凡展示历史动作的地方（审计、已投递事件、自由文本日志）以「保留原值 + 映射表」对齐，不篡改留痕。

## 4. 迁移步骤（`025_unify_inspection_order_numbers.ts`）

1. 建映射表 `inspection_order_no_renumberings`（幂等 `CREATE TABLE IF NOT EXISTS`）。
2. 用领域函数 `resolveInspectionOrderNoPrefix` + 既有单号在 TypeScript 侧算出「旧号 → 新号」，落库到映射表（同一事务）。
3. 按映射表更新 `inspection_orders.order_no`（含 `-R{n}` 复检行：只改基号，保留轮次后缀）。
4. 按映射表更新活引用：`mrb_reviews.source_order_no`、`pending_mrb_items.source_order_no`、`batch_trace_nodes.order_no` / `inspection_order_no`、`external_document_mappings.local_aggregate_id`。
5. Outbox：未投递事件改引用 + 追加 `renumberedFrom`；已投递事件仅追加 `renumberedFrom`。
6. 补写单号池 `(prefix, day_key, last_seq)`（`ON CONFLICT DO UPDATE` 取 `GREATEST`）。
7. 打印本次迁移统计（改号条数、各引用表命中行数、单号池新增键）。

> 事务性：Kysely `Migrator` 默认对每个迁移包裹事务（`disableTransactions` 未开启），因此上述 1~6 步要么全成功、要么全回滚。

---

## 5. 回滚（`down()`）

按映射表反向执行：活引用还原为旧号 → `inspection_orders.order_no` 还原 → 删除映射表中本次记录 → 单号池键保留（高水位只增不减，回滚后新建单仍不会与历史号撞号）→ 删除映射表。
