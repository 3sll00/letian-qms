## 1. 现状核查：真实测试栈（口径纠正）

**必须纠正的前提**：仓库内**既无 Vitest、也无 Playwright，且不存在 `e2e/` 目录**。

核实证据：`pnpm-lock.yaml` 中 `vitest` / `playwright` / `cypress` / `jest` 命中数**均为 0**；全仓各 `package.json` 亦无对应依赖项。

真实测试栈为四层，全部为**自研脚本式**（无第三方测试运行器）：

| 层 | 载体 | 位置 | 运行入口 | 判定方式 |
|:---|:---|:---|:---|:---|
| 领域 / 基础设施单元 | `tsx` 直跑断言脚本 | `packages/domain/src/__tests__/`、`packages/infrastructure/src/__tests__/` | `pnpm test`（根脚本 `pnpm -r --no-bail run test`） | 抛错即失败，进程退出码非 0 |

| 前端 Mock 契约 | MSW + Zod `parse` | `apps/web/src/mocks/validate.ts` | `pnpm validate:mocks` | 任一数据集与契约不符即非 0 |

## 4. 「合格后传递」测试能力设计（本期 P0 核心）

### 4.1 被测对象

`packages/domain/src/state-machines/inspection-state-machine.ts` 的 8 态矩阵：

```
PENDING → INSPECTING → PASSED → COMPLETED
   ↓          ↓          ↑
 DRAFT ←──────┘       IN_MRB_REVIEW ← FAILED
                         ↓    ↑         ↓
                    RE_INSPECTING ──────┘
```

业务语义：「合格后传递」= 只有 `PASSED`（合格放行）的单据才允许进入 `COMPLETED`（结单归档）并向下游传递；`FAILED` 必须经 MRB 裁决方可改变结论。

### 4.2 性质清单（断言型）

| 编号 | 性质 | 判据 | 若失败意味着 |
|:---|:---|:---|:---|
| **P1（进行中）** | ✅ ① MRB `defect_qty` vs 源单 `fail_qty` 白盒断言（见 §8）；⏳ ② `heat-batch-trace` 契约护栏（依赖 D9 先修） | ✅ 断言在真实库可复现（150 项检查 / 0 不一致），且已证可证伪；⏳ 契约漂移拦截待 D9 |
| **P2** | 合格后不可改判 | 自 `PASSED` 出发的**任意长度**合法路径，终点只能是 `COMPLETED` | 合格单可被回退/重开 → 「合格后传递」护栏失效 |
| **P3** | 终态吸收 | `COMPLETED` 无非自身出边；随机游走一旦到达该态，后续转移必须全部非法 | 已结单仍可流转 → 台账与追溯链被污染 |
| **P4** | 不合格不可静默放行 | 自 `FAILED` 回到 `PASSED` 的**任意路径，必经 `IN_MRB_REVIEW`** | 直接对应「上游不合格却传下去」 |
| **P5** | 无死锁 + 可达性 | ① 任一非终态至少 1 条出边；② `PENDING` 可达 `COMPLETED`（BFS） | 矩阵改动造成孤岛状态 / 单据永久卡死 |

实现要点：P1、P5 为**穷举/确定性**检查；P2~P4 由 fast-check **随机游走**生成状态序列验证（`numRuns` 可配），失败时输出**最小化反例 + 随机种子**用于复现。

### 4.3 诊断清单（非断言）

`PASSED` / `FAILED` 的**全部入边**枚举后，凡入边源**不属于「检验入口态」**（`INSPECTING` / `IN_MRB_REVIEW` / `RE_INSPECTING`）的边，单独列出供业务口径确认，**不判定为失败**。

> 目的：把「语法上合法但业务语义待确认」的边暴露出来，而不擅自替业务判定。

### 4.4 目录、命名与运行方式

| 项 | 定稿 |
|:---|:---|
| 文件 | `packages/domain/src/__tests__/inspection-state-machine.property.test.ts` |
| 命名后缀 | `.property.test.ts` —— 与既有 `.test.ts` 同规范，`tsconfig` 的 `exclude` 已覆盖 `src/**/__tests__/*`，**不会进入构建产物** |
| 运行 | `pnpm --filter @letian/domain exec tsx src/__tests__/inspection-state-machine.property.test.ts`，并追加进 `packages/domain/package.json` 的 `test` 脚本链（随 `pnpm test` 全量跑） |
| 失败判定 | 抛错 → 进程退出码非 0（沿用现有脚本约定），并打印反例与种子 |

### 4.5 与既有基线 `state-machine.test.ts` 的分工（不重复）

| 维度 | 既有 `state-machine.test.ts` | 新增属性测试 |
|:---|:---|:---|
| 方式 | 手写用例，枚举**已知**边 | 随机序列 + 穷举，验证**不变式** |
| 覆盖 | 正向链路、已知非法对 | 任意长度的路径性质（含未枚举到的组合） |

### 4.6 实测结果（2026-09-23，真实运行）

**运行命令**：`pnpm --filter @letian/domain exec tsx src/__tests__/inspection-state-machine.property.test.ts`
**结果**：`[PASS] 合格后传递 属性测试: 6/6`，退出码 `0`；并入 `pnpm test` 后 `@letian/domain` 全量 **10 个脚本全绿**。

| 性质 | 结果 | 说明 |
|:---|:---|:---|
| P1 转移接口自洽 + 非法必抛领域错误码 | ✅ 通过 | 穷举 64 个状态对：`canTransition` 与 `getNextStates` 完全一致，非法对全部抛 `INVALID_INSPECTION_TRANSITION` |
| P2 合格后不可改判 | ✅ 通过 | 含「任意起点 × 400 次 × ≤25 步」与「自 FAILED 起点 × 400 次 × ≤50 步」随机游走 |
| P2b 合格必经检验 | ✅ 通过 | 自 PENDING 出发 400 次随机游走，未出现「绕过检验直接判合格」 |
| P3 终态吸收 | ✅ 通过 | COMPLETED 无非自身出边，随机游走到达即终止 |
| P4 不合格不可静默放行 | ✅ 通过 | FAILED 之后回到 PASSED 的路径均经 IN_MRB_REVIEW |
| P5 无死锁 + 可达性 | ✅ 通过 | 8 态自 PENDING 全部可达；非终态均有出边 |
| 变异自检（注入 7 处缺陷） | ✅ 全部被对应护栏拦下 | 见下表 |

**撞出的反例**：**0 处**。针对上述 5 条性质，现有 8 态矩阵**未发现违反项**。

为防止「全绿」是空转，本轮追加**变异自检** —— 故意注入 7 处缺陷，逐条验证护栏「必红」：

| # | 注入缺陷 | 应被哪条护栏拦下 | 实测 |
|:--|:---|:---|:---|
| 1 | `PENDING → PASSED`（跳过检验直接判合格） | P2b 合格必经检验 | ✅ 拦下 |
| 2 | `PASSED → INSPECTING`（合格后回退重检） | P2 合格后不可改判 | ✅ 拦下 |
| 3 | `COMPLETED → INSPECTING`（终态流出） | P3 终态吸收 | ✅ 拦下 |
| 4 | `FAILED → PASSED`（不合格直接改判合格） | P4 不合格不可静默放行 | ✅ 拦下 |
| 5 | `DRAFT` 出边全删（单据卡死） | P5 无死锁 | ✅ 拦下 |
| 6 | `FAILED → IN_MRB_REVIEW` 删除（MRB 不可达） | P5 可达性 | ✅ 拦下 |
| 7 | `PENDING → COMPLETED` 旁路（接口与矩阵不一致） | P1 接口自洽 | ✅ 拦下 |

**fast-check 反例格式演示**（临时脚本注入缺陷 1 后实跑，跑完即删、未留痕）：

```
Error: Property failed after 5 tests
{ seed: -2050729279, path: "4:4:2", endOnFailure: true }
Counterexample: [["PASSED","PENDING"]]
Shrunk 2 time(s)
```

即：5 次运行即命中；最小化输入为意图序列 `["PASSED","PENDING"]`（起点 PENDING 直接走注入边到 PASSED）；种子 `-2050729279`，可用 `FC_SEED=-2050729279` 复现。

**诊断清单实测输出**：

```
PASSED 的入边: INSPECTING, IN_MRB_REVIEW, RE_INSPECTING（无非检验入口态来源）
FAILED 的入边: INSPECTING, IN_MRB_REVIEW, RE_INSPECTING（无非检验入口态来源）
矩阵非自反边 17 条；基线显式覆盖 14 条
矩阵允许但基线未显式覆盖: INSPECTING -> FAILED ; RE_INSPECTING -> PASSED ; RE_INSPECTING -> FAILED
```

**覆盖不到的部分（明确边界）**：

1. **跨环节链路门禁** —— 「上游环节未合格 ⇒ 下游不得开始」属 **docs/48** 的范围；本轮只覆盖**单张检验单**的状态机，**不覆盖** IQC → IPQC → OQC 之间的传递门禁。
2. **应用层用例是否真的走状态机** —— `FinalizeInspectionStatusUseCase` / `CreateReinspectionUseCase` / `TriggerMrbReviewUseCase` 是否**确实调用**状态机（而非绕过它直接写库），不在本轮范围；状态机绿 ≠ 链路绿。
3. **同态幂等的业务口径** —— `canTransition(s, s)` 对**终态** `COMPLETED` 亦返回 `true`（源码设计如此，基线亦按此锁定）；若业务要求「终态完全不可再次提交」，需单独立口径。
4. **数据层一致性** —— MRB `defect_qty` vs 源单 `fail_qty` 属白盒 SQL 断言（TBD-05），本轮未做。
5. **前端表现** —— Banner / 带出值 / 清空回滚属 CDP 探针与 docs/47 AC-01~AC-13 的范围。

> **未纳入本轮但需知晓**：仓库既有门禁 `pnpm audit:code` 当前为**红灯**（`any` 145 处 / 预算 138，明细全部落在 `apps/api/src/controllers/*` 等既有文件）。本轮新增文件**未引入任何 `any` / `@ts-ignore`**，该失败与本轮改动无关，需另行排期。

## 8. MRB 不合格数量白盒对账断言（P1 · ✅ 已落地）

> **设计前提**：**不假设库是静止的** —— 并行会话 / 探针 / 人工操作都可能改库。因此本节断言只做**可重复的只读对账**：
> 任何时刻跑都得到该时刻的真实结论，不依赖「上次跑完之后没人动过」，也不写库、不做清理。

### 8.1 定位与分工

| 维度 | `mrb-defect-qty-parity.test.ts`（并行交付，黑盒） | `mrb-defect-qty-db-parity.test.ts`（本次，白盒） |
|:---|:---|:---|
| 视角 | **写路径**：HTTP 建单 → 录值 → 终判，验「新写入是否写对」 | **存量全库**：一条写语句都没有，直接对账库里**已有全部行** |
| 能抓到 | 本次新写入的时序缺陷（建单在前、填写值在后） | 历史脏数据、绕过写路径的裸 SQL 造数、关联悬挂 |
| 副作用 | 造数 + 自动清理 | **只读、可重复跑、无清理逻辑** |
| 关系 | 互补，两者都保留 | 同上 |

### 8.2 断言规则（5 条，口径固化）

| 规则 | 内容 | 判据 |
|:---|:---|:---|
| **R1** | 源单可解析（无孤儿行） | 每条 MRB 单 / 不合格台账条目都必须能命中源检验单 |
| **R2** | MRB 不合格数量 = 源单不合格数量 | `mrb_reviews.defect_qty = inspection_orders.fail_qty`（按 `source_order_no = order_no`） |
| **R3** | 台账不合格数量 = 源单不合格数量 | `pending_mrb_items.defect_qty = 源检验单.fail_qty`（按 `source_order_id = id`） |
| **R4** | 台账 ↔ MRB 同源数量一致 | 台账已关联 MRB 时两处数量必须相等，且关联指向的 MRB 单必须存在 |
| **R5** | 数量非负且非 NULL | 上述全部数量值 >= 0 且非 NULL |

**豁免口径（有据，非放水）**：源单 `fail_qty` 为 `0` / `NULL` 视为「检验员未填写」，按 docs/21 §14 口径③ **保留既有值、不回退成 0** ⇒ 该情形豁免 R2 / R3 的严格相等，但其数量**仍必须非 NULL**；豁免条数在输出中单独计数公示，便于发现豁免被滥用。

**实现口径**：
- 连接走 `@letian/infrastructure` 的 `createDatabaseConnection()`（Kysely 查询构造器）；`kysely` / `pg` 在 `apps/api` 下不可直接解析（pnpm 严格依赖），因此**不做未声明导入**、**零新增依赖**。
- `pending_mrb_items.mrb_review_id` 是 **varchar**，而 `mrb_reviews.id` 是 **uuid** 且无外键 ⇒ R4 在 JS 侧按字符串比对，不在 SQL 里做强转（避免类型强转掩盖数据模型问题，见 E2）。
- 库不可用时**显式失败**（不静默跳过），并在报错里提示 `pnpm db:local:start`。

### 8.3 豁免阈值与防滥用（CI 可收紧）

豁免一旦泛滥，R2 / R3 就退化成空转 —— 因此豁免必须**可计数、可核查、可设限**：

| 机制 | 默认 | 行为 |
|:---|:---|:---|
| `MRB_PARITY_EXEMPT_WARN` | `0` | 豁免数 **> 该值** → 打印 ⚠ 告警（**不失败**），并列出豁免明细供人工核查 |
| `MRB_PARITY_EXEMPT_MAX` | 未设置 | 显式设置后成为**硬上限**：豁免数 > 该值 → **失败（退出码 1）**，供 CI 收紧 |
| **空转保护** | 恒生效 | 某条规则的豁免数 == 检查数（100% 被豁免）→ 该规则已无约束力，**直接判失败**（不允许「全绿」建立在「什么都没检查」之上） |

- 豁免明细**必须可见**：每条被豁免的行都打印 `[规则] 单据号：源单 fail_qty 值 ⇒ 保留的侧值`，不允许静默豁免。
- 环境变量取值非法（非「非负整数」）时**立即报错**，不静默回落默认值。
- 建议 CI 收紧写法：`MRB_PARITY_EXEMPT_MAX=0 pnpm verify:mrb-parity`（当前 0 豁免，可直接启用）。

**CI 落地**（已写入 `.github/workflows/ci.yml` 的 `Run Automated Tests` 步骤）：

```yaml
        env:
          NODE_ENV: test
          DATABASE_URL: postgresql://letian_user:letian_secure_pass_2026@localhost:5432/letian_qms_db?schema=public
          # MRB 不合格数量白盒对账（docs/49 §8.3）：豁免零容忍 —— 当前 0 豁免故设 0；
          # 一旦出现豁免，先判定是数据问题还是口径问题，再决定是否放宽该阈值。
          MRB_PARITY_EXEMPT_MAX: "0"
```

**重要语义澄清（避免误判 CI 绿灯）**：CI 的 PostgreSQL 是**全新迁移库、无业务数据**，因此该门禁在 CI 上是
**「0 项检查」的空转通过** —— 断言会在日志里显式打出 ⚠ 提示（`库内无可对账行 … 属「空转通过」，不可据此判断数据质量`）。
真正具备约束力的运行发生在**有数据的库**（本地 / 预发 / 生产巡检）。
若要让 CI 也具备实际约束力，需在迁移后追加 `pnpm db:seed`（会改变其它用例的数据前提，须单独评估，本方案不擅自启用）。

## 11. 契约一致性探针入仓与 CI 门禁落地（TBD-12 · ✅ 已落地）

### 11.1 定位与设计原则

随着 `openapi.yaml` 成为多会话协作的共同枢纽，契约登记一旦无人对账，极易迅速退化成「纸面契约」。
本探针（`scripts/testing/openapi-conformance.cjs`）定位为**只读、轻量、高可信度**的自动化契约门禁：

1. **零新增 npm 依赖**：复用 pnpm 虚拟存储中既有的 `yaml@2.9.1` 与 `ajv@8.20.0`，无需给 root 或 apps/api 安装新包。
2. **纯只读幂等对账**：只跑 GET 读操作，绝不向数据库写入任何脏数据，对真实库与测试库均零副作用。
3. **阶梯式六层断言**：
   - ① **规格自检**（离线）：44 个 schema 语法与类型解析、路径参数匹配度、根级 security 登记核实。
   - ② **路由存在性**（在线）：核实 spec 中声明的 19 个 GET 路由在 Fastify 实际路由表中均已注册。
   - ③ **响应体逐字段校验**（在线）：调用真实接口，拿返回体与 200 schema 做 Ajv 递归校验（支持已知漂移豁免表）。
   - ④ **核心焦点逐单回归**（在线）：对全库全部检验单（57 单 / 210 指标项 / 4 组炉批号）逐一跑深度校验。
   - ⑤ **离线可证伪性自检**（离线）：用硬编码的冷冻快照运行反例变异测试，强制验证缺字段、错类型、超枚举必能被探针判红（探针有牙）。
   - ⑥ **空转保护**：断言总数必须 > 0；CI 环境允许数据例数按 `OPENAPI_CONFORMANCE_MIN_CASES=0` 空转，但若有数据则必须达标。
4. **自拉起与清理闭环**：探针检测到本地/CI 无运行中服务时，自动通过 `process.execPath + tsxCli` 拉起 Fastify API 实例；脚本退出时（无论成功还是异常）通过 `finally` 强制安全销毁子进程。

### 11.3 `additionalProperties: false` 收紧评估（顺手收紧结果）

针对是否顺手将全部 schema 收紧为 `additionalProperties: false` 的技术评估：
