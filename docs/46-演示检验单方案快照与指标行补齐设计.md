## 1. 现象与复现

用户路径：以 `陈静`（`IQC_INSPECTOR`）登录 → 【来料检验(IQC)】台账 → 命中新增测试行 `INS-20260921-0001`（批次 `TEST2609-001`）→ 行内【详情】进入**检视与评定**页。

实测（2026-09-23，真实库 + 真实 HTTP `:3100` + 真实界面 `:5200`）：

| # | 观测点 | 实测结果 | 结论 |
|:---:|:---|:---|:---|
| 1 | 页面横幅 | 标题「**检验单方案快照加载失败**」，副文案「服务端返回的检验单详情不符合契约，已阻止按错误数据回看判定依据」 | 读侧**主动拒读**，不是网络失败 |
| 2 | 指标条 | 「检验项总数 **0** 项」 | 待检指标清单为空 |
| 3 | 三个指标分区 | 全部为空，空态为「待检指标清单未就绪（方案未命中 / 加载失败 / 当前账号无数据权限）…」 | 分区拿不到任何待检行 |
| 4 | `GET /api/v1/inspections/{id}` | HTTP 200 正常回包，但响应体里 `planSnapshot = {}`、`items = []`（服务端读侧**不做响应契约校验**，原样返回库中行） | **数据本身残缺**：缺陷在库里，暴露在客户端 |
| 5 | 库中该行 | `plan_snapshot = '{}'::jsonb`、`items = '[]'::jsonb` | 即两列的**列默认值** |

> **区分两个"没数据"**：本现象不是「权限拦截」也不是「方案没配」（docs/42 的两类），而是**这一张工单自身的判定依据从未被写入**。同一台账里种子行（如 `INS-20231013-0001`）打开即正常，仅新增测试行异常 —— 这正是"新增的测试数据"这一限定的由来。

## 2. 根因

### 2.1 D1（数据·主因）：裸 SQL 造数绕开建单链路，快照两列落到列默认值

新增测试数据由一段**裸 SQL** 写入（`scripts/logs/testdata-TEST2609.sql`，该目录已 gitignore，属临时造数脚本）：23 行 `INSERT INTO inspection_orders (...)` 的**列清单里没有 `plan_snapshot` 与 `items`**，于是 PostgreSQL 用列默认值补全：

| 列 | 定义处 | 默认值 | 后果 |
|:---|:---|:---|:---|
| `plan_snapshot` | `packages/infrastructure/src/migrations/002_align_schema_to_contracts.ts:77` | `'{}'::jsonb` | 快照缺 `planId / planCode / planName / versionId / versionNo / items` |
| `items` | 同文件 `:78` | `'[]'::jsonb` | 待检指标行 0 项 |

**关键区分**：这两列的默认值是**迁移期的兼容兜底**（让既有行在 `ADD COLUMN ... NOT NULL` 时能补全），**不是**建单语义。正常建单链路（`create-inspection-order.ts`）会把匹配到的方案版本**全量固化**进快照（docs/17 §7.3「快照即证据」）。任何绕过链路的写入（裸 SQL 造数、外部批量导入）都会留下一张"**能查得到、但没有判定依据**"的检验单 —— 这是本次缺陷的**唯一真因**。

### 2.2 D2（读侧·放大器）：严格契约校验把"空快照"升级为"整单不可读"

快照残缺不会被静默渲染成空白：**前端读侧**在取值时用 `InspectionOrderSchema`（`@letian/contracts`，与后端共用同一份定义）严格校验，失败即 fail-closed，再由三处渲染点把它呈现给用户 —— 因此"库里数据残缺"在界面上表现为**显式报错**而不是空白页：

| 层 | 位置 | 行为 |
|:---|:---|:---|
| 前端回看取值 | `apps/web/src/lib/planMatch.ts:560` | `InspectionOrderSchema.safeParse(payload)` 失败 → `throw new ApiError(502, '服务端返回的检验单详情不符合契约，已阻止按错误数据回看判定依据', 'invalid-inspection-order-payload')`（`:564`） |
| 横幅渲染 | `apps/web/src/components/common/PlanMatchBanner.tsx:177` | 落到「检验单方案快照加载失败」分支（`data-status="error"`、`data-source="SNAPSHOT"`） |
| 分区空态 | `apps/web/src/lib/planMatch.ts:611` | 返回「待检指标清单未就绪…」——**不说**「无需录入」（该文案只属于"方案已就绪且本分区确实无指标"） |

这个 fail-closed 行为是**正确的**（宁可显式报错，也不按结构不明的数据渲染判定依据 —— 否则会出现"拿当前生效方案顶替快照"的错判）。因此**修数据、不放松契约**是唯一正确路线（§3 D2）。

### 2.3 D3（种子路径·潜在）：构造器只支持数值型指标

排查中发现同源隐患：把"方案指标项 → 快照 / 实测项"的映射**曾写在种子 runner 内联逻辑里**，且对**定性指标**直接抛 `SEED_ORDER_ITEM_REQUIRES_NUMERIC` —— 即"方案含定性指标"时种子灌库会失败。若不收敛，本轮修复工具与种子会各写一份映射，迟早出现"种子库合规、补齐库不合规"的口径漂移（§3 D3）。

### 2.4 D4（造数口径·伴生）：该批演示行的物料与方案无对应关系

同一段 SQL 里，`plan_id / plan_version_id` 取自 `SELECT ... FROM inspection_orders WHERE order_type='IQC' LIMIT 1`（**一份 IQC 方案套给全部 23 行、跨 6 种检验类型**），物料则按 `row_number() OVER (ORDER BY material_code)` **全表轮询**取值 —— 两者互不相关。这与真实建单链路（按"物料编码 + 检验类型 + 物料分类"两级匹配，docs/17 §7.3）完全不同口径，因此"补齐快照"不能简单照抄这两列，必须重走匹配（§3 D1）。

> **附注（数量口径，2026-09-23 第八轮）**：同一脚本写入的还有同批 **MRB 评审单与不合格台账**。此前脚本把 MRB 的
> 不合格数量写成 `3 + r.rn`、把台账分母写成报检总数，与 `docs/21` §13.2 的「不合格数量 = 源检验单 `fail_qty`」
> 及 `docs/03` §2.3 的「分母取抽样数」两条口径都冲突。脚本已改为从源单取数（MRB 段 `r.fail_qty`、
> 台账段 `o.fail_qty` / `o.sample_qty`），库内存量 12 条演示 MRB 与 12 条台账行也已按该口径订正，明细见
> `docs/21` §14.7。**造数脚本本身同理适用于 §2.1 的教训：写入方必须与链路同口径。**

## 3. 口径决策（本轮定稿）

| 编号 | 决策 | 理由 |
|:---|:---|:---|
| **D1** | **快照与指标行只能由建单链路固化**；绕过链路的写入视为违规数据。补齐时方案一律按 `findActivePlan(物料编码, 检验类型, 物料分类)` 重解析 —— 与建单链路**同一套两级匹配**（物料专属 → 分类通用兜底），**不做任何"猜一个方案"的兜底** | 保证补出来的工单与"今天真的建一张单"完全一致；照抄库里那对与被检物料无关的 `plan_id` 只会把错误固化下来 |
| **D2** | **读侧契约不放松**：保留 `InspectionOrderSchema` 的严格校验与 fail-closed 文案，改由**修数据**解决；工具写完库后**重新读一遍**再判定结论 | 空快照若被"容错渲染"，页面就会退化成用当前方案重算历史结论，直接违反 §7.3「快照即证据」 |
| **D3** | `方案指标项 → 快照指标 / 工单实测项` 的映射**只保留一份实现**：`packages/infrastructure/src/seeds/order-builders.ts`，种子灌库与修复工具共用 | 一处定义、两处复用，杜绝口径漂移（同 docs/44 的单点收敛做法） |
| **D4** | **定性 / 文本型指标不编造实测值**：方案给出 `acceptableValues` 时取清单首项（不合格取清单外文本）；**清单缺失即保持 `PENDING`**，交人工判定 | 演示数据可以"假"，但不可以"假得违反判标规则" |
| **D5** | **演示行的物料归位**仅对**指定批次前缀**（默认 `TEST2609-`）开放：匹配不到方案时，按其检验类型下 ACTIVE 方案的**覆盖范围**选一份"反查能命中"的方案，并把物料**归位**到该方案覆盖的物料（名称 / 规格型号 / 计量单位随物料主数据同步）。**非演示行匹配不到方案只报告、不擅改** | 该批演示行的物料本就是随机落下（§2.4），归位是**纠正造数错误**而非篡改业务数据；非演示行属于真实业务数据，擅自改物料是越界 |
| **D6** | `TEST2609-` 批次前缀**保留给本工具链**：`seeds/data.ts` 不得占用该前缀的物料 / 批次，避免"造数脚本与种子脚本互相污染" | 一个前缀只归一个来源，出问题时能一眼定位 |
| **D7** | 违规判据 = **①** 工单本体不通过 `InspectionOrderSchema`，**或 ②** 快照含指标项但 `items` 为空（有方案无待检行） | 两条都直指"检视必然空白"；`②` 覆盖"快照写全了、指标行漏了"的半残形态 |

## 5. 工具用法

```bash
# ① 只读体检：有违规行即以退出码 1 失败（可直接进 CI / 巡检）
pnpm db:demo:check

# ② 试算（不写库）：先看清要改哪几行、改成什么
pnpm db:demo:repair -- --dry-run

# ③ 修复：按建单口径补齐快照与指标行，写库后自动复查
pnpm db:demo:repair

# ④ 允许"物料归位"的演示批次前缀（逗号分隔，默认 TEST2609-）
pnpm db:demo:repair -- --demo-batch=TEST2609-,OTHER-
```

退出码约定：

| 退出码 | 含义 |
|:---:|:---|
| `0` | 体检全部合规；或修复后复查无残留违规 |
| `1` | 仍存在违规行 / 存在无法自动处理的行（结论本身就是失败信号） |
| `2` | 用法 / IO 错误（如连不上库） |

**注意**：`pnpm db:seed` 会**重建整库演示数据**（含清掉本批测试行），需要保留本批数据时**不要**执行。
