## 1. 界面定位

一句话：**检验录入页是质检员"干活"的地方。**

- 检验单**列表页**回答"今天还有哪些单子要检"；检验**录入页**回答"这一单具体怎么检、结果填哪儿"。
- 两者是一进一出关系：列表点【检验】进入录入页，提交后回到列表并回写状态。
- 录入页不产生新的业务概念，它只做一件事：**把标准（质检方案）落到实物上，并留下可追溯的证据**。

### 1.1 角色与动作

| 角色 | 在录入页的动作 |
| :--- | :--- |
| 质检员 | 逐项录入实测值、保存草稿（检验到一半可暂存）、一键提交检验结果 |
| 质检主管 | 查看录入结果；在不合格待审核池中逐条核实并【发起评审】 |
| 质量 / 技术 / 生产 | 在 MRB 评审流程中会签决策（不在本页操作，但结论会回写本页所属工单状态） |

> 只读回看：已检工单从列表【详情】（或点【已合格 / 不合格】的行）进入**同一张表单**，
> 但判定依据取**本单方案快照**、实测值与单项判定取工单落库值，编辑锁死且不显示提交按钮（§7.8）。

## 2. 界面职责（四件事逐条拆解）

| # | 需求表述 | 大白话 | 系统行为 | 代码落点 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 根据物料自动匹配质检方案，显示需要检验的指标清单 | 系统自己去翻"这个物料该按哪份标准检"，把该检的项目列出来 | 按 `物料编码 + 检验类型` 匹配**已启用 (ACTIVE)** 的方案版本，把方案内的指标项（外观 / 尺寸 / 机械性能 / 化学成分 / 膜厚 / 硬度）渲染为待检清单 | `GET /api/v1/plans/match`；`packages/infrastructure/src/repositories/inspection-plan-repository.ts` → `findActivePlan` |
| 2 | 逐项填写实测值，系统按标准值自动判定合格/不合格 | 每项填一个实测数，系统拿标准值/上下限比一下，合格绿、不合格红 | 指标项自带 `nominalValue / upperTolerance / lowerTolerance / standardText`；客户端调领域服务实时判标并高亮，服务端提交时用**同一份算法复判**（防篡改） | 客户端：`apps/web/src/lib/planMatch.ts`（`judgeIndicatorRow` → `packages/domain/src/services/tolerance-evaluator.ts`）；服务端复判：`packages/domain/src/models/inspection-order.ts`；判定用例：`packages/domain/src/__tests__/evaluate-inspection-item.test.ts` |
| 3 | 检验结果一键提交，支持保存草稿 | 检到一半先存着，下午接着填；检完一次性提交 | 草稿态 `DRAFT`；提交后进入 `COMPLETED` 并落终判 `PASSED / FAILED / CONCESSION` | `POST /api/v1/inspections/{id}/submit-measurements`（录入与判定）、`POST /api/v1/inspections/{id}/status`（状态与终判） |
| 4 | 提交后自动更新出货检验列表状态，不合格的触发评审流程 | 提交完列表里的状态自己就变了；不合格的自动进池子等评审 | ① 回写 `inspection_orders.status / judgment`，列表刷新即反映；② 不合格条目自动汇聚到**不合格待审核池**，由质检主管逐条【发起评审】 | `apps/web/src/pages/mrb/PendingMRBPoolPage.tsx`；`POST /api/v1/mrb/pending-pool/initiate` |

### 2.1 判定规则要点（与领域层保持一致）

- **定量项**：按 [标称值 + 上下公差] 形成的**闭区间**判定，`PASSED / FAILED`；带 `1e-9` 浮点容差保护（不错杀浮点误差，也不吞真实超差）。
- **定性项（TEXT / 定性描述）**：必须有判定标准语才判定；缺标准语一律 `PENDING`，**严禁无标准放行**。
- **免检 / 不解检**：特定工序经质量部经理特批可标记 `isExempt`，生成工单档案与放行标识，但不计入合格率的分母。
- **整单终判**：任一项 `FAILED` → 整单 `FAILED`（详见 `inspection-order.ts` 的终判逻辑）。

### 2.2 责任边界（重要口径）

需求原文写作"不合格的触发评审流程"，实际定稿为**两阶段机制**：不合格只**自动入池**，评审必须由人工**逐条发起**（见 PRD §3.6 与《需求澄清记录》Q3）。
因此本页面的责任边界到"入池"为止，**不自动发起评审**。

检验录入页是**一套交互、四个入口**，由 `apps/web/src/pages/inspections/index.tsx` 按 `initialStage` 分派：

## 7. 质检方案自动匹配口径（契约级定稿）

### 7.1 问题：匹配职责悬空

需求要求"根据物料**自动**匹配质检方案"，但改造前代码是三处口径互相打架：

| 位置 | 改造前现状 | 问题 |
| :--- | :--- | :--- |
| 建单契约 `CreateInspectionOrderRequestSchema` | `planVersionId` 为**必填** UUID | 调用方必须先知道方案版本才能建单，"自动匹配"无从发生 |
| 建单控制器 `inspections.controller.ts` | 拒绝空值与未知版本，注释写死"**禁止静默降级为自动匹配**" | 保护了"不静默用错方案"的正确原则，但把匹配责任完全推给了前端 |
| 建单用例 `create-inspection-order.ts` | 保留了一条 `findActivePlan` 自动匹配分支 | **不可达死代码**；且 `planId` 写入的是字符串 `'AUTO_MATCHED'`，而 `inspection_orders.plan_id` 是 `UUID NOT NULL` → 一旦走到必然报 UUID 解析错误 |

结论：**匹配能力早已存在，但没有任何一条路径能安全抵达它。**

### 7.2 定稿方案：两步显式匹配

采用"**先预览、后建单**"两步法，匹配规则只有一份真相，每个入口都显式可解释：

1. **第一步（读）**：新增只读匹配接口 `GET /api/v1/plans/match?materialCode=&inspectionType=`。
   录入页打开（或选定物料）时调用，拿到命中方案的**版本 ID + 指标清单**，直接渲染待检项。未命中返回 404，页面提示"未匹配到质检方案，请联系质量工程师配置方案"。
2. **第二步（写）**：建单 `POST /api/v1/inspections` 的 `planVersionId` 由**必填改为可选**：
   - **显式传入** → 必须真实存在，否则 404（保持原行为，"禁止静默降级"原则不变）；
   - **未传入** → 服务端按同一规则自动匹配；匹配失败返回 **400 `inspection-plan-not-found`**（明确报错，绝不猜、绝不静默用错方案）。

职责划分：前端负责"给人看"，服务端负责"落库为准"；两端调用**同一个仓储方法**，不存在两套匹配规则。

### 7.3 匹配规则（唯一真相）

采用**两级兜底匹配**：先找料号专属方案，找不到再下沉到该物料所属存货分类的通用方案；两级都不命中才算匹配失败。

| 级 | 命中条件 | 定位 |
| :--- | :--- | :--- |
| 第一级（物料专属） | `material_code = materialCode` 且 `inspection_stage = inspectionType` | 精度最高，命中即用 |
| 第二级（分类通用兜底） | `material_code = ''`（空串即"全分类通用方案"）且 `category_code = 该物料所属存货分类` 且 `inspection_stage = inspectionType` | 新料号首次送检、还没建专属方案时不至于"检不了" |

两级共用的前置条件与口径：

| 项 | 规则 |
| :--- | :--- |
| 输入 | `materialCode`（物料编码，精确匹配）+ `inspectionType`（`IQC` / `IPQC_CT` / `IPQC_RL` / `IPQC_FN` / `OQC_SF` / `OQC_SH`，以及委外七分类 `OQC_HEAT` / `OQC_BLACK` / `OQC_ZINC` / `OQC_NICKEL` / `OQC_PHOSPH` / `OQC_DACRO` / `OQC_MACH`） |
| 版本状态 | 只认 `version_status = 'ACTIVE'`，草案 (DRAFT) 与停用 (INACTIVE) 版本绝不参与匹配 |
| 生效周期 | 版本级 `effectiveStartDate / effectiveEndDate`（复用 `sampling_config` JSONB，未新增列）；不在周期内视为失效，继续往下一级兜底 |
| 多命中处理 | 按 `created_at DESC` 取最新一行（同一物料（或同一分类）+ 同一检验类型，业务上只应存在一份生效方案） |
| 绑定结果 | 检验单快照 `planSnapshot`（`planId / planCode / planName / versionId / versionNo / items`）全量固化，**快照即证据**，方案后续改版不影响已建工单 |
| 命中来源回填 | 只读匹配接口响应 `matchSource`：`MATERIAL`（物料专属）/ `MATERIAL_CATEGORY`（分类通用兜底） |
| 匹配来源留痕 | 建单审计 `planMatchSource`：`EXPLICIT`（调用方显式指定版本）/ `AUTO_MATERIAL`（服务端按物料自动匹配）/ `AUTO_MATERIAL_CATEGORY`（服务端按分类兜底匹配） |
| 唯一实现 | `packages/infrastructure/src/repositories/inspection-plan-repository.ts` → `findActivePlan(materialCode, inspectionType, materialCategory?)`，只读匹配接口与建单自动匹配**共用这一个方法** |

### 7.4 异常与错误码

| 场景 | HTTP | 错误码 | 提示文案 |
| :--- | :--- | :--- | :--- |
| 显式传入的 `planVersionId` 不存在 | 404 | `resource-not-found` | 质检方案版本不存在 |
| 匹配接口 `GET /api/v1/plans/match` 两级匹配均未命中 | 404 | `inspection-plan-not-found` | 未找到适用于物料 [X]、检验类型 [Y] 的已启用质检方案 |
| 匹配接口 `GET /api/v1/plans/match` 请求者物料维度越权 | 403 | `pbac-permission-denied` | 三维 PBAC 安全拦截：无权操作 [匹配质检方案]（**方案域只判物料分类 + 物料编码**，供应商维度不参与判定，见 `docs/42` §3；录入页横幅走「无该物料的数据权限」分支，**不引导**去配置方案，分区空态也不得显示「无需录入」） |
| 未传 `planVersionId` 且服务端两级匹配均未命中 | 400 | `inspection-plan-not-found` | 未找到适用于物料 [X]、检验类型 [Y] 的已启用质检方案 |
| 匹配到方案，但该方案无任何 ACTIVE 版本 | 400 | `inspection-plan-not-active` | 质检方案当前无已启用的有效版本 |
| 匹配到的版本指标项为空 | 400 | `inspection-plan-not-found` | 方案版本不包含任何指标项，无法生成检验项 |

**为什么升版不做角色门禁**：`…/status`（审批 / 停用）改变的是**方案的生效状态**，属质量主管职责，故按角色门禁（TBD-10）；升版只产出一个 **`DRAFT` 草稿**，不改变生效状态，与「新建方案」`POST /plans` 同级，因此只做 PBAC 物料权限校验（与 `POST /plans` 完全一致），避免出现「能建整个方案、却不能给方案升个草稿」的口径裂缝。

**为什么新草稿不继承生效周期**：升版语义是「以当前版本为模板」，但生效周期是**日期绑定**的 —— 若照抄，旧版本周期已过期时新草稿会「出生即过期」（审批后仍不参与 `GET /plans/match`），比「没有周期」更糟。故新草稿默认**长期有效**；需要限定时由调用方显式传 `effectiveStartDate` / `effectiveEndDate`。

**为什么版本号也要服务端取号（与 TBD-11 同口径）**：`plan_code` 已定稿为「省略由服务端取号」（TBD-11），版本号若让前端自造（改造前的 `handleCopy` 就是 `V1.0` 硬编码 + `{编码}-C{时间戳}` 伪编码），既可能撞号也会与库中既有 `v2.4` / `V1.0` 形态分叉。故 `versionNo` 同样**可省略**：省略即按领域规则在服务端升位，显式传入按原值使用（与 `plan_code` 完全对称）。

**顺带修掉的相邻缺陷（e2e 取数不确定 → 偶发红灯）**：`apps/api/test/integration/e2e.test.ts` 有 3 处「取任一 ACTIVE 方案、拿它的 `material_code` / `plan_version_id` 去建单」的查询（`§2.1.0` 出货单号取号、`§2.1.0c` 出货 008 字段写路径、`§2.1.0b` 来料检验 006 字段写路径）都写作 `selectFrom('inspectionPlans').where('versionStatus','=','ACTIVE').where('inspectionStage','=','IQC' | 'OQC_SH').executeTakeFirst()`，**既没有 `ORDER BY`、也没有排除分类通用方案**：同一次测试运行里自建的分类通用方案（`material_code = ''`）一旦排在堆序前面，建单就会 400 `materialCode: String must contain at least 1 character(s)`。Postgres 无 `ORDER BY` 时的行返回顺序随物理堆序变化，故这是**偶发红灯**（同一份代码在本次验证中一次失败、一次通过）。修法：连同 `§2` 开头「挑一个带 `NUMERIC` 指标项的方案」那一处在内，**共 4 处**取数统一显式排除 `material_code = ''` 并补 `ORDER BY plan_code, version`，让用例只针对**物料专属**方案取数、且每次命中同一行。

**为什么【审批】必须打到草稿版本行（真机走查发现的缺陷，已修）**：升版后方案会**同时**存在 `ACTIVE`（旧版本）与 `DRAFT`（新草稿），而方案级状态仍是「已启用」。此时若沿用「生效版本」作审批目标（`effectiveVersion` 优先 `ACTIVE`），点【审批】只会对已生效的那一行做一次**幂等**启用 —— 接口 200、列表照常刷新、**界面毫无报错**，但新草稿永远批不下来。故 `approvalTargetVersion()` **优先草稿**、无草稿才回落生效版本（此时重复审批即幂等放行）。与此配套，【审批】的可见性由「方案级状态 = 待审批」放宽为「**存在待审批草稿**」：否则「已启用 + 新草稿」这一升版后的常态在列表上根本没有审批入口（走查中的实际表现是「升版后只能先【停用】才能【审批】」，中间方案一度掉出自动匹配）。两条口径都由 `verify-plan-version-actions.mjs` 钉死 —— 这类缺陷类型检查与契约校验都发现不了。

**TBD-09 评估（2026-09-21，结论：本轮暂不实施）**

- **收益**：同义写法可分组、可标注首选写法，录入下拉能分区展示；为「这个值为什么可接受」留备注位。属**录入体验与可读性**改善，不影响判定正确性（判定只做「清单成员包含」判断）。
- **不做的原因（成本与风险）**：
  1. 属**契约破坏性变更**：`acceptableValues: string[]` → `{ value, label?, preferred? }[]`，波及 9 个文件约 56 处引用（契约 / 领域层判定与单测 / 前端数据层 / 方案设计弹窗 / 录入表单 / `verify-plan-snapshot.mjs` / e2e）。
  2. **历史数据不可改写**：方案指标项落在 `inspection_plans.items`，工单快照落在 `inspection_orders.plan_snapshot`。按本项目「快照即证据」原则，历史快照不得回填改写，因此读侧必须**长期兼容两种形态**（需要一层规范化函数作为唯一口径 `normalizeAcceptableValues()`），否则历史工单回看会判错。
  3. 当前无阻塞性需求：原始需求「根据物料自动匹配质检方案，显示需要检验的指标清单」不受影响，TBD-06 已让可接受值可结构化配置。
- **后续若实施，建议路径**：① 契约升级为 `z.union([z.string(), z.object({ value, label?, preferred? })])` 并同步 OpenAPI 描述；② 领域层与前端数据层共用同一个 `normalizeAcceptableValues()`（`string` → `{ value }`），判定与候选值只读规范化结果；③ 方案设计侧「可接受值」列升级为可增删小行（值 / 同义说明 / 首选标记）；④ 先补契约、领域层与 `verify-plan-snapshot.mjs` 的守门用例，再动 UI。

### 7.7 前端接线实现（架构与数据流）

```text
检验单列表行 (含 materialCode)
        │ 点击【检验/录入】
        ▼
录入表单 (IQC / OQC / 委外 / IPQC 弹窗)
        │ ① useMatchedPlan(materialCode, inspectionType)
        ▼
GET /api/v1/plans/match ──► MatchedInspectionPlanSchema 校验
        │  命中 → plan.items 经 splitPlanItems 分到三个分区
        │        → toPlanIndicatorRow 生成待检行（实测值留空）
        │  未命中 → 404 inspection-plan-not-found → PlanMatchBanner 引导配置方案（不渲染任何演示行）
        ▼
质检员逐项录入实测值
        │ ② judgeIndicatorRow(row) → evaluateInspectionItem(领域层) → PASSED / FAILED / PENDING / EXEMPT
        │    summarizeJudgements 汇总（合格率分母剔除免检项，分母为 0 显示"暂无有效参检项"，不伪造 100%）
        ▼
提交：planVersionId 原样回传 + 实测项明细 → 服务端按同一算法复判落库
```

**指标行模型**（`PlanIndicatorRow`，四个表单共用）：

| 字段 | 来源 | 说明 |
| :--- | :--- | :--- |
| `seq` | 方案指标项 / 工单实测项 | 分区内排序键（方案 `seq` 与工单 `seq` 同源，回看不乱序） |
| `itemCode` / `name` / `title` | 方案指标项 | `itemCode` 用于提交与炉批号溯源匹配；`title` 是界面主标题 |
| `standard` | `standardDisplayOf(planItem)` | 优先用方案 `standardText`；缺失时由 `nominalValue ± 公差` 回拼；页面内允许现场修订 |
| `actual` | 质检员录入 / 工单落库值 | 新建录入时为录入值；只读回看时为工单 `measuredVal`（无则 `measuredText`），只展示不改写 |
| `unit` / `isExempt` | 方案 + 质检员 | `isExempt` 默认 `false`（非强制项不做自动免检，避免静默把指标踢出合格率分母） |
| `planItem` | `PlanBasis`（方案指标项 / 工单实测项共有的判定基准） | 数值基准与判定规则的唯一读取处，保证前端预判与后端复判同口径 |
| `storedDecision` | 工单实测项的 `result` | **只读回看专用**：有值时 `judgeIndicatorRow` 直接返回它，不做前端重算（快照即证据） |

**数值基准优先级**（`buildEvaluatorInput`）：

1. 方案显式给出的 `nominalValue / upperTolerance / lowerTolerance`（种子与方案配置页写入的正常路径）；
2. 缺失时，从标准语解析数值区间（`0.37 ~ 0.44` / `0.05%~0.11%` / `32~38HRC` / `Φ5.00±0.02` / `≤0.030` / `≥650MPa`，数值与 `~` 之间允许夹一个百分号）反推：区间取中点，单侧上限按"中心值 +0 / 无界下差"处理，单侧下限反之；
3. 两条都推不出来 → 保持缺省，判定落在 `PENDING`（界面显示"待判定"），**绝不默认放行**。

> 说明：单侧公差（≤ / ≥）用 `Number.MAX_SAFE_INTEGER` 作为无界侧公差参与闭区间计算，
> 使该侧退化为不限制；QC 量程远小于该值，不损失有效精度。

### 7.8 只读回看数据流（TBD-04 定稿）

关键口径：**同一张表单，两种判定依据来源**。来源由"是不是在看已完成的工单"决定，不由页面自己猜。

```text
检验单列表行
        │
        ├─【检验 / 继续】新建或续录 ──────────────► MATCH 模式（§7.7 数据流）
        │
        └─【详情】/ 行状态已是「已合格 · 不合格」 ─► SNAPSHOT 模式
                                                        │ useMatchedPlan(code, type, { orderId, readOnly: true })
                                                        ▼
                                        GET /api/v1/inspections/{id} ──► InspectionOrderSchema 校验
                                                        │  工单自带：planSnapshot（方案编码 / 版本 / 指标基准）
                                                        │            items（实测值 + 单项判定 + 免检标记）
                                                        ▼
                                        toPlanIndicatorRowFromOrderItem → PlanIndicatorRow（storedDecision = items[].result）
                                                        │ splitIndicatorRows 分到三个分区
                                                        ▼
                                        只读渲染：标准值 / 实测值 / 单项判定全部取工单落库值
                                        （fieldset[disabled] 锁死编辑；不渲染提交按钮）
```

来源对照表（页面文案与判定依据必须一致，不得混淆）：

| 维度 | MATCH（新建 / 继续录入） | SNAPSHOT（只读回看） |
| :--- | :--- | :--- |
| 数据来源 | `GET /api/v1/plans/match`（当前生效方案） | `GET /api/v1/inspections/{id}`（本单方案快照 + 工单实测项） |
| 提示条标题 | 「已匹配质检方案」 | 「本单方案快照」 |
| 命中来源 `matchSource` | 有（物料专属 / 分类兜底） | **无**（当时怎么命中的不编造，恒为 `null`） |
| 单项判定怎么来 | 前端调领域层 `evaluateInspectionItem` 实时预判（提交后服务端复判为准） | 直接取工单 `items[].result`（`storedDecision`），**不重算** |
| 标准值 / 数值基准 | 方案指标项（允许现场修订后判标） | 工单快照（只读，不可修订） |
| 未命中 / 失败文案 | "未匹配到质检方案，请联系质量工程师配置并启用方案" | "未找到该检验单 / 快照加载失败，请刷新列表重试"（不误导去配置方案） |
| 方案改版影响 | 当场生效（尚未建单，本来就是按当前方案检） | **不影响**：已固化快照，回看结论与当时一致 |

为什么回看不能重算：工单的 `items` 是建单时由方案快照派生、并随录入更新的**唯一证据链**。
前端若按"当前标准"重算，会出现两类事故：

1. 方案改版（标准收紧）后用新标准审判历史单据，把当时合格的判成不合格；
2. 快照数据本身带瑕疵时（示例：mock 工单 `INS-20231012-0001` 的 DIA-001 把下偏差写成 `-0.02`），
   前端重算会得出与工单落库结论（PASSED）相反的结论，界面上"标准/实测/判定"三者互相矛盾。

> 对应回归守门：`apps/web/scripts/verify-plan-snapshot.mjs`（`pnpm --filter @letian/web test`）逐张 mock 工单断言
> "回看行判定 == 工单落库判定"，并把上面第 2 类样本钉死；`apps/api/test/integration/e2e.test.ts` 新增
> 「只读回看数据源」用例，保证接口侧 `GET /inspections/{id}` 自带判定基准 + 实测值 + 落库判定。

回看入口覆盖面（TBD-07 起）：来料检验（列表「详情」/ 已合格·不合格行）、出货检验（行 `isReadOnly`）、
委外检验（列表「详情」按钮）、过程检验（详情弹窗）四条入口**全部走上面这条 SNAPSHOT 数据流**，
不再各自另写一套判定依据来源。

定性 / 文本型指标的判定基准优先级（TBD-06 起，录入与回看**共用**，见 §7.5.4）：

```text
acceptableValues 清单（方案侧结构化配置，随快照固化）
        │  非空 → 只认清单成员：标准语里多出来的取值不再放行，空白成员一律过滤
        ▼
standardText 按 [,，/|] 拆分（历史方案的回落口径，行为不变）
        │  二者都拿不到
        ▼
PENDING（缺判定依据，挂起待确认；严禁无标准放行）
```

> 产出的是 **`DRAFT` 草稿**、既有版本行原样不动 —— 方案改动必须「升版 → 审批」两步，
> 历史检验单的 `plan_snapshot` 因此不会被追溯改写。它与「新建方案」同级（只做 PBAC 物料权限），
> 而**不**像 `…/status` 那样需质量主管角色。端到端守门见 §7.5.8。
