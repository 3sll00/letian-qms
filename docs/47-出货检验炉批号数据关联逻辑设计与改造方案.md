## 1. 客户需求原文与转写

### 1.1 原文（逐条转写，作为验收依据）

| 编号 | 客户原话 | 类型 |
|:---|:---|:---|
| **R1** | 出货检验填写炉批号时，系统优先关联**委外热处理环节**的检验记录 | 优先级 |
| **R2** | 若委外热处理无该炉批号记录，则**回退关联来料检验**记录 | 优先级 |
| **R3** | 若两处均无记录，则**不显示关联数据** | 空态 |
| **R4** | 关联成功后**自动带出机械性能等历史检验数据** | 带出内容 |
| **R5** | 带出数据**支持手工编辑修改** | 可编辑 |

### 1.2 需求含义拆解（本方案的理解口径）

1. 「炉批号」是**关联锚点（key）**，不是普通展示字段：出货检验录入人填一次炉批号，系统据此回查上游检验记录并作为初值回填。
2. 「关联」发生在**录入时（在线、准实时）**，不是事后批处理报表。
3. 「不显示关联数据」（R3）指**空态、静默**：不弹错误、不用占位值或演示值填充，录入人继续手工录入。
4. R5 的「支持手工编辑」隐含一条质量红线：**带出值只是初值，最终以录入人实测为准**，但必须可追溯「哪些值是继承来的、哪些被改过」（EN 10204 3.1 质保书对炉号与实测值的可追溯要求）。

## 2. 现状核查：这条链路现在通不通

### 2.1 结论

**不通。** 服务端 `HeatBatchTraceService` 的优先级算法（委外热处理 → 来料检验 → NONE）**与客户需求几乎逐字一致，但已上线的是「死链」**：炉批号在四个录入表单里都没有写库路径，且查询键与匹配字段错位，该接口**任何输入都只返回 `NONE`**，前端 Banner 永不出现 —— 即客户现阶段看到的现象是「R1/R2/R4 完全没生效」（等价于永远走 R3）。

## 3. 目标口径定稿（唯一真相）

### 3.0 口径依据（行业对标，避免闭门造车）

- **EN 10204 3.1 质保书**：对外证书必须能指明炉号（Heat No）及其对应的力学 / 化学成分实测来源 —— 带出值必须**可回溯到源检验单**，不允许「来源不明」的数值。
- **IATF 16949 §8.5.6.1 / CQI-9（热处理系统评估）**：热处理属特殊过程，其记录须与炉次绑定并可追溯 —— 故第一优先级给「委外热处理」符合行业惯例（热处理工艺直接决定力学性能）。
- **通行 QMS / MES 做法**：上游检验结果**作为初值继承 + 允许人工复测修正 + 保留继承标记**（常见字段名 `inheritedFrom` / `sourceInspectionNo`），而非「继承后锁定」。
- 落地方式沿用本仓既有范式：**口径单点收敛**（同 `docs/43`、`docs/44` 的「唯一实现」做法），不引入新框架。

### 3.1 术语、键与归一化

| 项 | 定稿 |
|:---|:---|
| 业务名 | 炉批号（Heat No）= 钢材冶炼炉号 / 热处理炉批号 |
| 物理列 | `inspection_orders.furnace_heat_batch_no`（**复用既有列**，不新造同义列） |
| 契约字段 | `furnaceHeatNo`（读写统一用名；废弃「用 batchNo 兜底当炉号」的任何写法） |
| 归一化 | 入库与查询前统一：`trim` → 去全角空格 → 转大写 → 删除 `-` / `_` / 空格等分隔符后比较（**归一后比较，原值落库**） |
| 唯一性 | 炉批号在同一物料下唯一；跨物料可重复（见 §3.4） |

### 3.2 关联优先级（三级链路，逐级回退）

```
L1  委外检验·热处理单   inspectionType = 'OQC_HEAT'  且已终判合格
        │ 命中 → sourceType = OUTSOURCE_HEAT_TREATMENT（界面文案「委外热处理」）
        ↓ 未命中
L2  来料检验单          inspectionType = 'IQC'       且已终判合格
        │ 命中 → sourceType = IQC_RAW_MATERIAL（界面文案「来料检验 (IQC)」）
        ↓ 未命中
L3  NONE —— 不显示关联数据（静默空态，不弹错、不填演示值）
```

- 「已终判合格」= `status ∈ {PASSED, COMPLETED}` **且** `judgment ≠ FAILED`（沿用现有实现，并在契约中显式写明；不合格炉次不带出，见 TBD-01）。
- 级别之间**不合并**：只在 L1 全空时才看 L2；L1 命中即返回，不做「混合带出」。

### 3.3 多命中取数排序（同级别内）

同一优先级下若命中多张单，取**唯一确定**的一条：

```
ORDER BY judgment_at DESC NULLS LAST, created_at DESC, order_no DESC LIMIT 1
```

即「**最近一次终判的检验记录**」。排序键必须显式落进仓储 SQL（禁止 `Array.find` + 默认顺序），保证同一输入多次调用结果一致（幂等可复现）。

### 3.4 物料维度

- 请求带 `materialCode` 时：**先在同物料内匹配**；同物料无命中，再放宽到跨物料匹配，并在响应里回 `matchScope = MATERIAL | GLOBAL`。
- 跨物料命中的界面表现：Banner 追加「（跨物料命中，请确认炉次归属）」提示 —— 不静默带出。
- 请求不带 `materialCode` 时：直接全物料匹配（当前表单行为，保留兼容）。

### 3.5 带出数据范围与映射（R4）

| 源检验项 `metricCategory` | 带出到目标分区 | 说明 |
|:---|:---|:---|
| `MECHANICAL_PERFORMANCE`（抗拉 / 屈服 / 伸长率 / 冲击等） | 机械物理性能 | 需求点名的「机械性能」 |
| `HARDNESS` | 机械物理性能 | 委外热处理的核心结果项 |
| `TENSILE_STRENGTH` | 机械物理性能 | 与抗拉同族，避免两套口径 |
| `CHEMICAL_COMPOSITION` | 化学成分 | 冶炼炉号的原始依据 |
| 其它（尺寸 / 外观 / 镀层…） | **默认不带出** | 与炉次无因果关系，见 TBD-05 |

映射规则：**按 `itemCode` 精确匹配优先，`name` 归一包含匹配兜底**；匹配不到的目标指标行保持空值（不猜、不填 0）。只带出「源单里有实测值」的项，空值项不带。

### 3.6 可编辑与留痕口径（R5）

1. 带出值仅作**初值**，录入人可任意修改（现有能力保留）。
2. 每行指标记录来源标记 `inheritedFrom`：`OUTSOURCE_HEAT_TREATMENT` / `IQC_RAW_MATERIAL` / `MANUAL_ENTRY`（契约已有枚举，本轮**真正写入**）。
3. 检验单头记录关联溯源信息：`heatSourceType` / `heatSourceOrderNo`（新增列，见 §4.1），供台账与证书追溯。
4. 修改留痕：Banner 显示「已手动修改 N 项」（现有能力保留），提交时把 `inheritedFrom` 与实测值一并落库；打印链路**禁止**再把缺失来源硬编码成 `OUTSOURCE_HEAT_TREATMENT`（D10）。

### 3.7 明确不做的事（防止范围膨胀）

- 不因带出而自动改判、不自动终判、不自动触发 MRB。
- 不覆盖已终判单据的历史指标（回看只读，口径同 `docs/17 §7.3` 快照即证据）。
- 不在「两处均无记录」时用演示值 / 占位值填充（R3 的静默空态）。
- 不改动 `findByBatchNo` 的既有语义（其它调用方按「批号」使用），炉批号查询**新增方法**。

### 3.8 TEST 标记与清理边界（本轮追加约束，2026-09-23）

本轮为打通链路而**新建或改造的演示 / 联调检验单**（`OQC_HEAT`、`IQC`，以及为链路演示服务的 `OQC_SH` 出货单）必须**统一带 TEST 标记**，以便随时整体清理，且**绝不触碰既有真实数据**：

| 项 | 定稿 |
|:---|:---|
| 标记载体 | `inspection_orders.batch_no` **前缀 `TEST<YYMM>-`**（本月即 `TEST2609-`）—— 复用既有演示约定，判定入口唯一实现 `isDemoRow()`（`packages/infrastructure/src/scripts/demo-inspections.ts:50 / :135`），**不新造列、不引入第二套标记** |
| 清理匹配 | `batch_no LIKE "TEST%"`（宽匹配兜底，兼容往月与后续批次前缀） |
| 演示炉批号 | 演示数据的炉批号一律以 `TEST-` 开头（如 `TEST-HT-2609-001`），保证外溢到台账 / 质保书 / 追溯看板时**一眼可辨**，不与真实钢厂炉号、真实 MTC 混同 |
| 硬边界 | 任何**回填、修复、清理**只允许命中 `batch_no LIKE "TEST%"` 的行；无此前缀的真实行一律**只报告、不修改、不删除**（与既有 `db:demo:repair` 中「非演示行只报告不擅改」同一条口径） |
| 演示样例 | 至少三组：① 同一 TEST 炉批号在 `OQC_HEAT` 与 `IQC` 各一条（验 L1 优先）；② 仅有 `IQC`（验 L2 回退）；③ 两处均无（验 L3 静默空态） |

> 为什么不用新列 `is_test_data`：仓库已有 `batch_no` 前缀这一**在用的**演示标识（`docs/46` 的体检 / 修复工具正靠它划边界），再引入布尔列会形成两套标记口径；若后续需要「测试库 / 演示库物理隔离」，再单独立项。

### 3.9 同炉异常提示（TBD-01，P1 已实现）

源单「未终判 / 判不合格」一律**不参与带出**（§3.2 的筛选条件）；同时，**同一炉批号**存在异常记录时，`GET /inspections/heat-batch-trace` 在响应里附 `upstreamWarning`（`code` / `orderNos` / `message`），界面渲染为一条琥珀色提示条：

| 项 | 定稿 |
|:---|:---|
| 提示 ≠ 门禁 | **只提示、不带值、不阻断** —— 带出链路照常按 L1→L2 回退；「不合格就不许下游开工」属跨环节传递门禁（`docs/48`），两者**不合并、互不替代**（一个挂在录入页的取数上，一个挂在建单 / 放行上） |
| 理由码 | `UPSTREAM_FAILED`（存在不合格记录）/ `UPSTREAM_UNDER_MRB`（MRB 评审未结案）/ `UPSTREAM_INSPECTING`（尚未终判） |
| 归类优先级 | 单据状态 `IN_MRB_REVIEW` **先归 MRB**：进 MRB 的单同时带着 `overallDecision = FAILED`，若先按不合格归类，「MRB 评审未结案」这个码永远报不出来（实现里最容易写错的一处，已有单测锁定） |
| 报告优先级 | 多类同时存在**只报一类**：不合格 > MRB 未结案 > 未终判；同类命中单号一并给出（升序、最多 10 条） |
| 文案 | 服务端**单点组装**（`warningWithMessage()`），界面只选标题、不二次拼文案；带出成功时补「本次带出的数据来自最近终判合格的记录（请核对炉次归属）」，空态时说明「未带出该炉数据」与处置方向 |
| 物料维度 | 提示与带出**同一物料维度**：带 `materialCode` 时只看同物料异常；跨物料同炉的异常不参与本提示（跨物料信号由 `matchScope = GLOBAL` 承担），避免给出与本次带出无关的噪声 |
| 自单排除 | 查询必须带 `excludeOrderId`（录入页自动带本单 id）：本单自身处于「检验中」，不排除会被判成「上游尚未终判」而给出**假提示**，使「上游两处均无」的炉号凭空冒出提示条（直接污染 AC-04 的静默空态） |
| 无异常 | **整个字段缺省**（不是 `undefined` 值），避免契约校验解析出悬挂键 |

> 为什么提示挂在「带出接口」上、而不新开一个「上游体检」接口：录入人此刻只关心一件事 ——「这个炉号的数据能不能用、有没有坑」。两者放在同一次请求里，界面才不会出现「数据带出来了、提示还没到」的中间态。

```
   inheritedItems → 按 itemCode / name 映射到本单方案指标行，标记 inheritedFrom

④ 落库（提交）

   POST /inspections/{id}/status（终判，口径不变）
        └─ 后续：台账「炉号」列、质保书「炉号/批号」栏、追溯看板按炉批号倒查（D13 连带点亮）
```

### 9.3 实施踩坑（迁移 034 生成列正则）

生成列 `furnace_heat_batch_no_norm` 的正则字符类**必须双重转义**：TS 源码写成 `'[\\s\\-_\\u3000]'`（SQL 侧得到 `[\s\-_\u3000]`）。

- 写成单反斜杠 `'[\s\-_　]'`：JavaScript 先吃掉 `\s` → SQL 退化成 `[s-_　]`（`s-_` 成了非法区间）；
- 写成 E-string `E'[\s\-_\u3000]'`：PostgreSQL 的 E-string 解析器同样吃掉 `\s` → 同样退化。

两种错法都**静默**（建列成功，写入时才报 `invalid regular expression`）。已实测：`' test-ht_2609-001 '` → `TESTHT2609001`，全角空格同样被剔除。
