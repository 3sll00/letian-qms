# 26-来料检验「物料名称 / 规格型号」数据字段与接口打通设计

需求原文：【来料检验】里面你把【规格型号】列的内容放进了【物料名称】列内，需要把数据字段、数据库对接字段
和接口（数据库字段迁移脚本、后端契约与 API 接口）一并改造打通。

---

## 1. 现象与根因

### 1.1 现象

来料检验（IQC）台账第 5 列「物料名称」显示为 `不锈钢线材 Φ5.0mm` / `35CrMo 合金圆钢 Φ8.0mm` 这类
**品名 + 规格** 的合体文本，而第 6 列「规格型号」整列为空。

### 1.2 根因（本机库实测，2026-09-22）

```sql
SELECT order_no, order_type, material_code, material_name, specification, unit
FROM inspection_orders ORDER BY order_no;
```

24 行结果中 `specification` 与 `unit` **全部为空**（NULL/空串），`material_name` 则完整取自
`materials.material_name`（管家婆 ERP `Ptype.FullName` 快照，该字段本身含简短规格后缀）：

| order_no | material_code | material_name | specification | unit |
|:---|:---|:---|:---|:---|
| INS-20231011-0001 | MAT-35CRMO-08 | 35CrMo 合金圆钢 Φ8.0mm | *(空)* | *(空)* |
| INS-20231012-0001 | MAT-304SS-05 | 不锈钢线材 Φ5.0mm | *(空)* | *(空)* |
| INS-20231013-0001 | MAT-304SS-05 | 不锈钢线材 Φ5.0mm | *(空)* | *(空)* |

而权威规格来源 `materials.spec_model` 一直是有值的：

| material_code | material_name | spec_model | unit |
|:---|:---|:---|:---|
| MAT-304SS-05 | 不锈钢线材 Φ5.0mm | Φ5.0mm / 盘圆 / 304HC | KG |
| MAT-35CRMO-08 | 35CrMo 合金圆钢 Φ8.0mm | Φ8.0mm / 热轧圆钢 / 35CrMo | KG |
| MAT-BLT-88-M10 | 六角螺栓M10 | M10×30 / 8.8级 / 蓝白锌 | PCS |

断链位置：

1. **写路径未落列**：`inspection_orders.specification` 与 `unit` 是迁移 `006` 新增的快照列，
   但 `seeds/runner.ts` 建单时只写了 `materialName`，从未写入 `specification` / `unit`；
   `KyselyInspectionOrderRepository.save()` 又是「显式传入才写」口径，于是两列恒为 NULL。
2. **无回填迁移**：存量库没有把 `materials.spec_model` 回填到台账的迁移脚本。
3. **读路径与契约其实已就绪**：契约 `specification` / `spec` / `unit`、领域 `toDTO()`、
   仓储 `mapRow()`、API 透传、前端 `IqcList.tsx` 第 6 列 `{item.spec}` 都在位。
   即：**这是一条「读得出、写不进」的断链**（与 `docs/24 §6 D4` 的 `work_order_no` 同型）。

> 结论：修复点不在前端渲染，而在 *数据 + 写入路径*。仅补数据不回填写入路径，下次播种/建单会再次为空；
> 仅改写入路径不回填数据，当前界面依旧为空。二者必须同时做。

## 2. 口径结论（唯一权威）

| 台账列 | 契约字段 | 数据库物理列 | 权威来源 | 语义 |
|:---|:---|:---|:---|:---|
| 物料名称 | `materialName` | `inspection_orders.material_name` | `materials.material_name`（ERP `Ptype.FullName`） | **物料品名**（ERP 品名快照，管家婆该字段自带简短规格后缀） |
| 规格型号 | `specification` | `inspection_orders.specification` | `materials.spec_model`（ERP `Ptype.Standard`） | **规格型号**（独立列，与品名各归其位） |
| 规格型号（别名） | `spec` | *不落库* | 读侧由 `specification` 派生 | 兼容早期调用方的只读别名 |
| 数量单位 | `unit` | `inspection_orders.unit` | `materials.unit`（ERP `Unit1`） | 计量单位 |

三条硬口径：

1. **`specification` 是规格型号的唯一落库列**，`spec` 只是读侧别名，**永不落库**（避免同一语义两个物理列）。
2. **`materials` 是 ERP 主数据镜像，QMS 不得改写**。`material_name` 中出现的规格后缀是管家婆
   `Ptype.FullName` 的既有形态，属 ERP 侧数据口径；QMS 的职责是把「品名」与「规格型号」两列**各自接对**，
   而不是伪造/裁剪 ERP 品名。若业务要求「物料名称」只显示品名，应改 ERP `Ptype.FullName`
   或在主数据引入独立品名列（**不属于本次字段打通范围**，见 §7 遗留项）。
3. **兜底方向唯一**：`specification` / `unit` 只能从 `materials` 主数据按 `material_code` 回查，
   匹配不到即保持为空，**绝不从 `material_name` 猜规格**（那正是本次要消除的歧义）。

`GET /inspections` 返回行同时带 `specification` 与 `spec`（同值），前端优先取 `specification`。

## 3. 数据库字段改造（迁移 `023`）

新增 `packages/infrastructure/src/migrations/023_backfill_inspection_order_spec_snapshot.ts`（已在 `runner.ts` 注册）：

| 动作 | SQL 语义 |
|:---|:---|
| 回填规格型号 | `UPDATE inspection_orders o SET specification = m.spec_model FROM materials m WHERE o.material_code = m.material_code AND (o.specification IS NULL OR btrim(o.specification) = '')` |
| 回填计量单位 | `UPDATE inspection_orders o SET unit = m.unit FROM materials m WHERE o.material_code = m.material_code AND (o.unit IS NULL OR btrim(o.unit) = '')` |

安全边界：

1. **只填 NULL / 空白行**，不覆盖任何已有快照值（与迁移 `011` / `022` 同口径）；
2. 匹配不到主数据的行保持原样，不做任何猜测；
3. `down()` 保留空实现并注明理由：回填类迁移不可逆，无法逐行区分哪些值是本迁移写入的；
4. 该迁移与种子数据（`seeds/runner.ts` 的 `materialSpecOf()` / `materialUnitOf()`）构成双保险——
   种子负责新写入的行，迁移负责把已存在的历史库一次性对齐。

`packages/contracts/src/schemas/inspection.ts`：

| Schema | 字段 | 改造 |
|:---|:---|:---|
| `InspectionOrderSchema`（读模型） | `materialName` | 描述明确为「物料品名（ERP Ptype.FullName 快照）」 |

## 5. 领域 / 应用 / 仓储 / API 改造

| 层 | 文件 | 改动 |
|:---|:---|:---|
| 领域 | `packages/domain/src/models/inspection-order.ts` | 无改动（`specification` / `unit` 私有字段、getter、`toDTO()` 已按 `specification` 同时回填 `spec` 别名） |
| 应用 | `packages/application/src/use-cases/inspections/create-inspection-order.ts` | 建单时按 `material_code` 从存货档案兜底补齐 `materialName` / `specification` / `unit`（见 §5.1） |
| 应用 | `packages/application/src/use-cases/inspections/create-reinspection.ts` | 复检单沿用原单快照：`specification` / `unit`（§5.1），以及单据标识列 `inboundNo` / `inboundDate` / 客户 / 销售出库 / 委外工艺（§5.2） |
| 基础设施 | `packages/infrastructure/src/repositories/inspection-order-repository.ts` | `save()` 的 insert 与 `onConflict doUpdateSet` 两处改为 `order.specification ?? order.spec` 归一后落 `specification` 列——此前只认 `specification`，只传契约别名 `spec` 的调用方会静默写不进去 |
| 基础设施 | `packages/infrastructure/src/database/schema.ts` | 无改动（`specification` / `unit` 列类型已在位） |
| 接口 | `apps/api/src/controllers/inspections.controller.ts` | `GET /inspections` 走 `selectAll()` 透出 `specification`（无改动）；`POST` 的 `materialName` 改为「传了才透传」，省略时交由用例按存货档案补齐 |

### 5.1 写路径的存货档案兜底（本轮补齐的第二处断链）

上一版只修了「存量数据」与「仓储落列」，但**建单写路径仍是纯透传**：

```ts
// 改造前（create-inspection-order.ts）
materialName: cmd.materialName,
specification: cmd.specification ?? cmd.spec,   // 调用方不带就落 NULL
unit: cmd.unit,
```

后果：ERP / MES 下发建单（通常只带物料编码）或任何省略规格型号的调用方，新建的检验单
`specification` 依旧为空 —— 迁移 `023` 只救历史数据，**新单会再次空掉**，等于断链没真正闭合。

改造后，`materials` 主数据（调用用例时已经为 PBAC 分类判定加载过一次）直接用于兜底：

| 字段 | 优先级 |
|:---|:---|
| `materialName` | 请求体 → 存货档案 `materials.material_name`；两者都没有 → 400 `validation-failed`（`material_name` 是 NOT NULL 列，绝不写空） |
| `specification` | 请求体 `specification` → 请求体别名 `spec` → 存货档案 `materials.spec_model`；都没有 → NULL（不猜） |
| `unit` | 请求体 → 存货档案 `materials.unit`；都没有 → NULL |

口径细节：

1. **空串与纯空白一律视作「未提供」**（`nonBlank()` 归一），避免把 `''` 当成快照落库；
2. **显式传入永远优先**：兼容 ERP/MES 下发的历史值、以及现场手工改规格的场景；
3. `CreateInspectionOrderRequestSchema.materialName` 由必填改为**可选**（放开是为了让只带
   `materialCode` 的 ERP/MES 调用方合法建单；对既有调用方完全向后兼容）；
4. 前端 Mock（`apps/web/src/mocks/handlers.ts`）按同一口径兜底，离线演示与真实后端一致。

### 5.2 复检单沿承原单的「单据标识快照」（本轮的第三处断链）

复检单由 MRB 返工处置产生（`decide-mrb-disposition.ts` → `create-reinspection.ts`），
它检验的是**同一批来料、同一张出入库单据**，因此描述「批次从哪来」的凭证列必须与原单逐字段一致。

改造前 `create-reinspection.ts` 只透传 `materialName` / `supplierName` / `specification` / `unit`，
`inboundNo` / `inboundDate` 等列在构造复检聚合根时被整体丢弃。后果：复检单与原单同检验类型、
并列出现在同一张台账里，却出现**「原单有入库单号、复检行显示 `-`」**的链路断点
（本机库当前无复检行，属**潜伏缺陷**：任何一次 MRB 返工处置都会立即产生空列行）。

| 类别 | 字段 | 处理 |
|:---|:---|:---|
| 来料检验（006） | `inboundNo` / `inboundDate` | 原单有值即沿承 |
| 出货检验（008） | `customerCode` / `customerName` / `salesOrderNo` / `dispatchDate` / `salesOrderPoNo` / `erpStatus` | 同上（建单接口当前只下发 `customerName`，`customerCode` 一并沿承以备对账键） |
| 委外检验（009） | `processType` / `vendorName` | 同上 |
| 委外检验（009） | `outsourceNo` / `returnDate` | **刻意不沿承**：读侧 `mapRow` 对这两列已有展示兜底（缺省回落 `batchNo` / 建单日期），若在此落库，等于把「展示推导值」固化成「真实凭证号」，此后无法再区分该值是 ERP 下发还是系统推导 |
| 检验人（006） | `inspectorId` / `inspectorName` | **刻意不沿承**：检验人快照的写入方是实际录入实测值 / 草稿的操作人（`record-measurements-and-judge.ts` / `save-inspection-draft.ts`），复检单录入后自然带出真实检验人，沿用原单会张冠李戴 |

口径细节：

1. 沿承**只发生在原单有值**时（`...(origOrder.X !== undefined ? { X: origOrder.X } : {})`），
   原单该列为空时复检单保持同样为空 —— 不猜、不推导；
2. 沿承**不回查主数据**：与 `supplierName` 同一原则，保证复检单与原单的展示口径完全一致；
   即使原单的值来自建单当时的存货档案快照、此后主数据被改动，两行依然对得上账；
3. 本轮**不新增数据库迁移**：这 10 个物理列自 006 / 008 / 009 起已在位，
   `save()` 的 insert 与 `onConflict doUpdateSet` 也早已按「显式传入才写」落列（见 §5 基础设施行），
   缺的只是用例透传这一层。
4. 复检单标识由**处置响应**回吐（第四轮闭环）：`POST /mrb/records/{id}/disposition` 处置 `REWORK`
   时返回 `reinspectionOrderId` / `reinspectionOrderNo`，调用方无需按 `batchNo` 反查
   （反查在复检单尚未提交时必然为空），见 `docs/21-MRB不合格品处置数据字段与接口打通设计.md` §11。

## 7. 验收口径与证据

1. `pnpm db:migrate` 后 `inspection_orders.specification` / `unit` 不再为空（IQC 三行为
   `Φ5.0mm / 盘圆 / 304HC` 与 `Φ8.0mm / 热轧圆钢 / 35CrMo`）；
2. `pnpm db:seed` 重新播种后上述值仍成立（种子双保险验证）；
3. `scripts/testing/inspections-verify.cjs` 新增断言（浏览器实际渲染值 = 接口值）：
   - IQC 表头含「规格型号」；
   - IQC「规格型号」列逐行非空且**逐行等于接口 `specification`**；
   - IQC「规格型号」列取值**不等于**同行「物料名称」列（两列不得同值，防止再次串列）；
   - IQC「物料名称」列**逐行等于接口 `materialName`**（该列此前从未与接口对账过）；
4. `apps/api/test/integration/e2e.test.ts` §2.8.1：POST 建单**刻意省略** `materialName` / `specification` / `unit`，
   断言回包与落库三列均等于 `materials` 存货档案值（覆盖 §5.1 的写路径兜底，防止新单再次空掉）；
5. `apps/api/test/integration/e2e.test.ts` §2.3.2（返工 → 复检单全链路）：带 `inboundNo` / `inboundDate` /
   显式 `specification` / `unit` / `customerName` / `processType` / `vendorName` 建单 → 越界录入判定 `FAILED` →
   入待审核池 → 发起评审 → MRB 处置 `REWORK`，断言复检行（`{原单号}-R2`）在**库中**与**台账查询接口**
   两处都逐字段等于原单；其中 `specification` / `unit` 刻意取与存货档案**不同**的值，
   用以区分「沿承原单快照」与「回查存货档案」两种实现；并断言**处置响应体**回吐
   `reinspectionOrderNo = {原单号}-R2` 且与库内行的 `id` / `order_no` 逐一对齐（`docs/21` §11）；
6. `pnpm typecheck`、API 单测 / 契约测试全绿。

### 7.1 遗留项（本次不实施，已记录）

- **物料名称是否应只显示品名**：当前 `materials.material_name` 为 ERP `Ptype.FullName` 镜像，
  含简短规格后缀。若业务要求台账「物料名称」只显示品名，需要
  (a) 改 ERP `Ptype.FullName`；或 (b) 主数据新增独立品名列并在 `inspection_orders` 增列快照。
  二者都属于主数据口径调整，不在「把规格型号接进规格型号列」这一范围内。
