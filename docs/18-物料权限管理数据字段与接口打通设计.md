# 物料权限管理 (PBAC) 数据字段与接口打通技术方案

> **版本**：v1.0
> **更新时间**：2026-09-21
> **对应原型**：WPS图片(20)
> **对应页面**：系统管理 → 物料权限管理（`apps/web/src/pages/integration/index.tsx`）
> **对应迁移**：`013_permission_management_hardening.ts`

---

## 1. 背景与业务目标

依据《乐天质量管理系统 (QMS) 业务需求说明书》(`01-PRD.md` §3.9) 与原型 `prototypes/WPS图片(20).png`，物料权限管理承担「用户只能查看自己有权限的物料数据」的行级数据隔离职责，包含三个子能力：

1. **用户权限列表**：按用户 × 角色维护三维白名单（物料分类 / 物料编码 / 供应商），支持新增、编辑、复制、启停、删除、CSV 批量导入；
2. **按角色批量配置**：一次性改写某角色下全部用户规则的三维白名单；
3. **权限校验日志 + 权限校验工具**：记录每次敏感数据查询的行级过滤与拦截结果（PRD 要求保留 ≥ 180 天），并提供「某用户 × 某物料」的实时诊断能力。

本次任务对上述三块能力做**全字段链路核查**：界面字段 → `@letian/contracts` 契约 → Fastify API → Kysely 仓储 → PostgreSQL 物理列，逐项确认是否存在「界面有、链路断」的情况，并对断链处一次性改造打通。

## 3. 核查结论

### 3.1 已打通字段（无需改造）

| 界面字段 | 契约字段 | 物理列（`material_permissions`） | 接口 | 结论 |
|:---|:---|:---|:---|:---:|
| 用户姓名 | `userName` | `user_name VARCHAR(64) NOT NULL` | `GET /permissions/materials` | ✅ 已通 |
| 用户ID | `userId` | `user_id UUID NOT NULL`（FK → `employees.id`） | `GET /permissions/materials` | ✅ 已通 |
| 角色 | `roleCode` | `role_code VARCHAR(64) NOT NULL`（FK → `roles.role_code`） | `GET /permissions/materials` + `GET /permissions/roles` | ✅ 已通 |
| 物料编码权限 | `materialCodes` | `material_codes JSONB NOT NULL DEFAULT '[]'` | `GET/POST/PUT /permissions/materials` | ✅ 已通 |
| 物料分类权限 | `materialCategories` | `material_categories JSONB NOT NULL DEFAULT '[]'` | `GET/POST/PUT /permissions/materials` | ✅ 已通 |
| 供应商权限 | `supplierCodes` | `supplier_codes JSONB NOT NULL DEFAULT '[]'` | `GET/POST/PUT /permissions/materials` | ✅ 已通 |
| 状态（启停开关） | `isActive` | `is_active BOOLEAN NOT NULL DEFAULT true` | `PUT /permissions/materials/:id` | ✅ 已通 |
| 权限校验日志（时间/用户/资源/动作/结果/明细） | `createdAt` / `userName` / `resourceType` / `action` / `decision` / `detail` | `authorization_logs` 对应 6 列 | `GET /permissions/logs` | ✅ 已通 |
| 唯一性口径（一人一角色一条规则） | 冲突返回 409 | `uq_permission_user_role UNIQUE (user_id, role_code)` | `POST /permissions/materials` | ✅ 已通 |

> 补充确认：读侧行级过滤（`buildMaterialPermissionWhere`）与写侧安全上下文（`SecurityContextFactory`）均直接消费上述三维 JSONB 列，与「界面配置即运行时口径」的 PRD 要求一致。

> **三维维度的域适用范围（2026-09-23 定稿，见 `docs/42` §3）**：三维不是任何场景都全判 ——
> **供应商维度只在"对象自身具备供应商属性"的域参与判定**（检验单 / 不合格待审核池 / MRB 处置单）。
> **方案域**（`inspection_plans`：方案 / 方案版本 / 指标项）对象无供应商属性，读方案只判**物料分类 + 物料编码**；
> 否则三维限定账号（如 IQC 检验员：分类 + 编码 + 供应商）会在录入页按物料匹配方案时恒 403、指标清单恒空。
> 实现开关：`SupplierDimensionMode = 'ENFORCE' | 'NOT_APPLICABLE'`（领域层 `PBACEvaluator`、读侧 `buildMaterialPermissionWhere`、
> 写侧 `ISecurityContext.assertAccess` 三处共用；默认 `'ENFORCE'`，**仅方案域**显式传 `'NOT_APPLICABLE'`）。
> 边界：不放宽物料维度（分类 / 编码不命中仍拒绝）、不放宽单据域、无生效规则仍 fail-closed。

### 3.2 断链清单（本次改造对象）

| # | 断链点 | 现象 | 根因 | 影响面 |
|:---:|:---|:---|:---|:---|
| **D1** | 编辑规则保存（`PUT /permissions/materials/:id`） | 实测返回 `400 参数验证失败 — userName: Required` | 契约 `UpdateMaterialPermissionRequestSchema = MaterialPermissionSchema.omit({id:true})` 把 `userName` 定为**必填**，而编辑弹窗 `RuleEditorModal.handleSave()` 提交的 body 不含 `userName` | **编辑权限配置、复制后调整保存 100% 失败**（列表页的状态开关因显式带了 `userName` 才未暴露） |
| **D2** | 职员主角色（`employees.role_code`） | 实测 `GET /auth/users` 与 `POST /auth/login` 恒返回 `roleCode=GUEST` / `roleName=普通访客`；库中实际为 `QA_MANAGER`/`IQC_INSPECTOR` 等 | 物理列已由迁移 003 建立并由种子写入，但 `KyselyMasterDataRepository.mapEmployee()` **未映射 `roleCode`**，`saveEmployee()` 也**不接受 `roleCode`** 入参，字段在仓储层被静默丢弃 | 物料权限管理页的用户下拉/校验工具下拉角色失真；登录身份角色错标；`/permissions/logs` 的 `role_code` 全部记为 `GUEST`；**`getRequestPermissions` 里 `ADMIN`/`QA_MANAGER` 的超级角色兜底永久失效** |
| **D3** | 数据库完整性与查询性能 | `employees.role_code` **无外键**约束（可指向不存在的角色）；列表页「按物料编码筛选」走 `material_codes ? $1` 的 JSONB 包含运算符，但 `material_codes` **无 GIN 索引** | 迁移 003 只建了 `fk_permission_user` / `fk_permission_role`，未覆盖 `employees.role_code`；三维 JSONB 列只建了普通 B-Tree（`idx_permissions_role`） | 脏角色编码可写入库并导致规则外键报错；按物料编码检索退化为全表顺序扫描 |
| **D4** | OpenAPI 注册表与运行时不符 | `packages/contracts/src/openapi/generator.ts` 把规则 CRUD 注册在 `/api/v1/permissions` 与 `/api/v1/permissions/{id}`，而控制器实际挂载在 `/api/v1/permissions/materials` 与 `/api/v1/permissions/materials/{id}`；编辑接口的请求体还登记为全字段必填的 `CreatePermissionRequestSchema` | 控制器路由在 `/permissions` 前缀下追加了 `/materials` 段，OpenAPI 注册表未同步；PUT 契约收敛后登记项未跟进 | 对外接口文档指向不存在的路径，且编辑所需字段集合与运行时校验不一致 |

## 4. 数据库迁移设计（`013_permission_management_hardening.ts`）

迁移遵循「**幂等、只补不删、不覆盖业务语义**」原则（与 010/011 历史回填迁移同构），全部语句可重复执行。

| 序号 | 变更 | 目的 | 幂等策略 |
|:---:|:---|:---|:---|
| 1 | `UPDATE employees SET role_code = NULL WHERE role_code NOT IN (SELECT role_code FROM roles)` | 清理历史脏角色编码，为加外键扫清障碍 | 条件更新，天然幂等 |
| 2 | `ALTER TABLE employees ADD CONSTRAINT fk_employee_role FOREIGN KEY (role_code) REFERENCES roles(role_code) ON DELETE SET NULL` | 打通「职员主角色 → 角色字典」引用完整性（D3） | `pg_constraint` 存在性判断后创建 |
| 3 | `UPDATE material_permissions p SET user_name = e.name FROM employees e WHERE p.user_id = e.id AND (p.user_name IS NULL OR p.user_name = '')` | 冗余展示列 `user_name` 为空时按职员档案回填，保证列表「用户姓名」列永不为空 | 仅在为空时回填，**不覆盖**已有姓名（保留演示口径，如「张三 (测试质检员)」） |
| 4 | `CREATE INDEX idx_permissions_material_codes ON material_permissions USING gin (material_codes jsonb_path_ops)` | 支撑列表页 `material_codes ? $1` 的物料编码检索（D3） | `CREATE INDEX IF NOT EXISTS` |
| 5 | `CREATE INDEX idx_permissions_user ON material_permissions (user_id)` | 支撑 `findByUserId` / `findAllForUser`（运行时权限评估热路径） | `CREATE INDEX IF NOT EXISTS` |
| 6 | `CREATE INDEX idx_authorization_logs_user_created ON authorization_logs (user_id, created_at DESC)` | 支撑校验日志「按用户 + 倒序分页」查询 | `CREATE INDEX IF NOT EXISTS` |
| 7 | `UPDATE authorization_logs l SET role_code = e.role_code FROM employees e WHERE l.user_id = e.id AND l.role_code IS DISTINCT FROM e.role_code AND e.role_code IS NOT NULL` | 历史日志角色错标（D2 期间全部落库为 `GUEST`）回正为真实主角色 | 条件更新，天然幂等 |

**回滚（`down`）**：删除 4/5/6 三个索引与 `fk_employee_role` 外键；数据回填类变更不可逆（与 010 的口径一致，保留空实现）。

## 5. 契约层改造（`@letian/contracts`）

`packages/contracts/src/schemas/permission.ts`：

- `UpdateMaterialPermissionRequestSchema` 由 `MaterialPermissionSchema.omit({ id: true })` 改为**显式定义**，其中：
  - `userName` 由必填改为 `z.string().min(1).optional()`，与 `CreatePermissionRequestSchema` 的「缺省时服务端从职员档案补全」口径**完全对齐**；
  - 其余字段（`userId` / `roleCode` / 三维数组 / `isActive`）保持原有约束不变。

> 该改造消除 D1 的根本原因：契约不再要求调用方回传一个服务端本就能推导的冗余展示字段。

`packages/contracts/src/schemas/integration.ts` 的 `EmployeeSchema` 已含 `roleCode`（`z.string().optional()`，注释「主角色编码，关联角色字典 roles.role_code」），**无需变更**——缺口在仓储映射层实现，见第 6 节。

`packages/contracts/src/openapi/generator.ts`（OpenAPI 注册表）同步对齐运行时路由与契约（D4）：

| 注册项 | 修正前 | 修正后 |

## 6. 后端改造

### 6.1 控制器（`apps/api/src/controllers/permissions.controller.ts`）

`PUT /materials/:id`：当请求体未携带 `userName` 时，服务端调用既有 `resolveUserName(userId)` 从职员档案补全后再落库，保证 `material_permissions.user_name` 快照始终有值：

```
const userName = body.userName ?? existing.userName ?? (await resolveUserName(body.userId));
```

（三重兜底顺序：请求体 → 规则原值 → 职员档案，避免因改名/换人导致姓名快照被无意义清空。）

### 6.2 仓储（`packages/infrastructure/src/repositories/master-data-repository.ts`）

| 方法 | 改造 |
|:---|:---|
| `mapEmployee(row)` | 补 `roleCode` 输出：`...(row.roleCode !== null ? { roleCode: row.roleCode } : {})`，把物理列 `employees.role_code` 真正暴露到 `Employee` 契约（D2 核心） |
| `saveEmployee(data)` | 入参增加可选 `roleCode`，写入 `role_code` 列，使 ERP 同步/新增员工路径也能维护主角色（写路径打通） |

改造后，`/auth/users`、`/auth/login`、`/master-data/employees` 三个接口同时恢复真实角色输出，且不改变任何既有字段的语义与顺序。

### 操作提示（一次性）

JWT 的 `role` 声明是**签发时刻的快照**。修复前签发并缓存在浏览器 `localStorage`
（键 `letian_qms_token` / `letian_qms_user`）的令牌里仍是 `role: 'GUEST'`，
因此在完成本次修复的机器上需要**退出登录后重新登录一次**（或页面 `401` 自动重登），
顶栏与权限校验日志才会显示真实主角色。修复后新签发的令牌均为真实角色，无需再次干预。

## 9. 分类字典变更的同步口径（027 补记，2026-09-22）

`material_permissions.material_categories` 在 SQL 下推时走**精确 `IN` 匹配**：
`packages/infrastructure/src/repositories/pbac-sql-translator.ts` 生成
`EXISTS (SELECT 1 FROM materials WHERE materials.material_code = 目标行.material_code AND materials.category_code IN (...))`，
**没有父子继承展开** —— 白名单里写了 `CAT-FINISH`（成品紧固件，1 级）并不会自动覆盖 `CAT-FIN-BOLT`（2 级）。

由此得到一条硬口径：**任何新增 / 调整存货分类，都必须同步核对受影响规则的分类白名单**，
否则会出现「分类改了、授权范围悄悄变小」这类静默失效（fail-closed 之下表现为列表条数变少，不报错）。

本轮（迁移 `027`，见 `docs/33` §4）新增分类 `CAT-FIN-MACH`（机加工成品件）并把两条委外机加工成品件归位，
按上述口径同步扩展了唯一一条覆盖成品件的规则，使可见范围与迁移前**等价**：

| 规则 ID | 用户 / 角色 | 变更前白名单 | 变更后白名单 |
|:---|:---|:---|:---|
| `70000000-0000-4000-8000-000000000003` | 刘芳 / `OQC_INSPECTOR` | `["CAT-FINISH","CAT-FIN-BOLT"]` | `["CAT-FINISH","CAT-FIN-BOLT","CAT-FIN-MACH"]` |

守门断言：`scripts/testing/mrb-wiring-verify.cjs` 的「池 PBAC 分类维度下推」逐条比对**接口返回的物料编码集合**
与**按当前白名单从库现算的期望集合**（期望值不写死），因此白名单与 `materials.category_code` 任何一侧漂移都会失败。
