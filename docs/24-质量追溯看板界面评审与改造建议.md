# 24 质量追溯看板界面评审与改造建议

> **评审对象**：质量追溯看板（订单维度原型稿，共 3 张截图：`订单信息 — PO-B-002`、`订单信息 — PO-D-004`、`订单 PO-B-002 时间线`）
> **评审依据**：`docs/01-PRD.md` §3.1、`docs/09-界面与开源组件.md` §3、`docs/04-API与导入规范.md` §3.6
> **评审结论**：视觉设计与信息分层**合理，予以保留**；但追溯口径发生漂移，**必须按 §4 改造后再交付**。
> **落地状态**：代码与文档变更清单见 §9。

---

## 1. 一句话结论

界面本身"层级清楚、状态可读"，问题不在长相，在**口径**。

原型把「**订单 → 检验环节时间线**」画成了「**完整质量追溯链路**」。而 PRD 与后端定义的质量追溯，是**以批次号 / 炉批号为唯一主键**的「原材料 → 工序 → 委外 → 成品 → 出货」血缘 DAG。

两者不是同一件事：

- 一张订单可以投多个批次（换料、分批投料）；
- 一个批次可以流向多张订单 / 多个客户（一批原料供多单）。

用订单号当追溯主键，会同时产生两类错误：

| 错误类型 | 表现 | 后果 |
| :--- | :--- | :--- |
| **假阴性** | 只用本订单号展开，查不到该批次流向的其它订单 | 客户投诉时漏查受影响批次；原料缺陷影响面评估不完整 |
| **假阳性** | 把同一订单下**并列**的多条检验环节串成一条"链" | 把没有血缘关系的批次画成上下游，误导追溯结论 |

**结论：批次是追溯的主键，订单号是检索入口。**

## 2. 保留项（视觉设计与交互骨架）

| 保留项 | 说明 |
| :--- | :--- |
| 三段式页面结构 | 「筛选栏 → 概览卡 → 链路画布」，阅读顺序符合"先定位、再看结论、最后追细节" |
| 节点卡片信息结构 | 单号 / 结论 / 时间 / 状态四件套齐全，横向箭头表达流转方向 |
| 原材料追溯独立分区 | 「采购入库 & 来料检验」从主链路中拆出来单独一块，符合现场"先看料、再看工"的习惯 |
| 时间线表格 | 序号 / 环节 / 单号 / 来源单据 / 状态 / 检验人 / 时间的列顺序合理，适合直接打印 |
| 色彩语义 | 绿=合格、红=不合格、蓝=检验中、灰=待检验，与 `docs/09` §3 一致 |

## 3. 口径漂移清单（含证据）

### 3.1 追溯主键从"批次"漂移成"订单"

- **现象**：筛选栏只有「订单号 / 物料编码 / 成品名称」，没有「批次号 / 炉批号」。
- **证据（文档）**：`docs/01-PRD.md` §3.1 定义该看板为"**批次与炉批全景追溯链**（原材料炉批号/来料批次 → 工序流转 → 委外 → 销售出货），支持双向追溯"；`docs/09-界面与开源组件.md` 原型索引 `WPS图片(12).png` 同样写"**炉批号/生产批次/委外批次**全景血缘拓扑图谱"。
- **证据（代码）**：`apps/api/src/controllers/trace.controller.ts:43` 只有 `GET /:batchNo`；`packages/contracts/src/schemas/trace.ts:42` 把 `batchNo` 定义为必填；`trace.controller.ts:16` 的唯一路径参数就是批次号。
- **后果**：§1 的假阴性 / 假阳性。

### 3.2 节点卡片丢失"批次号 / 炉批号"两个关键标识

- **现象**：卡片主标题是检验单号（如 `IPQC-CT-20260706-0002`），没有批次号与炉批号。
- **证据**：`docs/01-PRD.md` §3.1 与 `docs/09` §3 都把"炉批号"列为追溯第一标识；`batch_trace_nodes.batch_no` 本身是 `UNIQUE` 键（见 §5.1）。
- **后果**：现场拿到一张卡片无法回到实物批次，追溯断在最后一厘米。

### 3.3 缺少追溯方向与非订单方向的影响面统计

- **现象**：只有一条"正向"链路，没有正向/反向切换，也没有"本批原料流向哪里"的统计。
- **证据**：`packages/contracts/src/schemas/trace.ts:20-24` 已定义 `FORWARD / BACKWARD / BOTH`；`docs/01-PRD.md` §3.1 明确要求"客户投诉反查"与"原材料缺陷正向影响评估"两个方向。
- **后果**：`direction` 能力在契约层已就绪却没有界面出口；影响面数字（追溯最有价值的输出）完全缺失。

### 3.4 图例不完整、`★` 无解释、特采无凭据

- **现象**：图例只有 4 项（已合格 / 不合格 / 检验中 / 待检验）；节点卡片上的 `★` 与"特采"徽标没有任何说明。
- **证据（漏项）**：`packages/contracts/src/schemas/trace.ts:29-35` 的状态枚举是 **5** 个值，除图例 4 项外还有 `STORED`（已入库）；而原型图中确实出现了"已入库"徽标。
- **证据（特采口径）**：本项目"特采" = MRB 处置结论 `CONCESSION`（`packages/contracts/src/schemas/inspection.ts:41`、`packages/contracts/src/schemas/mrb.ts:86`），且 `mrb.ts:203` 要求必须挂**客户书面授权件**，缺失则服务端 400。
- **后果**：图例漏项 → 用户把"已入库"绿点误读为"已合格"；特采只有徽标没有 MRB 单号 / 客户授权件 → 审核时无法举证。

### 3.5 标题过度承诺："完整质量追溯链路"

- **现象**：订单维度的检验环节序列被命名为"完整质量追溯链路"。
- **后果**：与 PRD 的血缘语义冲突，形成"文档说 A、界面用同义词说 A′"的口径打架；用户会以为链路已经穷尽。

### 3.6 文档缺位（违反"文档优先"）

- **现象**：原型稿引入的订单维度筛选、订单信息卡、原材料追溯分区、时间线表格，在 `docs/` 下**没有任何规范章节**。
- **证据**：`docs/04-API与导入规范.md` §3.6 写的还是 `GET /api/v1/trace/genealogy` + `heat_no/lot_no/max_depth`，与真实路由 `GET /api/v1/trace/:batchNo` 和真实参数 `direction/maxDepth` **完全对不上**（历史遗留漂移，见 §9.2）。
- **后果**：下一次改动无据可依。

## 4. 改造方案（6 条建议，已批准执行）

| # | 建议 | 落地方式 |
| :--- | :--- | :--- |
| R1 | 每张卡片恢复**批次号 + 炉批号**；概览卡补**客户订单号 / 销售出库单号 / ERP状态** | 契约 `TraceNodeSchema` 新增 `materialCode / furnaceHeatBatchNo / inspectionOrderNo`；迁移 020 落列 |
| R2 | 查询主键回到**批次号 / 炉批号**；订单号 / 物料 / 成品名降级为**检索条件**，先出"匹配批次列表"，点行再开图 | 新增 `GET /traceability/batches`；前端新增"批次检索结果"表 |
| R3 | 增加**方向切换（正向/反向/双向）**与**影响面统计** | `TraceabilityGraphResponseSchema` 新增 `impact`；前端方向选择器 |
| R4 | 补全图例（含**已入库**、**特采**）；`★` 加解释；特采节点带 **MRB 单号 + 客户授权件状态** | `TraceNodeStatusEnum` 新增 `CONCESSION`；迁移 020 放宽 CHECK；前端图例与徽标 |
| R5 | 订单维度视图**诚实命名**：不叫"完整质量追溯链路"，改叫"**本订单检验环节**"；血缘链路只由批次图承担 | 前端文案与分区标题 |
| R6 | **文档优先**：先补本文 + 修订 `docs/09` / `docs/04` §3.6，再动代码 | 本文 + `docs/09` §3.3 + `docs/04` §3.6 |

### R2 / R5 的展开：页面为什么变成"两段"

改造后的页面是**两个并列的能力**，各有各的主键：

1. **订单入口（检索）**：「订单号 / 物料编码 / 成品名称」→ 命中一批**批次**（列表）→ 点任意一行进入批次图。
2. **批次主键（追溯）**：以 `batchNo`（或 `furnace_heat_batch_no`）为根 → 正向 / 反向 / 双向穿透 → 节点卡片 + 时间线 + 影响面。

其中订单维度的「检验环节序列」只作为**该订单的检验台账视图**，标题一律用「**本订单检验环节**」，不得使用"完整""全链路"等穷尽性表述 —— 真正的穷尽性链路在批次图上。

## 5. 数据与接口改造

### 5.1 数据库（迁移 `020_trace_node_lineage_fields`）

现状（迁移前 `batch_trace_nodes`）：`id / batch_no / stage_name / material_name / operator_name / node_status / order_no / supplier_or_customer / occurred_at / created_at`。

问题：**没有 `material_code`、没有 `furnace_heat_batch_no`、没有 `inspection_order_no`**，而 PRD 与原型都要求卡片显示"炉批号"与"检验单号"。

迁移动作：

| 动作 | 对象 | 说明 |
| :--- | :--- | :--- |
| `ADD COLUMN` | `batch_trace_nodes.material_code` | 物料编码（可空，回填自 `materials.material_name` 同名行） |
| `ADD COLUMN` | `batch_trace_nodes.furnace_heat_batch_no` | 炉批号（可空） |
| `ADD COLUMN` | `batch_trace_nodes.inspection_order_no` | 检验单号（可空，回填自同行的 `order_no`） |
| `DROP/ADD CONSTRAINT` | `batch_trace_nodes_node_status_check` | 由 5 值放宽为 **6 值**，新增 `CONCESSION`（特采 / 让步接收） |

> `CONCESSION` 术语与 MRB 侧 `MRBDisposition` 的 `CONCESSION` 保持同名同义（口径统一），不新造词。

### 5.2 契约（`packages/contracts/src/schemas/trace.ts`）

| 变更 | 内容 |
| :--- | :--- |
| 扩展枚举 | `TraceNodeStatusEnum` 新增 `CONCESSION` |
| 扩展节点 | `TraceNodeSchema` 新增 `materialCode?` / `furnaceHeatBatchNo?` / `inspectionOrderNo?` |
| 新增 Schema | `TraceImpactSummarySchema`：`downstreamBatchCount` / `upstreamBatchCount` / `downstreamOrderCount` / `downstreamPartyCount` / `downstreamOrderNos` / `downstreamParties` |
| 扩展响应 | `TraceabilityGraphResponseSchema` 新增必填 `impact` |
| 新增 Schema | `TraceBatchSummarySchema` / `TraceBatchSearchResponseSchema`（批次检索结果列表） |
| 新增 Schema | `TraceOrderChainStageSchema` / `TraceOrderChainResponseSchema`（本订单检验环节） |

### 5.3 接口（`/api/v1/traceability/*`）

| 方法 | 路径 | 用途 | 主键 |
| :--- | :--- | :--- | :--- |
| `GET` | `/traceability/batches` | 批次检索：按批次号/炉批号/订单号/物料编码/成品名 命中批次列表 | 批次 |
| `GET` | `/traceability/orders/:orderNo` | 本订单检验环节（订单维度台账视图） | 订单 |
| `GET` | `/traceability/graph/:batchNo` | 批次血缘图谱（含 `impact` 影响面） | 批次 |
| `GET` | `/trace/LOT-2026-FN-01` | 同上（历史别名，保持向后兼容） | 批次 |

`GET /traceability/batches` 请求参数（一律服务端过滤，前端不得二次过滤）：

| 参数 | 说明 |
| :--- | :--- |
| `batchNo` | 批次号 **或** 炉批号，模糊匹配 |
| `orderNo` | 订单号：同时匹配 `sales_order_po_no` / `sales_order_no` / `work_order_no` / `order_no` |
| `materialCode` | 物料编码，模糊匹配 |
| `productName` | 成品/物料名称，模糊匹配 |
| `page` / `pageSize` | 分页，默认 1 / 20，`pageSize` 上限 100 |

> 检索结果来自两个数据源并集：`batch_trace_nodes`（已建立血缘的批次）与 `inspection_orders`（有检验台账的批次）。
> 每行用 `sources` 字段标明命中来源；两个来源都命中的批次同时返回 `nodeStatus` 与 `relatedOrderNos`。

`GET /traceability/graph/:batchNo` 请求参数：`direction` (`FORWARD` / `BACKWARD` / `BOTH`，默认 `BOTH`)、`maxDepth` (1~10，默认 5)。

`impact` 口径：沿 `batch_trace_relations` 的 `parent_batch → child_batch` 方向做**递归闭包**，统计下游可达批次数、上游可达批次数，以及下游节点上的**关联单号**与**外部单位**（`supplier_or_customer`）去重数。

> **口径说明**：追溯节点表不区分"客户 / 供应商"，因此界面文案统一写"**下游单位**"，不写"客户数"。

## 8. 验收口径

1. `GET /traceability/graph/:batchNo` 返回的每个节点**必须**携带 `batchNo`；`furnaceHeatBatchNo` / `materialCode` / `inspectionOrderNo` 无值为 `null` 或缺省，**不得**用空串或占位符填充。
2. 响应必须满足 `TraceabilityGraphResponseSchema`（含 `impact`），且 `impact.downstreamBatchCount` 与独立递归推导结果一致。
3. `GET /traceability/batches` 的筛选条件**全部下沉 SQL**；前端不做二次过滤。
4. 节点的 `nodeStatus` 只能取 6 个枚举值之一；`CONCESSION`（特采）节点在前端必须同时展示 MRB 单号与客户授权件状态（无则显式提示"缺客户授权件"）。
5. 时间线表格的"耗时"列只允许出现时长或 `—`。
6. 订单维度分区标题必须为「本订单检验环节」，不得出现"完整""全链路"字样。
7. PBAC 命中拦截时接口返回 403，页面提示"权限拦截"而非"无数据"。
