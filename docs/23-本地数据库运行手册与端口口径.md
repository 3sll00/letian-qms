## 2. 唯一受支持的启停方式

```powershell
cd D:\乐天\letian-qms

pnpm db:local:status    # 状态体检（默认动作，只读）
pnpm db:local:doctor    # 完整体检：端口一致性 / 迁移滞后 / API 连通 / Docker 可用性
pnpm db:local:start     # 启动（端口永远取自 .env 的 DB_PORT）
pnpm db:local:stop      # 停止（fast 模式）
pnpm db:local:restart   # 重启
```

脚本入口：`scripts/db/local-db.ps1`，可用参数 `-DataDir` / `-PgBin` / `-WaitSeconds`，或环境变量 `LETIAN_PGDATA` / `LETIAN_PGBIN` 覆盖路径。

**结构性防漂移设计（四条口径）**：

1. **端口无命令行参数**：永远从仓库根 `.env` 的 `DB_PORT` 读取（无该键时再从 `DATABASE_URL` 解析，最后回落 `5432`），因此「脚本启动的实例端口」与「应用连接的端口」天然一致，不可能再出现 55432 这类手工漂移；
2. **只清理陈旧 `postmaster.pid`**：仅当其中记录的 PID 已不存在时才删除，避免「上次异常关机」导致启动失败，同时不会误删在跑实例的锁文件；
3. **启动前做端口占用检查**：目标端口被别的进程占用时直接报错，而不是静默失败或另起一个实例；
4. **退出码约定**：`0` = 正常 / `1` = 异常，便于脚本与 AI 协作流程判定。

## 3. 端口口径与历史遗留（为什么会冒出 55432）

| 端口 | 来历 | 现状 |
| --- | --- | --- |
| **5432** | 本机开发库正式端口，`.env`、`.env.example`、`docker-compose.yml`、`docs/08` 全部一致 | ✅ **唯一有效端口** |
| `55432` | ① 容器时代的 `DB_PORT=55432`（`docker compose up -d postgres` 把容器 `5432` 映射到宿主 `55432`）；② 与之配套的一份手工启动命令 `pg_ctl -D D:\letian-qms-pgdata -o "-p 55432" start` | ❌ **已废弃**：本机无任何进程监听 55432，连它必然 `Connection refused` |

两个必须知道的坑：

- **同一数据目录、不同端口**：那份遗留命令里 `-o "-p 55432"` 启动的就是 `D:\letian-qms-pgdata` 这个**同一个**数据目录，只是把端口改成了 55432。此时应用（按 `.env` 的 5432 连接）连不上，而按 55432 配置的客户端才能连上——**两边必然有一边报错**。
- **`D:\PostgreSQL\17\data` 不是本项目的数据目录**：它是 PostgreSQL 安装器自带、本项目**从未使用**的目录（Windows ACL 受限，普通用户读不到）。不要用 `pg_ctl -D D:\PostgreSQL\17\data` 启动。

**典型报错的含义**：

```
connection to server at "localhost" (::1), port 55432 failed: Connection refused (0x0000274D/10061)
        Is the server running on that host and accepting TCP/IP connections?
```

这是 libpq 客户端的标准报错（IPv6 / IPv4 各试一次），含义是「本机 55432 端口没有监听」。触发它的**不是**本工程代码，而是某个按废弃端口 `55432` 保存连接的客户端（Navicat / pgAdmin / DBeaver）或一条旧的 `psql` 命令。

**处置**：把该客户端的端口改成 `5432`（或删除该连接后按 §4 重建）；不要再使用上表②的历史启动命令。

## 5. 故障排查表

| 现象 | 根因 | 处置 |
| --- | --- | --- |
| `connection ... port 55432 failed: Connection refused` | 客户端仍按废弃端口 55432 配置 | 客户端端口改为 5432；并检查是否仍在用历史启动命令（§3） |
| `connection ... port 5432 failed: Connection refused` | 实例没起来 / 上次异常关机留下 `postmaster.pid` / 端口被占 | `pnpm db:local:doctor` → `pnpm db:local:start` |
| 启动报 `another server might be running` | 已有实例在跑（可能跑在**别的端口**），或 `postmaster.pid` 陈旧 | `pnpm db:local:status` 看实例实际端口；确认后 `pnpm db:local:restart` |
| 库里能连、应用连不上 | `.env` 端口与实例实际端口不一致 | `pnpm db:local:doctor` 会直接点出错配项 |
| `pnpm db:up` 报 Docker 相关错误 | 本机 **Docker 守护进程未运行**，容器路线在本机不可用 | 改用 `pnpm db:local:start`（容器路线仅用于其他环境） |
| 表 / 字段缺失导致接口 500 | 迁移未跟进 | `pnpm db:migrate`（`doctor` 会列出未应用迁移） |
| 表结构正常但数据不对 | 误执行了 `db:seed`（会清表重建） | 从 §7 备份或 `D:\乐天\db-backup-*` 恢复，再评估是否重播种子 |

**实例为何会「自己停」**：本机实例**不是 Windows 服务**，父控制台被关闭或进程被强制结束都会让它退出（实例日志实测过一次 `server process (PID ...) was terminated by exception 0x40010004`，即进程被外部终止）。要彻底消除「开机 / 重启后连不上」，见 §6。

## 6. 可选：注册为 Windows 服务（开机自启，需管理员）

> 仅在需要「开机即起、异常退出自动拉起」时执行；执行前先 `pnpm db:local:stop`。

```powershell
# 以下命令需在「管理员 PowerShell」中执行
$pg   = 'D:\PostgreSQL\17\bin\pg_ctl.exe'
$data = 'D:\letian-qms-pgdata'

& $pg register -N letian-qms-postgres -D $data -S auto -w
Get-Service letian-qms-postgres
```

注意事项：

- 服务以本机服务账号运行，需保证该账号对 `$data` 具备完全控制权限（必要时：`icacls $data /grant "NT AUTHORITY\NetworkService:(OI)(CI)F" /T`）；
- 注册成功后请**统一用** `Start-Service` / `Stop-Service`，不要与 `pg_ctl start/stop` 混用；
- 撤销注册：`& $pg unregister -N letian-qms-postgres`。

## 8. 真库形态自检：我起的前端到底连没连上这个库

本机有两种启动前端的方式，界面完全一样，但「保存」的去向不同：

| 命令 | 实际形态 | 保存写到哪里 |
|:---|:---|:---|
| `pnpm dev:all`（= `pnpm dev:api` + `pnpm dev:web`） | Vite `:5200` 把 `/api` 反代到 API `:3100`，MSW 关闭 | **PostgreSQL**（即本文件描述的库） |
| `pnpm dev:mock`（`vite --mode mock`，读 `apps/web/.env.mock`） | MSW 在浏览器里拦截 `/api/*` | **浏览器内存**，刷新即回演示值，**不落库** |

两者**端口也一样**（`.env.mock` 里 `VITE_PORT=5200`），因此「端口对不对」不能当作判据；`docs/35` §R7 记过一次真实事故：探针打到了「看起来一样」的真实后端代理实例，把库里一条 MRB 从 `UNDER_REVIEW` 改成了 `DISPOSED`。

一条命令给出**运行期**结论（只读、不写库、不点保存）：

```powershell
pnpm verify:dev-mode                                          # 扫描 :5200/:5201/:5202，自动挑真库形态实例受检
$env:WEB_BASE="http://127.0.0.1:5202"; pnpm verify:dev-mode    # 指定实例：mock 实例判 FAIL，退出码 1
```

`scripts/testing/dev-mode-check.cjs` 不读配置文件，四类运行期证据：① 形态（解析 dev server 下发的 `/src/mocks/browser.ts` 里被注入的 `import.meta.env` —— `MODE=mock` 或 `VITE_USE_MOCK=true` 即演示模式）；② MSW 开关；③ 经前端同源请求 `/api/v1` 必须得到真后端 `401 + application/problem+json`；④ 接口返回的单号集合必须全部存在于库内。同时列出 `:5200/:5201/:5202` 上**所有**在跑实例的形态，误起 mock 时一眼可见。

> 注意：③④ 只证明「服务端链路通」（Vite 代理 -> API -> 真库）。**Mock 实例上 ③④ 同样会通过**，因为 MSW 只在浏览器里拦截；判据永远是 ①② 的模块形态。浏览器侧的人工确认见 §8.1。

### 8.1 浏览器侧人工确认（可选，双保险）

在页面里按 F12，控制台执行：

```js
// ① 有没有 MSW 接管：真库形态下应为 0 条注册
navigator.serviceWorker.getRegistrations().then(r => console.log('SW 注册数:', r.length, r.map(x => x.active?.scriptURL)));
// ② 浏览器是否真的取过 MSW 脚本：真库形态下应为空数组
performance.getEntriesByType('resource').filter(e => e.name.includes('mockServiceWorker')).map(e => e.name);
```

Mock 形态下会看到 `[MSW] Mocking enabled.` 日志与 `/mockServiceWorker.js` 请求。

### 8.2 点保存后立刻查库

```powershell
pnpm db:recent            # 最近 5 条检验单（单号 / 类型 / 物料 / 状态 / 判定 / created_at / 相对时间）
pnpm db:recent 20         # 最近 20 条
pnpm db:recent 5 OQC_SH   # 只看某一类（order_type）
```

判据：真入库的新行 `created_at` 显示为「几秒前」；更新既有单时 `updated_at` 前移、`created_at` 不动。

### 8.3 改完后端仍报旧错：先确认 `:3100` 的进程不是旧进程

事实基线：`pnpm dev:api` 跑的是 `tsx src/server.ts`，**没有 watch / 热重载**；Vite 的 HMR 只覆盖前端源码
（`apps/web/src`）。因此「改完后端 -> 浏览器刷新」看到的行为仍可能完全是**改动前**的，尤其两条：

1. `apps/api` 依赖各包 `package.json` 的 `main`（`dist/index.js`），**改 `packages/*/src` 不重编不生效**：
   需 `pnpm --filter @letian/<包名> run build`（或根目录 `pnpm build`）；
2. 重编了 `dist` 但**没重启 API 进程**，进程内存里仍是旧 JS —— 本机 2026-09-23 实测过这一例：
   复检轮次续录修复落码并重编后，页面仍报 `ORDER_NOT_EDITABLE`，根因是 `:3100` 的 API 进程
   （`StartTime` 11:03）比修复更早，重启后同一次提交立即 `200`。

自查三步（30 秒）：

```powershell
netstat -ano | Select-String ":3100\s" | Select-String "LISTENING"   # 1) 取 PID
Get-Process -Id <PID> | Select-Object Id, ProcessName, StartTime      # 2) StartTime 早于改动时间 = 旧进程
# 3) 重启：Stop-Process -Id <PID> -Force 后重新 `pnpm dev:api`
```

前端 `:5200` 的 Vite 无需重启（刷新页面即可）；`apps/web/src/mocks/handlers.ts` 这类**离线 Mock** 改动
只影响 `dev:mock`（`:5201`）实例，真实形态页面不受影响。
